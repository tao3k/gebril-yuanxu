#+title: 20.36 Metadata Catalog Prototype

Catalog stores canonical symbolic module names, exact version labels and
dependency references. It pulls a stream of metadata rows into private
Gerbil red-black trees. The outer tree indexes names and each inner tree
orders the version labels of one name. Labels sort lexically for
enumeration. Resolution requires an explicit label and selects the exact
release object from the supplied snapshot.

Demand checks that the selected release still belongs to its snapshot and
calls the dependency metadata reader once with the name, version and
reference. Catalog retains the scalar reference. The reader owns its
interpretation and any I/O. Module and Prototype realization are separate
operations. Gerbil owns package installation, source lookup and imports.

Publication applies a finite edit batch to private persistent roots.
An edit supplies the actual expected release identity, or absence for
insertion. If a conflict occurs, the operation returns no successor.
Successful point edits share the untouched branches and do not enumerate
unrelated names or versions. Older snapshots remain queryable.

=CatalogPublication.lean= models the point edit, conflict, untouched
keys and exact release check. The Scheme tests exercise the same cases
with actual tree snapshots and count calls to the dependency reader.
The untouched-name projection preserves requested version order and
release identities. The proof abstracts tree balance and callback
execution. The native tests exercise lexical enumeration and dependency
callback cardinality.
The companion SysML requirement is =MetadataCatalogOwnership=.

The independent capacity test runs through =just test-file
t/qualification/catalog/metadata-capacity-test.ss=. It uses 100,000 and
1,000,000 releases in two distributions. The wide catalog has one
128-version name. In the skewed catalog one name owns half the release
rows. The same cases measure cold indexing, first and repeated point
lookup, version enumeration, one dependency request, two successful
edits, and rejection of a batch that conflicts after a provisional edit.
These are metadata workloads.

The first local native run used Gerbil =2591dcd= with the Core candidate's
installed dependencies. Both capacity cases and the separate functional
Catalog suite passed.

* Ordered edit differential

The functional Catalog Suite checks every prefix of one deterministic
replacement, insertion, deletion and reinsertion sequence. It compares
one-edit publication and batched publication with a cold reconstruction,
including missing versions, missing names and release identity. It checks
that the original snapshot still resolves the original row after a conflicting
suffix. This exercises the ordered publication and conflict contracts in
=CatalogPublication.publish_append= and =conflict_discards_provisional_result=.

An isolated fault used the original version bucket to refuse a valid
reinsertion after that version had been removed from the provisional root.
The differential Case failed at that conflict with exit 42. The restored
functional Suite passed through the same Gerbil entry.

* Single-release representation candidate

The prototype candidate stores a name's first release directly in the
outer tree and builds its ordered version tree when a second distinct
release arrives. The existing persistent edit path publishes the promoted
tree in a fresh outer root. =CatalogPublication.promote_singleton_version=
proves that both release identities resolve independently of insertion
order. The native functional suite passed. An isolated publication fault
dropped the first release on promotion. The same suite failed at the valid
add-then-replace batch because its expected original release had vanished.

The existing Just workload ran reference, candidate, candidate, reference
on Gerbil =2591dcd=. Both builds used the same compiler options and workload.
All four invocations passed. Each invocation constructed four independent

The next candidate skips the spelling round trip for already interned
symbols. Noninterned symbols still use Gerbil interning. It also checks
duplicate versions directly in the representation being updated. With the
same four-run comparison the 100,000-row skewed CPU medians were 171.4 ms
for the reference and 173.9 ms for the candidate. GC still took about 60 ms
with the candidate, compared with about 40 ms in the reference. The functional
case checks that an uninterned name and version resolve to the same release
as the canonical symbols. =CatalogPublication.canonical_symbol_fast_path=
states the fixed-point condition that justifies the shortcut.

A further candidate carries the current name's version bucket while building
the private root. It refreshes that bucket when a singleton is promoted.
A different name reads the original outer index, as modeled by
=CatalogPublication.current_bucket_lookup_exact=. For the million-row skewed
fixture this avoids 499,999 outer lookups because the hub releases are adjacent.
The Scheme functional case interleaves names before adding a third version.
An isolated fault retained the pre-promotion bucket. Enumeration returned
=(v2 v3)= instead of =(v1 v2 v3)= and the test refused that result.
Four more capacity invocations passed. The candidate's million-row skewed
CPU samples were 1.991 and 2.430 s, and the paired reference samples were
2.287 and 2.356 s. Peak RSS remained about 958 MiB versus 1,248 MiB. The
100,000-row skewed candidate still took two collections. The retained CPU
and wall samples do not establish a consistent improvement for the skewed
workload. This variant remains an experiment.

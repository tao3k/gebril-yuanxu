* System boundary

Official =std/test= owns discovery, TestSuite registration, execution and
assertions. The existing Just entry fences the process before imports. Product
tests now default to 2 GiB, explicitly requested by the maintainer; this is a
capacity setting, not an optimization or a passing performance result. Source,
Case and build deadlines remain unchanged.

| Phase | Owner | Permitted demand |
|-------+-------+------------------|
| Discover source tests | Gerbil gxtest | Import files and obtain TestSuite values |
| Register Cases | std/test | Create TestCase descriptions and deferred bodies |
| Execute a Case | Existing Case Profile | Resolve the current method and enforce its policy |
| Import a workflow composition | Scenario Type and prototype | Construct a lazy POO value |
| Read a composition field | POO/MOP | Compute the field using the final receiver |
| Prepare a plan | Scenario input Contract and existing projector | Validate final inputs before deriving the plan |
| Publish a selected Module | Existing publication protocol | Independently authenticate source and obligations |

Test discovery must not activate Profiles merely because a composition library
is imported. Explicit namespace access inside a demanded field remains an
ordinary Module System operation, with its complete source admission. Moving
that expression into a lazy field neither grants missing dependencies nor
memoizes publication approval.

* Source correspondence

Core's =modules/funflow/scenario.ss= defines one =Scenario= using
native =define-type=, =Record= and =proto=. The Record owns the name,
configuration and constant tags. Its prototype owns derived fields and behavior.
This is the existing workflow composition value, not a special Module kind or a
new Scenario loader. Ordinary =def= and native =.new= name the composition.
There is no ProfileBundle-to-intermediate-Case factory chain.

Scenario libraries bind required Module values inside the computed configuration
expression, rather than top-level =.get init.exports Profiles ...= definitions.
Planning invokes native =validate= on the final receiver. Cached parent fields
do not supply the child's configuration, and malformed final configuration must
refuse before a plan is produced.

The shared Case invocation lives in =observability/testing-case.ss=. It keeps
the current Profile lookup and original body; only common executable code is
shared. Methods, Type checks, receipts and admission conclusions are not cached.
The product no longer publishes a second testing macro facade. Ordinary tests
import the Core owner; optional ASP policy composition stays in the existing
development package.

Lean =Observability.TestingCase.factoring_preserves_invocation= establishes

** Source routing and phase ownership

The ownership partition proposed below is not a closed production result.
Parallel downstream qualification identified that selected Graph entries are
SOURCE obligations, including entries outside the consumer's package prefix.
That prefix is an output-naming fact, not evidence that the source has become an
installed prerequisite. Retain the complete selected obligations. The canonical
library routing control is separate from a completed, source-identical product
cold/hot build. Do not describe the latter as qualified while sources change or
a build is incomplete. The earlier local-only partition
tests do not replace the independent downstream source-build control.

The current =package-library-spec= is not a metadata-only projection. It calls
=core-import-module= on each public root before walking the resulting expander
contexts. Cold requests therefore include macro expansion and compile-time
initialization. A shared visited set bounds the subsequent context traversal;
it does not eliminate the preceding expansion cost. Do not report this interval
as ordinary list projection, native Make scheduling, or Module runtime loading.

The installed Gerbil source separates the responsibilities:

| Owner | Actual operation |
|-------+------------------|
| Yuanxu =building/source-closure.ss:package-library-spec= | Expand roots, traverse contexts, enforce the production dependency policy, enumerate targets |
| Yuanxu =building/build-projection.ss:project-selected-source-spec= | Merge selected and retained entries, prepare source observations and compiler inputs |
| Yuanxu =source/preparation.ss:call-with-selected-source-view= | Materialize owner-qualified source paths when the projection contains foreign owners |
| Gerbil =std/make.ss:make-build= | Import targets, establish dependency completions, check freshness, schedule compilation |

Gerbil's =expander/module.ss:core-import-module= caches contexts by requested
and normalized source paths. The same module identity at a different source
path is not sufficient to reuse the original path's context. Consequently,
expanding original sources for enumeration and later compiling a generated
source view can duplicate expansion. The previous foreign-owner branch routed
all entries through that view, including ordinary retained libraries. A foreign
role must not silently turn every unrelated library into a new source instance.
This is a source-routing design issue, not grounds for another cache protocol.

Native Make still needs a target inventory: its coordinator waits on dependencies
whose identities occur in that inventory. Supplying only public roots can omit
private compilation targets. Deleting the closure walk without replacing that
inventory responsibility is therefore not a valid repair. Similarly, absolute
source paths are not a drop-in replacement for target names: Make also derives
library and static output paths from those names.

The repair must preserve one effective compiler source per target within a build
invocation, apply role lowering only where required, and let Make own dependency
scheduling. The source-policy callback must still inspect every reachable
dependency, including excluded output targets; enumeration is not permission to
skip policy checks. Input currentness, compiler-entry/return checks and separate
publication issuance remain independent obligations.

The required boundary keeps =yuanxu!= as the only selected-module spec export.
The package entry independently produces its library spec and passes that value
to =init.exports.std-make-spec= for the existing native build consumer. Inside
the projection, module targets are derived from the selected entries; library
targets retain their original native strings/options. Identical overlaps are
checked and emitted once. Ordinary library inputs must retain canonical source
identity rather than acquire a second role-source identity.

The compiler-input owner now derives the role inventory from admitted
publication inputs. Only those inputs emit role forms. A selected ordinary
library retains the existing Make input descriptor (a comment binding source
bytes, options and tools), but no Scheme module body is emitted there. The
existing extent-owned compiler-input association routes that descriptor to the
original Gerbil source path. It is neither a new public source registry nor an
approval cache. The real importer keeps its original context cache; source
admission still runs before and after import. Actual roles reuse their one
stable generated frame instead of another temporary copy in the same build.

The =module-build-role-test.ss= control requires the descriptor to read as EOF,
the resulting Context to be =eq?= to the original-path Context, and an original
source mutation to be refused even with that Context hot. Existing lifecycle
and downstream controls must additionally verify real compilation, equal-mtime
changes, interrupted retry, output isolation and complete foreign source input
coverage. These are separate gates; a canonical Context assertion alone does
not establish a complete product cold/hot result.

** Publication guard: pure work versus callback boundaries

The existing operation measurement reports inclusive =(read-attempts stage)=
counters for reader preparation, currentness, role imports, selected-graph
construction and Make. Nested spans overlap: adding their counts double-counts
work. A read attempt counts entry into content I/O, including failures; it is
not every logical read request, a guaranteed completed read, a compiler invocation
or a macro expansion. The counters do not install a source observer or change
read windows.

The current import input authenticates its owning publication before and after
Gerbil import, including repeated imports of an already registered Context.
Whole-graph checks around Make do not justify deleting these guards: an import
callback could change an earlier dependency and restore it before Make returns.
Source-window bytes cannot cross that callback. A future hot-import convergence
must establish the actual callback-free native branch and guard correspondence;
neither a source label nor a claimed pure function establishes this premise.

Within the existing closed synchronous guard, positive validation already checks
regular-file kind. Its private content reader reuses that check and the existing
byte table, avoiding the second kind query and a separate cache-membership lookup.
Public reads retain their regular-file check. An active source observer retains
the former query/callback sequence, even if it removes itself at the first event.
No observations survive an independent admission or effect boundary.

Lean =SourceWindows.pure_window_preserves_first_issue= proves ordered diagnostic
preservation under a sound stable-world byte table; =positive_bytes_imply_kind=
states the positive-observation implication. Native file-kind correspondence,
I/O exception identity and observer entry extraction remain Scheme obligations,
not consequences of that abstract theorem. Existing Quint =SourceWindows=
controls cover cross-effect reuse, omitted requirements, competing contributions,
parent isolation and laziness; no second lifecycle model is introduced.

** Prepared input checks are not compiler invocations

=link.prepare= binds a publication-local source preparation to the selected
link generation. Its =admit-current= first authenticates the link, invokes the
base preparation guard, and authenticates the link again. Thus a compiler input
lookup can reach the Reader's complete observed support; counting that work as
another compiler process would misidentify both its owner and its remedy.

The existing invocation-local measurement distinguishes the following sites:

| Producer site | Measured boundary | Work retained |
|---------------+-------------------+---------------|
| =link.prepare= wrapper | =prepared-input-before= / =prepared-input-after= | Link metadata and Reader support surrounding the base guard |
| =module-compiler-source-input= | =compiler-input-lookup= | Admission before exposing an enrolled input |
| =call-with-role-compiler-inputs= | =compiler-role-inventory= | Admission before materializing a role frame |
| Native import handoff | =compiler-import-before= / =compiler-import-after= | Independent checks surrounding import/initialization |
| Selected source view | =compiler-view-before= / =compiler-view-after= | Independent checks surrounding metadata demand and writes |

These are nested, inclusive spans, not disjoint filesystem totals. Reader
subspans identify which linked boundary actually read bytes. Repeated calls
within an existing pure window may already share bytes; a repeated call count
does not establish repeated physical I/O. Measurements retain only scalar
counters and do not install a source observer, extend a window, or authorize
skipping a guard.

restores the source. Existing Quint =SourceWindows= supplies independent
lifecycle controls for cross-effect reuse, missing requirements, conflicting
requirements, parent plans, eager demand and omitted return checks. Neither
model proves that a native import cache hit makes the surrounding extensible

** Native context identity and callback resumption

The preparation constructors receive the owning context procedure itself.
Only =eq?= with native =void= establishes that this particular context step
cannot call author code. It does not classify a procedure by name, SourceRef
label, warm cache state or a claimed purity flag. A native =void= context keeps
the existing pure source-byte window; byte/package checks still execute and a
new independent window still reads both inputs. The constructors bind their
no-context admission directly to =check-source!= once, avoiding two callback
wrappers or repeated runtime classification on each native guard call. This
local specialization does not remove any source comparison. The stable-world premise of an
existing pure window remains explicit: this does not supply an atomic snapshot
against another process changing files concurrently.

Every other context procedure passes through
=call-with-module-source-callback=. This suspends the existing byte window and
clears its observations before the call and on resumption using =dynamic-wind=.
The latter includes exception unwinding and continuation reentry. Suspending
alone is insufficient: restoring an enclosing table can expose its pre-callback
bytes even after the prepared input itself has rejected. The helper neither
adds an admission check nor changes its order; it invalidates the existing
observation table, including query/comparison entries, without touching source
collectors, contribution requirements or the exception being propagated.

Lean =SourceWindows.context_resume_sound= proves the identity/opaque split;
=context_resume_checks_all= retains every requirement and
=context_resume_preserves_first_issue= retains diagnostic order. Quint's
existing =SourceWindows_cross= counterexample rejects cross-effect byte reuse.
The Quint lifecycle does not model Scheme continuation machinery or establish
exception identity. The native =module-build-role-test= supplies those required
controls for normal failure and callback exception unwinding, and verifies two
independent native-void windows rather than caching an admission result.

This is a prerequisite correctness repair, not a proof that all linked guards
are passive or that whole-closure authentication may be removed. In particular,
=link.current!= still reaches Reader guards, native MOP replay, and potentially
extensible context/observation routes. Keep its checks at callback boundaries
until those remaining paths have their own production correspondence.

The remaining audit separates concrete callees, not a broad native/extension
label:

| Actual route | Callback boundary | Consequence |
|--------------+-------------------+-------------|
| Preparation's native =void= context | No procedure body beyond =void= | Bind =check-source!= directly; retain the existing byte window |
| =check-source!= byte/package reads | Source observer delivery when installed | The context proof alone does not certify this entire guard |
| Reader's public dependency guard | =module-compiler-source-input= invokes the selected input's =admit-current= | A native resolver path can still reach an extensible procedure |
| Link's complete metadata check | General publication fallback versus gated issued-read replay | Replay qualification does not prove the Reader's source guards passive |
| Compiler =import-input= | Input admission, then the captured Gerbil importer, then input admission | A native registry hit does not classify the surrounding admissions |

In particular, this repair does not mark a prepared object pure because it was
created by Core. It specializes only the constructor branch whose actual
context procedure is =void=. Source observers, selected compiler inputs and
general publication fallbacks retain their original open-route checks.

** Fresh-process correspondence

Semantic domains share the platform build, not a Scheme VM. The official
Harness imports all selected files before running any Case. An experimental
shared-Harness module run exposed both an already-loaded execution library and
a retained build-source binding into a released fixture. These failed samples

compiled-module integration test has its own job. This retains the previous
fresh-process assertions without reintroducing a development runner.

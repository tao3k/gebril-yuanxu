* One existing phase owner, two official initialization mechanisms

=module-system/source/deferred-declaration.ss= already owns source/runtime
projection boundaries. Its internal =module-entry-action= inspects the runtime
creating context: exact owner identity, module context and a source =.ss= path.
Only that actual source-evaluation route uses official =eval-syntax/import=.
It resolves the canonical binding AFTER initialization on every invocation.
The private closure retains immutable identifiers, not the creating context.

Compiled creation and unrelated callers use upstream =io.module-action=.
There is no catch-and-fallback on =module not found=, user source/compiled flag,
retained business procedure or second initialized-module registry. Source imports
use the standard Core importer in a fresh lexical context; publication importers
cannot capture built-in factories. Dynamic parameters restore on exceptions.
Both mechanisms preserve runtime initialization errors and tail =apply= results.
Source and artifact currentness remain at their existing build/admission owners.

This context test is an interpreter/compiler correspondence under the trusted
Gerbil context machinery, not an authentication proof against arbitrary runtime
metadata mutation. It does not promise automatic source reload within one epoch.
Changed source still requires rejection and a new source session.

* Why the first sixteen-module query is expensive

The existing census now uses installed Gambit's =##exec-stats= around the whole
query and three sequential envelopes. It retains only scalar stage diagnostics
and the original read records; it installs no new observer. Output occurs after
the measured operation. Signed VM allocation accounts can be negative and are
not claimed as physical allocation or exclusive retained bytes.

An initial accounted run was 8.406 seconds wall / 6.346 CPU at 16 modules,
including 0.571 GC wall. It cannot be explained solely by GC or scheduling.
The later stage-attributed run of the same production code was:

| Modules | Cold wall / CPU | Hot wall / CPU | Issued records | Cold / hot role expansion |
|---------+-----------------+----------------+----------------+---------------------------|
|      16 | 5.656 / 5.615 s | .0689 / .0688 s |           4985 |                    32 / 0 |
|      32 | 4.108 / 4.059 s | .1451 / .1450 s |           8600 |                    64 / 0 |

The first 16-module envelopes are sequential: source acquisition 3.704 seconds,
Graph read 1.890 seconds, final independent authentication .062 seconds. Existing
fixture spans place .083 seconds in init import and 2.607 seconds in the FIRST
module-namespace demand. The runtime linker entry and namespace initialization
are therefore the next major cold boundary; directory context itself accounts
for only .0012 seconds. The next 32-module Case shares initialized libraries:
its namespace demand is .0025 seconds and source acquisition .195 seconds.
This is a concrete one-time/case-order distinction, not evidence that a 32-module
Graph is inherently cheaper than a 16-module Graph.

Reader bootstrap (.857 s), candidate reads (1.703 s) and interface reads (.797 s)
overlap inside those envelopes; they must not be added to an invented total.
In the 16-module cold phase GC wall is .314 seconds and minor faults total
148,773, with zero major faults. Those counters locate memory/page pressure but
do not by themselves prove a disk-I/O bottleneck. The first namespace entry's
module loading versus prototype initialization still needs a narrower runtime
attribution before another production optimization is justified.

The hot envelopes spend essentially all their time in independent authentication;
source and Graph getters are microseconds. Removing that authentication or
prewarming outside the reported cold interval would change the guarantee or
hide the cost. Neither is performed. No performance speedup is certified from
these unpaired, differently initialized cohorts.

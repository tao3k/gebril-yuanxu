#+title: 20.21 Build Execution Cost

* Workload boundary

This investigation concerns the Core package's ordinary =gerbil build=, with
the existing 300-second build deadline, 2 GiB heap and two runtime compiler
workers. It does not change Module namespace acquisition or Loader semantics.
The previous 52.55-second zero-compilation receipt did not contain phase
measurements, so attributing all of it to source checks would be unsupported.

The source cohort is the unpublished coordinated Core/runtime-POO qualification
used by 20.20; the declared dependency pin is not advanced. Runtime compiler
and runtime sources are unchanged. All raw receipts remain local artifacts.

* Actual execution and authority

1. The installed package tool starts the package's source build entry.
2. =build.ss= registers its package/prelude, imports its library consumers and
   discovers the ordinary library specification through runtime import metadata.
3. =init.exports.std-make-spec= projects the selected Module compiler inputs
   and combines them with those ordinary library targets.
4. The existing =.with-compiler-inputs= checks current sources, installs the
   role-input association, and calls the official build-script consumer.
5. Product repair precedes runtime Make. Product completeness and a fresh source
   check follow it, before returning.

This path does NOT issue a publication approval. Explicit =.compile= owns
=call-with-build-artifact-issuance=. Avoid timing ordinary product checks as
though they were that separate signing path.

The installed =std/make:make-build= first imports each target to establish
completion identities. Its coordinator imports the target, considers actual
imports, checks target and dependency timestamps, and posts completion even
when it queues no compilation. =module-id= can import the same target again.
Those are runtime operations; the Core input hook's checks before/after runtime
import are not replaceable by a saved successful admission.

* Convergence decision

The four compiler-current calls and the two product checks are not the dominant
cost. Their identities remain distinct: projection return, init specification
consumption, compiler-entry and compiler-return. Imports and compilation may
run code between them. Do not remove them or extend a byte window across them.

The dominant open questions concern compiler projection construction and runtime
Make dependency/import work, including GC and wall/CPU variation. Module-load
benchmarks are not substitutes for either measurement. Reusing an import's
context is not by itself proof that its source association remains current.
Reusing an existing POO value must preserve its receiver/revision, complete
dependencies, first failure and observer order. The initial accounting slice
only attributed these costs. The production import convergence below then
reduces duplicate runtime binding/dependency representations; it does not reuse
approval results or replace Make's coordinator.

** std/make boundary found during the comparison

The installed =std/make.ss:build-dependent?= recursively normalizes each runtime
module-import/export/import-set node, then calls =dependency-timestamp= for
every encountered owner. =only-in= emits individual aliases; a zero-compilation
coordinator must visit all of them because no newer dependency short-circuits
the traversal. Repeated aliases can therefore repeat the same library-path
resolution and output timestamp comparisons. Runtime =core-import-module=
already has a module registry: adding another Core procedure/context cache is
not a fix for this repeated runtime dependency work.

A potential standard-library change would scope identity reuse to ONE
=build-dependent?= invocation after its completion waits, never to a build
session or accepted plan. It must retain every import edge, the first failure,
and fresh observations at the next target/callback/return boundary. Sharing a
timestamp requires a stable observation window; the existing SourceWindows
proof does not establish filesystem stability or runtime compiler immutability.

Core has no public std/make dependency-query hook. Mutating shared expander
contexts, rebinding installed Gerbil procedures, copying Make into a Core Builder,
or trusting a manually marked pure callback are rejected approaches. A runtime
standard-library fix would need separate qualification and authorization. None
is installed. Instead, the final production change below uses the existing
runtime import representation, without changing Gerbil sources.

** One production data flow, three representation fixes

1. =source/build.ss= constructs selected and retained Build Entries with runtime
   lexical slots: =(.o kind path compiler-identity input options owner contributor)=.
   These bindings are immutable local values, not receiver formulas. The
   original entry, input and read identities are not merged. All conflict
   checks and guard calls remain. =source/preparation.ss= similarly captures
   path, compiler identity and the SAME admission procedure directly. Its
   compiler forms and source-input formulas remain demand-computed. Runtime
   reflection gates check direct constant specifications and retained lazy forms.
2. Completed Make groups capture =prefix= and =spec= as runtime values. A spec
   getter no longer retains the entire mutable grouping table after assembly.
   Grouping still occurs only on demand, after all contributions are present;
   no live receiver formula or user callback is frozen.
3. =building/source-closure.ss= keeps the live DFS cursor in tail arguments,
   saving suspended frames only when descending into a new runtime context.
   The old walker allocated a replacement pair/spine for EVERY candidate,
   including duplicate aliases of an already visited context. The new walker
   keeps the same identity table, normalization, prelude checks, postorder and
   callback boundaries. It mutates neither import metadata nor private frames,
   and retains nothing across independent traversals.

For T normalized candidates and D descents, the explicit pair/spine allocation
sites change from =2 + 2T + 2D= to =2D=, excluding the common root-pending list.
This is a source-level allocation count on the same trace, not measured VM
allocation or exclusive live bytes. Lean =cursor_frame_cells_saved= states this
bound. =Admission.DFSFrames.cursor_enter_refines= and =cursor_return_refines=
connect the hoisted cursor to the EXISTING identity/frontier model. Its order
field tracks entry order; runtime tests, rather than that field, check postorder
callbacks, pruning, shared nodes, cycles and original exception identity.

** Keep the runtime prelude import-set

The prelude previously used import filtering to remove two constructor names.
Runtime =except-in= flattened Gerbil Core into thousands of import nodes, each
of which runtime Make can normalize and timestamp independently. The production
prelude now uses the existing import/export forms:

#+begin_src scheme

        :clan/poo/object
        (phi: +1 :gerbil/core)
        (phi: +2 :gerbil/core))

        (import: :clan/poo/object)

filter is qualified for THIS interface, not an arbitrary import rewrite. A

resolved binding =eq?=. It also checks the SAME 96 dependency contexts in the
SAME postorder. Top-level import nodes change from 6890 to 4. Aliases remain
inside runtime import-sets, not discarded or represented by a manual source table.
Bootstrap regression checks the complete Core import-set and POO constructor
identity. No replacement only-in macro or alternative loader is introduced.

The control is an isolated runtime metadata audit, not Module admission. The

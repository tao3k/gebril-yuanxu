#+title: Development System Architecture and Verification Allocation

* System entry

[[file:00-development-assurance.sysml][00 Development Assurance]] defines the
responsibilities of architectural modeling, temporal analysis, proof, runtime
correspondence and measurement. It is a textual SysML v2 design, not a new
build graph. The existing native selected graph and Just entrypoints execute work.
SysML parsing/semantic validation is not yet qualified in this repository.

Only populated areas get directories. A concern spanning areas has one primary
owner and cross references; it is not copied into several models. Existing QNT
and Lean paths remain stable. This index allocates their responsibilities and
does not relocate or duplicate them.

* One formal owner per question

| Question | Primary owner | Reuse instead of duplication |
|----------+---------------+------------------------------|
| Which immutable structures may share storage without changing lookup, identities or ordered edges? | Lean / LeanPoo | =PayloadSharing.lean=; no matching QNT copy |
| Can callbacks, invalidation, recovery or event ordering admit a stale value? | QNT | Existing =IssuedRootForwarding=, =ReadRetention= and =IncrementalRoles= transitions |
| Does the actual MOP preserve the modeled relation? | Scheme consumer regression | Existing Just/Harness controls |
| What is retained or allocated? | Bounded runtime measurement | GC accounts plus classified identity-union census |

SysML allocates these claims and assumptions; it does not prove them. A
workstream may have only a Lean owner or only a QNT owner. Shared premises
are linked, not reimplemented. The duplicate =PayloadSharing= QNT family
and its runner/digest bindings have been removed; historical receipts remain
historical, not current qualification requirements.

This allocation is not a ban on cross-tool refinement. If Lean must establish
an unbounded property of a transition abstraction, name that additional theorem
and its correspondence explicitly; copying the same finite assertion into two
tools is not that refinement.

The evaluation workstream includes [[file:10-evaluation/10.02-runtime-accounting.org][10.02 Installed Runtime Accounting]],
which separates native VM accounts from physical allocation and records the
matched source-window lookup control under the same SysML ownership model.
[[file:10-evaluation/10.03-replay-structure-ownership.org][10.03 Replay Structure Ownership]]

[[file:10-evaluation/10.04-declared-revision-replay.org][10.04 Declared Revision Replay]]

[[file:10-evaluation/10.05-issued-traversal-projection.org][10.05 Issued Traversal Projection]]

[[file:10-evaluation/10.06-issued-record-storage.org][10.06 Issued Record Storage]] separates duplicated issuer closure storage

[[file:20-module-loading/20.02-metadata-projection-correspondence.org][20.02 Metadata Projection Correspondence]]

before production Loader changes.

* Required trace for each workstream

| Question | Required artifact | What it cannot establish alone |
|----------+-------------------+--------------------------------|
| What is the system boundary? | SysML structure, actions and requirements | Executable correctness |
| What sequence must fail? | Existing QNT owner and matched negative trace | Unbounded correctness or filesystem trust |
| What property is preserved? | Lean statement, premises and Scheme projection | Native behavior without correspondence |
| Does current code implement it? | Source entry + focused Just regression | Untested executions |
| Is it more efficient? | Same workload, cold/hot action and time counts | Stable speedup from a single run |

Every row has an evidence status: design, modeled, machine-checked or runtime
observed. Status is per property, not a blanket badge for an entire workstream.
Model files do not carry trusted currentness results into runtime.

* Scope and result

This extends [[file:32.19-root-owned-child-analysis.org][32.19]], without modifying Scheme or integrating a Loader.
The question is which of its remaining 356 reads are redundant certification,
not whether repeating a path name implies repeating the same observation.

user-facing record format, purity DSL or authority-bearing success flag is added.

Result: keep the three open-callback whole-closure boundaries. A covered check
can be deferred into a complete final pass ONLY inside a qualified pure suffix.

read-only execution alone do not justify moving the JSON checks.

* Why the open boundaries cannot be merged

1. W4 authenticates callback entry, even if a later final check would reject.
   Deleting it may let an effectful callback run on stale inputs.
2. W5 obtains a new observation after the contribution callback. Sharing W4's
   cache can hide that callback's write.
3. Diagnostic locators are replaceable too. Success with empty diagnostics may
   invoke none, but that does not qualify all admissions or future locators.
4. A Context callback can check sources, then write one and return normally.
   Its own successful check is therefore not a post-callback certificate.
5. MOP =replay-slot-reads!= invokes the =current?= procedure stored in each read
   record. =make-slot-read= is exported by gerbil-poo's observation module. The
   native producer in =object.ss= uses =object-read-current?=, a structural
   revision/instance/value check. This does not prove every constructible or
   injected record uses that producer or is effect-free.

Consequently, the default open replay path ends with an independent fresh check.
A byte cache is never made current merely by retaining a receiver, epoch label,
previously accepted receipt, or callback function name.

The read-record inspection above is bound to gerbil-poo
=ece6f609357ea918038090559ac051a8d9f3e52f=. No dependency change is proposed.

* What the Lean proofs establish

=check= is the existing SourceWindows operation backed by LeanPoo
=ConstructionCache.ensureLookup=. Its filesystem argument is an actual function
=String -> Option String=; =Sound= says every cached byte observation agrees with
that function. A fresh empty cache establishes this condition constructively.

| Theorem | Derived result |
|---------+----------------|
| =check_append= | Sequential pure checks equal concatenation in acceptance, resulting cache and read count |
| =check_sound= | Checking in one stable world preserves source-cache soundness |
| =covered_suffix_zero_reads= | Already covered requirements require no new I/O in the same sound window; comparisons still execute |
| =conflicting_suffix_rejected= | Reusing a path does not erase a conflicting expectation |
| =defer_covered_check= | If the complete pass includes every exact earlier source/text pair, it also establishes the earlier predicate |
| =admission_same_world= | Sound byte reuse preserves the complete existing root predicate, not just object shape |
| =joint_requirements_retained= | Every selected port requirement still holds on the final configuration |
| =cached_parent_rejected= | A parent's analytic candidate cannot authorize a different final child |
| =fresh_after_callback_rejects_change= | A new check rejects a changed selected source |

Through =admission_same_world=, the existing root source-certificate and exact
contribution-coverage laws still apply. Source-cache hits are not admission
receipts. The native value-cache distinction is supplied independently by
LeanPoo =ContextSlot.read=: =SourceWindows.child_misses_parent= and =final_value=
prove that a different final receiver misses the retained parent and reads its
own constructed values. Mapping native references/revisions to these contexts
remains an explicit correspondence premise.

A small computed two-path witness checks cost 3 versus 2. An attempted synthetic
88-path kernel reduction reached Lean's existing recursion limit; that failed
attempt is retained. It was replaced by the general coverage/composition proof
and a small computational witness, not a higher recursion or trust limit.

* Conditional optimization frontier, not a new performance claim

After the LAST open callback has returned, consider the two document checks and
the final complete source projection. The final collector has already observed
the earlier successful document checks, so their exact requirements must remain
in that projection. Under a qualified read-only replay, no further callback,
no dropped/new unobserved requirement, stable source observations and a frozen
receiver/revision, the earlier document predicate can be discharged by the
complete final predicate. The final pass still checks all 88 requirements.

For the recorded cut, this identifies two potentially redundant document reads,
not another 87/88-read callback pass. A hypothetical 356-to-354 count would ALSO
require native validation of these premises and equivalent failure behavior.
It has NOT been measured, implemented or proved as an end-to-end Scheme cost.

The current replay API alone does not establish the closed-producer premise.
Nor does =Sound= prove a callback pure: soundness must be rebuilt after effects.
Any future adapter must qualify the actual replay producer and passive observer
behavior, materialize requirements without hidden getters, retain late demands,
and preserve the independent final certification. Until then, retain the open
path and all 356 reads.

The theorems establish acceptance/certificate and abstract read-count laws.
They do not establish identical first-error ordering, diagnostic message/source
positions, regular-file adapter completeness, exception traces or arbitrary
Scheme callback behavior. A future change must preserve those observations too;
set inclusion alone is insufficient justification for moving an exception across
another potentially failing operation.

* Reflection and next design questions

The useful result is the semantic boundary, not a promise to remove most of 356.
Most observed reads have distinct callback/return responsibilities. Deduplicating
path names across those boundaries would weaken the module system's guarantee.
The remaining narrow pure-tail opportunity is small in this Scenario.

Before a Scheme refactor, answer and validate:

1. Can Core obtain a closed, producer-qualified replay projection without trusting
   arbitrary =current?= callbacks or adding user-visible purity flags?
2. Does that projection preserve every selected requirement and newly discovered
   source, including different expectations for the same path?
3. Can the private final checker preserve diagnostic ordering and actual source
   locations while checking the same frozen final receiver/plan association?
4. Are object revisions and payload immutability sufficient throughout the final
   suffix, and are all tracing observers actually passive?
5. Does removing two reads improve real latency enough to justify the additional
   protocol surface? Read counts alone do not answer this.

No new user configuration syntax or manual source/evidence declarations follow
from these proofs. Users still configure the Scenario; Core owns certification.

** Two additional openings in the Core observer chain

The actual source adapter passes a singleton path:

#+begin_src scheme
(admit-field-sources! receiver (list (list key)))
#+end_src

This avoids the deeper =.ref= path-walk branch of =admit-field-sources!=. It does
NOT prove the whole call pure:

1. =slot-origins= calls =compute-precedence-list!=. A warm linearization is a
   structural read. A cold one can invoke =compute-precedence-list= through
   =invoke-object-hook=. The hook can have effects even if it returns the required
   C3 order. A preparation invariant would need to cover every replay receiver
   and ancestor; it is not established merely by the singleton path.
2. =module-source-read= and its guards invoke =current-module-source-observer=.
   The parameter is exported and accepts executable code. Slot replay's
   =without-observation= suppresses POO read observers/prechecks, not this source
   observer. Existing numeric-counter observers are not a proof about all
   replaceable observers.

Accordingly, the comment in =admission/source.ss= calling this pass pure is an
intended adapter discipline, not a proof of all producer/hook/observer closure.
No Scheme comment or behavior is changed in this proof-only work.

* Ordered replay projection and exact source coverage

[[file:../../../dev/proofs/lean/YuanxuProof/Admission/ReplayBoundary.lean][Admission.ReplayBoundary]] reuses =SourceWindows.fetch= and therefore LeanPoo's
=ConstructionCache.ensureLookup=. Its closed operation algebra has only concrete
source requests and structural token-coordinate comparisons. It has no
function-valued operation, getter, observer, public purity flag or alternate
runtime evaluator. It is a proof projection of a restricted program, not a
claim that every MOP replay already lowers to that program.

#+begin_src lean
inductive Op where
  | source (request : Request)
  | token (key : String) (recorded current : Binding)

-- Request includes path, expected bytes, message and location.
theorem ordered_diagnostic_exact (ops : List Op) (world : World) (cache : Bytes)
    (sound : Sound cache world) :
    (run ops world cache).issue = firstIssue ops world

theorem successful_coverage (ops : List Op) (world : World) (cache : Bytes)
    (accepted : (run ops world cache).issue = none) :
    (run ops world cache).observed = sources ops
#+end_src

These declarations are excerpts; the linked source contains the executable
recursive interpreters and proofs. In the same stable world, keeping operations
in the SAME order preserves the first error, including its request/message and
location. Successful execution discovers exactly the source operations on the
actual lowered trace. It does not enumerate every object field or unselected
module. The binary replay projection preserves both dependency branches.
Native cyclic/shared graphs still require correspondence to the actual
identity-deduplicated DFS; the tree lemma alone does not prove that refinement.
The model Request also retains a location, whereas the native source collector
stores input/message and raises with the source path. Mapping complete Scheme
exception payloads and field-locator positions to Request is still a premise,
not an assertion that the current collector stores that entire record.
This narrow Request uses present expected text, matching the two JSON documents;
full native projection must also account for expected absence and regular-file
checks. Their Scheme adapter semantics are not proved by this new model.

The collector projection uses the actual first-observed =(path, expected-text)=
policy, not path-only overriding:

#+begin_src lean
def enroll (seen : List Request) (request : Request) : List Request :=
  if input request ∈ seen.map input then seen else seen ++ [request]

theorem enroll_complete (seen : List Request) (request : Request)
    (key : String × String) :
    key ∈ (enroll seen request).map input ↔
      key ∈ seen.map input ∨ key = input request
#+end_src

=successful_coverage=, =both_branches_retained=, =enroll_complete= and
=enroll_retains_earlier= establish ordered coverage for this concrete projection.
The existing Core collector checks BEFORE enrollment, copies path/text, retains
different expected revisions, enrolls into all enclosing scopes, and performs
its final pass without traversing the candidate. This is the audited native
correspondence; no automatic extraction/refinement proof of that Scheme code
has been added.

Coverage is not the same as diagnostic order: native roots come from =hash-keys=,
and the collector uses first successful enrollment order. Equal input pairs may
have different messages. Preserve that actual order/first origin; do not sort
or replace it with a manually maintained field catalog.

* Why moving the two checks is still unqualified

The Lean computed counterexample uses changed =postgresql.json= and a retained
parent Pipeline token against the final child binding:

#+begin_example
Current schedule:
  check JSON -> "configuration source changed", postgresql.json
  [the stale Pipeline token is never reached]

Deferred JSON:
  check parent Pipeline token -> "stale slot dependency", pipeline
  [the final collector is never reached]
#+end_example

=moving_check_changes_diagnostic= proves those first results differ, even though
both schedules reject and the complete source requirements are retained.
=changing_first_origin_changes_diagnostic= separately shows that replacing a
JSON request with an acceptance-equivalent publication request can change the
message/location. =failing_prefix_preserved= proves that merely appending a
complete final collector cannot repair an earlier failure.

This is not a new native failure measurement. It is an executable Lean
counterexample and a matched QNT schedule, consistent with the audited native
check/replay order. The existing =defer_covered_check= theorem remains correct
for acceptance; it never proved identical first errors.

A valid future optimization could share byte observations while KEEPING the
ordered early JSON checks, but only through a closed, stable, effect-free suffix.
It must still execute token checks and compare every contribution requirement.
Removing/moving the early checks additionally needs a proof that intervening
operations cannot report a competing error, or a semantics-preserving ordered
failure protocol. Neither is currently established. No public purity marker
or manual evidence declaration is proposed to bypass that obligation.

* New finite controls and retained guarantees

=ReplayBoundary.qnt= executes source checks, structural token checks, an optional
cold metadata hook write, an optional source-observer write, and final source
certification. Writes are actual state transitions, not trusted purity labels.
The positive protocol starts the final source observation afresh.
The finite operations represent selected writes and failure codes, not every
exception or possible mutation of an arbitrary Scheme procedure.

| Instance | Property / intended result |
|----------+----------------------------|
| =ReplayBoundary= | Fresh final sources, complete selected coverage, ordered diagnostics on effect-free traces and unselected-branch laziness |
| =move= | First-error mismatch when JSON is stale AND parent token is stale |
| =reuse= | A metadata hook/source observer changes JSON; retaining earlier bytes can falsely accept |
| =omit= | An otherwise accepted result omits the late source |
| =effects= | Counterexample to assuming the whole adapter has no effects |
| =acceptance= | Witness that a valid configuration reaches acceptance |

The conditional diagnostic invariant uses the trace's actual write count; this
is a finite-model observation, not a producer's purity assertion. Source 2
remains unselected. The abstract token compares projected receiver/revision
coordinates; the Lean binding comparison includes instance/record/value too.
All previous RootChild and ReturnWindows controls remain in the catalog, so
both independent port requirements, child obligations, parent isolation and
source-change rejection remain independent gates.

The 356 native reads remain unchanged. Proof qualification and local artifact
results follow; no Scheme or Loader implementation is part of this follow-up.

** Updated decision

Keep all current checks and the current first-error schedule. Before proposing
any Scheme optimization, establish a producer-derived closed replay projection,
not a hand-maintained purity flag; prove its coverage of the selected native
DFS, including preparation/absence/file-kind observations; and prove ordered
exception/source-location equivalence. Sound same-order byte reuse is proved
for the closed projection. Deleting/reordering the two JSON checks is NOT yet
justified for the current native adapter. Both port requirements and final
receiver checks remain mandatory regardless of byte reuse.

* Matched domain configurations

** NixOS: analysis module using real options/submodule APIs

This is an UNEXECUTED analysis module, not official Gitea source. Each independently
maintained contributor owns a distinct requirement key; changing a scalar
definition's priority does not remove the other key's assertion.

#+begin_src nix
{ lib, config, ... }:
let
  inherit (lib) mkOption types;
  port = types.ints.between 1 65535;
  cfg = config.application;
in {
  options.application = {
    postgresql = mkOption {
      default = {};
      type = types.submodule {
        options.port = mkOption { type = port; default = 5432; };
      };
    };
    gitea = mkOption {
      default = {};
      type = types.submodule {
        options.databasePort = mkOption {
          type = port;
          default = cfg.postgresql.port;
        };
      };
    };
    requirements = mkOption { type = types.attrsOf (types.listOf port); };
  };
  config = {
    application.requirements.database = [ 5432 5433 ];
    application.requirements.client = [ 5432 5433 ];
    assertions = [{
      assertion = cfg.gitea.databasePort == cfg.postgresql.port;
      message = "application.gitea.databasePort must match final PostgreSQL port";
    }] ++ lib.mapAttrsToList (owner: ports: {
      assertion = builtins.elem cfg.postgresql.port ports;
      message = "application.postgresql.port violates requirement ${owner}";
    }) cfg.requirements;
  };
}
#+end_src

The user can set application.postgresql.port = 5433. The client default follows;
explicit application.gitea.databasePort = 5432 causes the assertion to fail when
the NixOS assertion consumer evaluates it. Application module authors retain
ownership of these relational assertions. A pure preview can project cfg's final
values without caching an old cfg outside the evaluation. A serialized detached
preview needs its own input applicability check; it is not an engine execution
plan merely because its values are known.

** Pulumi: analysis component preparation over the same known values

This UNEXECUTED component-library function intentionally uses known configuration
ports; resource-derived unknown Outputs require the existing Output protocol.
Requirements are supplied by the library's service composition, not by a user
copying provenance metadata. A complete production component also defines real
resources and dependency/lifecycle behavior, absent from all domain snippets here.

#+begin_src typescript
type Requirements = Record<string, readonly number[]>;
type Input = { postgresql: { port?: number }; gitea: { databasePort?: number } };

function checkedPort(value: number): number {
  if (!Number.isInteger(value) || value < 1 || value > 65535)
    throw new Error("port must be an integer in 1..65535");
  return value;
}
function prepare(input: Input, requirements: Requirements) {
  const databasePort = input.postgresql.port;
  const explicitClient = input.gitea.databasePort;
  const port = checkedPort(databasePort === undefined ? 5432 : databasePort);
  const client = checkedPort(explicitClient === undefined ? port : explicitClient);
  if (client !== port)
    throw new Error("config.gitea.databasePort: final port mismatch");
  for (const [owner, ports] of Object.entries(requirements)) {
    ports.forEach(checkedPort);
    if (!ports.includes(port))
      throw new Error(`config.postgresql.port: requirement ${owner} refuses ${port}`);
  }
  const config = { postgresql: { port }, gitea: { databasePort: client } };
  return {
    config,
    plan: { configuration: config, postgresql: { port }, gitea: { databasePort: client } }
  };
}
const requirements = { database: [5432, 5433], client: [5432, 5433] };
const application = prepare({ postgresql: { port: 5433 }, gitea: {} }, requirements);
#+end_src

An explicit databasePort of 5432 refuses. Only undefined activates the default;
an untyped null port reaches checkedPort and refuses rather than becoming absent.
Untyped external JSON still needs full object-shape validation, just as the Scheme
input needs its Contract. The full guard in the Pulumi
research article remains a separate analysis adapter for source/route/plan checks.

** POO: the same domain and the framework-owned envelope

The ordinary scalar change is the existing object-prefix refinement syntax;
the leaf is an assignment, not a transformation of the old number:

#+begin_src scheme
(.def (Release @ BaseScenario)
  config.postgresql.settings: =>.+ {port: 5433})

;; Maintainer declaration, NOT an ordinary user-maintained Requirements list.
contributions:
(.o postgresql-port:
    (.o target-owner: 'applications/gitea-postgresql
        target-admission: 'Application
        export-path: '(requirements postgresql))
    gitea-port:
    (.o target-owner: 'applications/gitea-postgresql
        target-admission: 'Application
        export-path: '(requirements gitea)))
#+end_src

The contribution fragment is real Scenario interface structure. Current service
defaults allow only 5432; the successful 5433 control intentionally supplies both
5432 and 5433 in both policies. The constructor supplies an absent client port
from the effective PostgreSQL value. Domain equality, policy conjunction and
plan association remain maintained checks. Shape declarations can use the native
ObjectContract proposal in 32.03; it has not replaced the production predicates.

The defensible improvement target is a reusable publication library that retains
selected independent requirements and source association before validating a
final application value. POO and typed functional composition can make that
library extensible, but do not eliminate its implementation or domain policy.
Our previous hand-written shape predicates are unnecessarily verbose; native
ObjectContract reduces that burden. Whether total maintainer cost beats a good
NixOS/Pulumi library is still unmeasured. Count public declarations, domain code,
framework code and diagnostic quality separately, under equivalent scope.

For the next complex case, add multiple databases/clients with typed endpoint
identities and cross-service dependencies without changing these evidence rules.
Do not claim a three-service normalization probe already validates thousand-module
scale, asynchronous external values, concurrent mutation or deployment success.

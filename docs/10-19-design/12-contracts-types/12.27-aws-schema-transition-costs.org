* Question and executed workload

Why does the init-owned AWS integration exceed its unchanged 60-second Ops
deadline when both provider packages already exist in the Nix store?

The subject is [[file:../../../scenarios/aws/tests/integration/context-publication-test.ss][the maintained AWS integration]], selected through root
=init.Scenarios=. It retains real AWS 5.99.0 and 5.100.0 packages, public value
Contracts, contextual child evidence, publication and failure retention. The
[[file:../../../scenarios/aws/tests/integration/fixtures.ss][private fixture]] supplies version-switching Nix inputs and the ordinary
publication-reader customization hook. It is not a second Loader or runner.

The phase callbacks divide each version into source-context creation, selected
build Graph preparation, package realization and realized-scope association.
Existing Nix completion observers measure actual external commands. Existing
source observers count reads, requests and actual publication-guard runs by
origin. Publication preparation and publication execution are measured separately.
The latter includes value admission, Context checks and evidence binding; its
whole duration must not be labelled pure Schema-validation CPU time.

* Observations before the final eligibility reduction

The first instrumented run expired before the second version. Initial Graph
preparation read source files 9,855 times. Initial publication association read
them 5,813 times, including 32 repeated reads of several SDK sources. This is
real source work in addition to Nix work, not evidence that Nix rebuilt providers.

A later instrumented run reached the second version and child publication but
still exceeded the Ops deadline. Its second Graph preparation took about 4.0
seconds and read sources 9,531 times; package preparation/realization took about
6.0 seconds; publication association took about 1.9 seconds. Child publication
completed at about 52.8 seconds from the fixture body start, before the final
negative controls finished. Ops also accounts for the child's import time before
that body timestamp. Body completion markers alone cannot qualify its deadline.

Nix durations varied materially between runs. Concurrent source compilation and
other focused tests were observed on the host. Keep deterministic work counts
separate from wall-clock observations; these runs do not establish a general
startup or end-to-end speedup.

* Changes with bounded reuse

1. Contribution-index preparation combines adjacent selection-source and
   selected-Graph source guards in the existing synchronous read window. It ends
   that window before route indexing can demand author declarations. The measured
   publication association drops from 5,813 to 5,637 source reads in this control.
2. Nix's prepared publication checks whether artifact realization is already
   cached. Cold realization keeps its source pre/post checks. Warm currentness
   retains a fresh Nix identity query and its source pre/post checks, omitting
   only the redundant guard around a cached artifact read.
3. Linking and source preparation use the private publication lookup immediately
   after eligibility admission. Only private hash operations intervene; the
   lookup no longer repeats that same eligibility guard. Publication reading,
   Contract execution and scope factories retain their post-effect checks.
   Dynamic eligibility callbacks receive an explicit post-policy source check
   before publication initialization.
4. Initial expression construction first performs a readonly Nix evaluation and
   asks =nix-store --check-validity= about that exact drvPath. A valid store entry
   avoids writable registration. A miss uses the original registration path;
   when both evaluations return paths, disagreement refuses construction. A
   failed optional lookup is not admission evidence. Currentness queries retain
   strict failure and never fall back to registration. Flake evaluation keeps
   its existing implementation.

These are local changes to existing owners, not a generation-wide success cache.
The measured source-read controls after the eligibility change are:

| Interval | Before | After |
|----------+--------+-------|
| First selected build Graph | 9,855 | 8,799 |
| Second selected build Graph | 9,531 | 8,475 |
| Publication association | 5,813 | 4,909 |

These counts cover the observed intervals, not all filesystem operations. They
establish less duplicate traversal; they do not establish an end-to-end latency
improvement under the observed CPU contention.

The selected Graph, actual publication objects and native receiver caches remain
authoritative. Replacing external version input still creates a fresh selection;
declaration expansion and initialization results are not cached across that effect.

An attempted blanket addition of nested caches to prepared-source guards did
not reduce the 9,855 initial reads. It was removed rather than presented as an
optimization. Existing callers already provide those pure observation windows.

* Checks which remain necessary

Readonly Nix queries still re-evaluate the expression and its arguments. A
completed provider build does not prove that its current selection is unchanged.
[[file:../../../t/nix-derivation-query-test.ss][The native transitive-input control]] changes an undeclared imported Nix file
and adds a previously absent file; source observations alone cannot replace that
query. No process result is reused across arbitrary validators or Context policy.

The store lookup is not a new evaluator cache: Nix re-evaluates transitive inputs
before checking store validity. A local pathname existence test would not suffice.
The configured store executable is reused for both validity and realization;
users supply no new field. Process metrics distinguish readonly evaluations,
store-validity checks, writable registration and realization. A cold construction
may add one registration evaluation; it is separately counted and bounded, never
hidden inside the warm query budget.

Likewise, every failed publication must retain the previous object. Source or
Schema changes, a copied same-name descriptor, stale evidence, invalid fields
and a modified responsibility map remain refusals. None of these assertions is
removed or replaced by a timing assertion.

* Focused controls

- [[file:../../../t/module-configuration-source-test.ss][Configuration-source controls]] retain initialization-time source mutation
  refusal and independent currentness checks.
- [[file:../../../t/module-nix-publication-test.ss][Nix publication controls]] exercise the real prepared-publication methods.
  Inert command probes check cold/warm source-guard counts, one realization,
  a new identity query on each check and post-query mutation refusal. Those
  probes are not evidence of Nix package performance.
- [[file:../../../t/module-selected-graph-test.ss][Selected-Graph controls]] retain dependency/Feature admission and add refusal
  when dynamic eligibility changes source state before publication reading.
- [[file:../../../t/nix-derivation-query-test.ss][Native Nix controls]] check actual cold registration, warm store validity without
  writable registration, undeclared transitive/negative-input changes, query-mode
  failure and a transitive change between lookup and registration. No provider
  acquisition is needed for this narrow derivation control.

The real integration verdict is recorded after the final focused run. The
60-second Ops limit, 120-second outer entry and one-GiB child heap fence remain
unchanged. No full repository build, runtime Loader or upstream patch is involved.

* Qualification record

The configuration-source, selected-Graph, Nix phase-publication and actual Nix
derivation controls passed through =just test-file= with MODULE-OK, HARNESS-OK,
final OK and natural exit zero. The native derivation control also checks that
a readonly guard does not force an unused store/realization capability.

The later full AWS attempt terminated with status 137 during source Graph
preparation, before executing the new Nix store-reuse path. Both its child and
outer entry failed; this is not evidence of a completed 60-second integration.
Separate host samples showed 0% idle CPU, 55--64 running processes and heavy
compression, with concurrent compiler activity. Available/reclaimable-memory
figures alone did not characterize that contention. Do not label signal 9 as a
proven heap overflow, successful timeout correction or Nix failure.

The original AWS Schema-update, stale-evidence, child-Context and previous-value
assertions remain unchanged. The final init-owned endpoint still needs a clean
fixed-budget completion after resource contention subsides. Standalone Nix tests
qualify the changed cache protocol; they do not replace that endpoint gate.

A subsequent endpoint run reached the real warm-store path: readonly derivation
evaluation, native store-validity checking and provider realization completed,
without writable registration in that interval. It then refused with
=compiler tool source changed; use a fresh reader= for =gerbil.pkg=, which was
modified concurrently. This run exited nonzero with ERROR CASE/ERROR HARNESS;
MODULE-OK/HARNESS-OK text in the same transcript does not make it a pass. It
qualifies neither the complete Schema transition nor a clean performance run.
An updated dependency is allowed: create a fresh reader and Graph against the
new locked revision. Refusal concerns reuse of the old observations, not the
legitimacy of upgrading POO. Bypassing that refusal would invalidate the experiment.

The next run used the current lock,
=gerbil-poo@ece6f609357ea918038090559ac051a8d9f3e52f=, with isolated compiled
dependency artifacts checked against their source manifest and Core read from
source. It retained the original limits. Its parent endpoint took approximately
77 seconds before starting the integration subprocess. Inside that subprocess,
the first Graph completed at about 17.0 seconds, packages at 26.3 seconds and
parent publication at 35.8 seconds. Same-name descriptor rejection completed;
Context checks followed, then Ops refused with status 124 before the second
Schema selection. The outer entry also reached its 120-second limit. This is
still an incomplete endpoint qualification, not a dependency-update refusal or
evidence that provider acquisition rebuilt a cached package.

The real interval again used readonly evaluation and native store validity,
with no writable registration. First-Graph source reads were 8,717 under this
revision; that source set differs from the earlier 26b4b58 control, so these
numbers must not be combined into an additional optimization claim. The current
revision's module-window, selected-Graph and real Nix derivation controls
completed serially through =just test-file= with MODULE-OK, HARNESS-OK, final OK
and natural exit zero, without ERROR CASE/CHECK/HARNESS or heap/stack overflow
markers. The Nix controls retain transitive-input change rejection and the
lookup/registration race refusal. These narrow successes do not close the AWS
endpoint gate; its failed run is retained locally without committing logs.

* Startup attribution and duplicate source expansion

The opt-in [[file:../../../t/qualification/aws-startup-observation.ss][startup probe]] wraps the original SDK module-import,
module-eval, expression-compile and expression-eval parameters. It restores them
before executing the test. It does not replace expansion, module initialization
or the native test lifecycle. Rows contain call count, inclusive seconds and
self seconds after subtracting nested observed callbacks. Repeated import calls
are not automatically repeated expansions; expression compilation is not a
count of macro transformations.

One observed run separated the previously aggregated startup interval:

| Boundary | Observed seconds |
|----------+------------------|
| Instrumented imports, including init syntax | 26.46 |
| First namespace access after test entry | 6.89 |
| Selected test-spec discovery | 25.13 |
| Remaining test/execution association | 0.89 |

The source import of =module-system/source/link.ss= accounted for 15.78 seconds
inclusive; =module-system/authoring/admission.ss= accounted for 10.10 seconds
inclusive. These overlap and must not be added. The largest import self-time
rows included =poo-clos/objects.ss= (2.28 seconds), =poo-clos/classes.ss=
(1.57), =module-system/source/selection.ss= (1.46), =types.ss= (1.14) and
=module-system/authoring/admission.ss= (1.12). The probe also observed eleven
expression-compile callbacks in =core/poo-clos/syntax= at phase one, totalling
about 0.25 seconds. This is not evidence that all remaining import time is
macro CPU time. A short process-stack sample separately showed expander,
allocation, MOP and filesystem activity, rather than a wait on Nix alone.

Test-spec discovery also imported additional role dependencies. Reading an
interface currently entails native expansion of its adjacent role imports;
not invoking =core.link= does not by itself make this declaration work cheap.
The root's selected Graph includes all explicitly selected roots, whereas the
test projection filters execution owners. Changing that contract to silently
drop selected roots is not an acceptable performance repair.

The reader had a concrete redundant path for symbolic library imports: first
ask the SDK to expand the canonical source, then replace the returned context
with an admitted private wrapper. Source-path imports already took the confined
route first. The repair uses the SDK's public path resolver before expansion
when the source is already covered by the existing owner/tool/kernel policy.
It sends that source directly through the same confined reader. Compiled
libraries retain their original SDK import closure. No result of a macro,
initializer, validator or package effect is reused as currentness evidence.

[[file:../../../t/module-publication-test.ss][The publication control]] uses a real phase-one initializer that refuses a
second expansion. The symbolic import must use its already admitted private
role once; an independent canonical SDK import is the negative control. Existing
fresh-session, source-mutation, confinement and deferred-export controls remain
in the same native suite. The initial test setup incorrectly treated SDK
=load-path= as a parameter; it was corrected to the SDK's =add-load-path!= and
=set-load-path!= functions with unconditional cleanup, without weakening the
initializer assertion.

This repair addresses one measured mechanism, not the complete laziness gap.
Cold infrastructure imports, eager role expansion during declaration discovery
and repeated source guards still require separate attribution. The instrumented
pre-repair endpoint remained unsuccessful (outer status 124, child status 137
during first-Graph preparation); a sample or partial phase log is not a passing
AWS Schema transition.

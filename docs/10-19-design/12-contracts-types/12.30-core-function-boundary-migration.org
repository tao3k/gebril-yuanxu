#+title: Core Function Types at Module and User Boundaries
#+date: [2026-10-23]

* Decision for discussion

Every function supplied by a module, user, extension or runtime adapter must
cross a native gerbil-poo Function Type boundary before Core invokes it.
Public callable Slots and exported operations declare their real signatures.
Authors continue to write ordinary functions and POO objects. The declaration
must make the code easier to read; a second callable framework is unnecessary.

This is a migration proposal and source inventory, not an implementation receipt.
Earlier partial Ops/JSON Schema work does not establish coverage of Core.
No implementation, dependency pin or proof is changed by this proposal.

=Function= takes result Types first, then argument Types. =Fun= exposes the
same direction with =<-= and is preferred for short readable signatures.
=element?= / =procedure?= recognition cannot check future calls. Consumers must
invoke the value returned by =validate=, including nested or returned callbacks.
ObjectContract diagnostic constraints alone do not install Function wrappers.

* What module authors and users should see

** A module operation

The following uses existing upstream syntax. Domain Types stand for maintained
domain definitions, not labels or new generic wrapper classes.

#+begin_src scheme
(def Render (Fun RenderedConfiguration <- Configuration))
(def ServiceScope
  (.cc ObjectContract. responsibilities:
    (.o render: Render)))

;; The author supplies an ordinary function.
(def service (.o render: render-configuration))
;; Publication/linking carries this result to users and dependants.
(def checked-service (validate ServiceScope service))
(.call checked-service render configuration)
#+end_src

Core publication uses its existing Scope admission and contextual evidence
around this native value normalization. It must expose =checked-service= through
both public exports and dependency bindings. Keeping the raw Scope in one path
would bypass the abstraction.

** A user-supplied operation

Funflow now submits one native signature and one ordinary body:

#+begin_src scheme
(flow-arr 'render
  (Fun RenderedConfiguration <- Configuration)
  render-configuration)
#+end_src

The former =name proc input-contract output-contract= form has been removed.
The native signature checks the submitted operation; symbols are not Types.
The task owns that signature and the checked executor. Input/output views are
derived from it. There is no additional Core Function class or signature DSL.

For =flow-map=, =flow-bind= and =conditional-flow=, the same operation signatures
are explicit at submission; composition checks native Types rather than labels.
A binder declares that it returns a typed Flow with the required input/output
meaning, rather than merely any object recognized as a Flow.

** A returned runtime callback

#+begin_src scheme
(def ProgressLine (Fun Any <- String))
(def ProgressFactory (Fun ProgressLine <-))
#+end_src

=Any= here describes the one ignored observer result. It does not erase the
String argument, result count or returned-callable requirement. Runtime adapters
and decoders need actual request/result Types, not =Any -> Any= placeholders.
Checking a descriptor does not invoke its callback or authorize its effects.

* Inventory conventions

The tables cover built-in module Scopes, exported operation objects, extension
protocols and runtime callback submission points in the current Core source.
Rows group aliases and constructors sharing the same actual callback protocol;
each named Slot in a group is part of the migration. Source links identify the
owner, not a second proposed implementation location.

Notation =A -> B= below means a proposed native =Fun B <- A= signature;
=() -> B= is a zero-argument Function; =?A= allows false; brackets denote lists;
=A => B= in prose is not a new language operator. Domain names in the tables
are proposed maintained Type names unless an existing descriptor is identified.
Optional arguments and keywords must follow the actual source lambda list.
They must not be flattened into a single catch-all argument list.

Result cardinality matters. Transparent call-with helpers preserve the actual
zero/one/multiple-value contract of the submitted action. Their Types must be
specialized to that contract; inventing a single Any result is incorrect.
Predicate APIs currently accepting truthy non-booleans require an explicit
semantic decision before imposing Bool. Typed membership predicates should
return Bool; legacy truthiness must not be silently reinterpreted.

* Mechanisms to delete or consolidate

| Current mechanism | Replacement and deletion boundary |
|-------------------+-----------------------------------|
| Scope checks that only enumerate callable names and call procedure? | Native Record/ObjectContract Function fields; retain independent domain/identity obligations |
| Function argument/result checks handwritten at individual consumers | The same native Function descriptor at the submission/publication boundary; remove duplicate arity/value checking after matching negative controls pass |
| Funflow symbolic input-contract/output-contract tuples such as pair/try/abs-dir/cas-item | Native Types and constructors; a task/flow owns one native signature, metadata views derive from it |
| Runner invoking raw Task.executor after only metadata admission | Runner receives the checked executor; delete the raw bypass |
| Constructor validates then stores original callback | Store/return the actual validate result, including nested and returned callbacks |
| Separate Scope copies for public exports and dependency requirements | Both paths carry their applicable actual checked Scope; retain descriptor/context evidence |
| Duplicate callback signatures in Ops, TestingScript and progress readers | One exported native progress descriptor composed into each owner contract |
| Domain-case type-id / schema-id labels treated as executable validators | Native Type/Function descriptor owns validation; identifiers remain diagnostic/provenance data |
| Core callable wrapper classes, invocation registries or local signature solver | Do not introduce them; use upstream Function/Fun and native specialization/declarations |
| CLOS field predicate walkers used as a second type-validation engine | Native structural Types and normalization; retain CLOS semantic relations only |
| Transformer Any-as-compatible policy described as subtyping | Remove the claim; use native supported relation evidence or explicit domain compatibility, with refusal for unsupported substitution |
| Empty contextual receipt producers around ordinary value/function checks | Native Type validation; keep only meaningful Core source/context/publication evidence |

Some listed mechanisms are already partially changed in the dirty worktree.
They require coherent consumer migration and fresh validation; an isolated
passing test does not qualify the whole migration.

* Ownership and adoption rules

1. Domain =types.ss= owns reusable value and callable descriptors. =objects.ss=
   supplies normal function bodies and prototypes. =interface.ss= publishes the
   checked Scope through Core's existing module publication boundary.
2. A direct public function export is checked at its exported binding. Internal
   recursion and private pure helpers remain named functions.
3. User-supplied functions are normalized when accepted into a maintained
   Task/adapter/policy object, before the first possible invocation. POO-derived
   objects must be checked as the actual derived value; a checked parent cannot
   certify a new override.
4. Share immutable descriptors. Do not cache current admission, suppress source
   guards, execute factories during declaration or add wrappers on every getter.
5. Parameterized Flow signatures use upstream native specialization. Infer only
   where a real domain needs inference; explicit Types are the readable default.
   No Core-specific solver or type-expression parser is added.
6. A Type error is not converted into success, false or an empty receipt. Existing
   domain failure translation remains explicit and preserves its original cause.
7. Type validation does not establish purity, rollback, scheduling correctness,
   historical authenticity or permission to execute an effect. Existing guards
   and explicit runtime handoff keep those responsibilities.

* What to test and what to prove

Runtime tests must establish that the ordinary user/module path executes the
checked function: invalid arguments fail before the body, invalid results fail
before downstream consumers, and nested callbacks remain checked after being
returned, inherited, cached or passed through dependency Scopes. Cover actual
optional/keyword/default/rest forms and zero/multiple results. Declaration and
preview must remain lazy. Fresh source/context checks remain around open effects.

For Funflow, test a complete submitted function -> Task -> composed Flow ->
runner/adapter path, including negative binder results, cache hits, substituted
POO operations and runtime response mismatches. For Build/Testing, keep issuance,
source currentness, heap fences, harness markers and watchdog budgets unchanged.

composition APIs for these actual boundaries. Prove propagation of checked
values through Scope/linking, Task/Flow composition and returned callbacks.

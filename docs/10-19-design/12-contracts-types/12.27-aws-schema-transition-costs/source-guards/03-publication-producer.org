* Publication-owned analysis and request callback attribution

The next audit identifies a missing integration, rather than a missing cache.
The AWS root now uses a public value Contract and an ordinary YuanxuContract.
The existing one-shot responsibility analysis was entered by the source
Contract wrapper, but publication did not enter it for this ordinary root.
Consequently registered children repeated the complete Context source check.

Publication now uses the existing producer boundary:

#+begin_src scheme
(call-with-contract-analysis-root descriptor value context-value
  (cut yuanxu-contract-admit descriptor value context-value))
#+end_src

The token matches the exact Contract, candidate and Context. The producer
consumes it before value checking, classification or open obligations. Only
explicit responsibility edges receive the corresponding child token. This
does not memoize evidence, source bytes, validation results or callback results.
The existing contribution Context checks actual registered Contract identity
and its observed revisions. A registered child with the original platform
handler needs no second whole-Graph traversal in that handler; root checks
still surround real platform callbacks. Inherited or replaced Context handlers
retain full checks. A nested independent admission or an override's second
inherited producer invocation has no token and retains its full check too.

The focused publication test uses the real source Graph, Context base,
producer, evidence binding and publisher, with explicit test policy callbacks.
It verifies one analytic child, a full root and an independent admission;
calling the child's inherited producer twice makes the second call full.
Rejecting the child prevents publication and preserves the previous object.
Running the new assertion against the prior publication producer fails with
zero analytic children instead of one. The repaired producer passes. The
existing contract-analysis mutation and independent-admission controls pass
as well. These policy probes are Core tests, not module-author requirements.

** What the request callback actually does

The build Graph observes each existing external request's getter and
=admit-current= invocation in a =dynamic-wind= bracket named
=(build-request position)=. Position refers to the existing request sequence;
it does not create another request tree or read identity slots during
admission. The observer closes the bracket on failure. It grants no authority
and changes no read-window or validity boundary.

The same observed AWS Case records this callback partition:

| Reads inside one request bracket | Brackets | Total reads |
|----------------------------------+----------+-------------|
| 0 | 64 | 0 |
| 8 | 132 | 1056 |
| 176 | 7 | 1232 |
| Total | 203 | 2288 |

The seven 176-read brackets each include a 167-read public configuration
guard, plus nine other reads. These nested reads are inclusive here, and are
not added again to the exclusive Graph table below. No native-import, Nix or
package stage occurs inside these measured request brackets. That observation
does not make an extensible request getter or callback universally pure.
Lazy request preparation still occurs before callbacks when external packages
are first demanded; that boundary remains outside any fused pure window.

The remaining before-guard hotspot is 139 brackets: 119 read the 167-file
Graph closure and 20 perform no physical read because the existing window
already covers their input. Four complete traversals were removed by restoring
the responsibility producer boundary, not by dropping all request guards.
The seven after-guards still read 1169 files in total. Configuration, package,
root Context and publication-return checks remain independent across open
callbacks. The remaining 19873 before-guard reads are an open optimization
target, not a claim that every one is necessary.

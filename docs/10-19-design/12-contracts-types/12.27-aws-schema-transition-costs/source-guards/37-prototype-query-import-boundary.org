* Remove a construction dependency from a read-only operation

The [[file:36-carrier-candidate-admission.org][carrier admission change]] removes a repeated check. The next actual import
edge is independent: prototype authoring dispatch imported =poo-clos/classes.ss=
for only two read-only projections. That import also initialized logical Class
construction/registration, although prototype dispatch does not need it.

The two functions now live in the existing =poo-clos/objects.ss= value layer:

#+begin_src scheme
(def (poo-clos-class-precedence-list class-value)
  (unless (element? ClosClass class-value) (clos-fail 'invalid-class))
  (.ref class-value 'class-precedence-list))

(def (poo-clos-class-precedence-position class-value target-value)
  (unless (and (element? ClosClass class-value)
               (element? ClosClass target-value))
    (clos-fail 'invalid-class))
  (hash-get (.ref class-value 'class-precedence-index) target-value))
#+end_src

These are the same Type checks and class-owned C4 list/index. There is no new
linearizer, approval cache or registry. =classes.ss= no longer defines or
re-exports these functions. =dispatch.ss= gets them from its existing objects
import and no longer imports Class construction. The existing full
=interface.ss= still exposes the query and explicitly loads Class lifecycle
support when that full interface is requested. The product C4 scenario's direct
query import moves to =:yuanxu/poo-clos/objects=; there is no forwarding layer.

This implements the distinction between a native POO projection and a heavier
Class lifecycle style. It does not make Class data untyped or bypass multiple
dispatch. A caller using Class construction still imports its actual owner.

* Diagnose the triggering deadline, not the interrupted dynamic scope

During the deferred field-row experiment described in topic 36, the child
observation file stayed empty before its worker harness. The Case stopped at
about 70 seconds but reported =duration-exceeded 600000 70302=. This was not a
completed 600-second capacity run, nor proof that macro lowering caused the
startup delay. The unqualified field macro was removed.

The watchdog checked its own progress state, then its exception closure
re-read =current-execution-progress= in the interrupted owner. That owner
could be inside a different nested Ops extent. An outer idle refusal could
therefore be labeled with an unrelated total budget.

=observability/memory.ss= now captures status, limit and elapsed in the
watchdog thread before interrupting. The stop condition, budgets and cleanup
are unchanged. The existing progress suite adds an outer 100ms idle / inner
still-current 1000ms negative case and checks the public duration receipt.
The final suite passes all nine cases, including genuine progress, noisy-stall
refusal and descendant cleanup. A preceding attempt failed in the existing
0.6-second Ops case inside =open-process=, before child output; that failed
run is retained and no bound or assertion was relaxed.

* Thousand-declaration result and remaining ownership work

The unchanged thousand-module gate runs actual declarations through the init
test object's =.run=, with observation enabled and the original 2 GiB heap,
60-second idle and 600-second total policy. It completes 614 publications.
The last completed publication reports 550158ms elapsed, 159963ms CPU and
230554 physical reads; the next publication stops during =types.ss= import.
The parent reports =Ops execution terminated= with signal 15, followed by
the outer guard's kill and exit 137. No heap-overflow marker is present.
Exit 137 is not, by itself, evidence of an out-of-memory kill.

The fixture directory is absent after termination and a scoped process query
finds no surviving worker. These observations support cleanup on this run;
the child's Graph-ready, source-change refusal and collected live-memory
assertions were NOT reached. There is no thousand-module memory receipt or
capacity acceptance, and the failed run is not retried unchanged.

Physical reads increase by 375 per completed publication in the final observed
stretch. That is not a renewed historical-prefix scan, but it remains costly.
At 576 publications, the existing phase observations report 16.60s import CPU,
20.26s metadata-replay CPU and 33.68s source-guard CPU. The overlapping reader
boundaries report 66.64s preparation CPU and 36.38s interface CPU; they must
not be summed as disjoint costs. At 614 publications the reader retains 315
SDK tools, 1842 private contexts/source objects and 2456 source guards. These
are ownership counts, not exclusive retained bytes or a proof of a leak.

The next candidate must therefore address repeated support replay and the
three private role contexts per publication along the real preparation and
interface boundaries. It must establish which context/binding references can
escape to lazy formulas before releasing or projecting them. The failed
field-row macro experiment is not used to explain this result. Neither the
finite Quint carrier schedule nor the Lean single-check law proves SDK
context non-escape, native GC behavior or thousand-module capacity. Open
callbacks continue to retain complete guards; the remaining work cannot be
justified by dropping their support or clearing SDK state.

* Reusing Nix's source-to-hash cache below the Flake cache

The complete follow-up through the same init-owned =.run= first reproduces
four evaluator-root loads, 16 cached attribute queries and the 802-path
multiset relations above. It exits zero with seven module, two harness and
two final success markers; AWS completes at 158149 ms. Schema transitions,
old-evidence rejection, previous-value preservation and cleanup all pass.
This confirms the boundary, not a speedup.

That trace exposes a second native cache layer: each miss reports 285
uncacheable source paths under the immutable package-set tree. In the inspected
=2.34.4= source, the final-input/NAR shortcut in
[[https://github.com/NixOS/nix/blob/2.34.4/src/libfetchers/fetchers.cc][Input::getAccessorUnchecked]]
obtains a Store accessor before the path scheme's normal resolution. For this
path input, its scheme fingerprint is absent. The normal
[[https://github.com/NixOS/nix/blob/2.34.4/src/libfetchers/path.cc][PathInputScheme::getAccessor]]
instead assigns a NAR-based accessor fingerprint and registers the native
source-to-hash entry. Without that fingerprint,
[[https://github.com/NixOS/nix/blob/2.34.4/src/libfetchers/fetch-to-store.cc][fetchToStore2]]
cannot reuse its persistent source-hash cache and enters =addToStore= again.
This includes source files embedded by dependency derivations, beyond merely
reading =flake.nix=. A copying log alone still does not quantify bytes written
or RPC service time.

The existing public Source already supports explicit input resolution. The
AWS fixture retains its setup-resolved, canonical immutable package-set path
and supplies that SAME path through this capability:

#+begin_src scheme
;; Existing NixFlakeSource.; package-set is resolved from the locked Store.
inputs: (.o nixpkgs: (.get fixture package-set))
#+end_src

The generated selected demand remains the separate =selection= input. The
original Flake declaration still retains its package-set NAR pin. Native
locking, GC roots, validity checks, source guards and serialized input guards
remain enabled. This does not normalize metadata, construct a new cache or
skip a derivation query. It reuses the existing Nix fetcher cache below the
root Flake attribute-cache boundary.

The focused native control publishes a small immutable source, then compares
two cold output attributes with identical derivation identity. Direct final
input resolution reports an uncacheable source; explicit resolution of the
same Store path instead reports a source-cache hit. The control checks native
GC-root requests, unchanged lock bytes and a subsequent warm attribute-cache
hit. The first attempt correctly rejected a macOS temporary-directory symlink;
the control now uses the same path normalization as the Source implementation.
No upstream source or standard library is modified.

This is an explicit upstream package-publication binding in the qualification
fixture, using an existing Source capability. It is not a claim that every
arbitrary publication is automatically rewritten, nor that four distinct root
fingerprints can share one attribute-cache database. The full AWS Case must
qualify the binding's work-count effect and all publication safety assertions.
The prerequisite is the setup-verified immutable Store path corresponding to
the retained NAR pin. This must not be generalized to arbitrary mutable input
directories or used to discard a lock mismatch. If a future Nix revision fixes
the final-input path accessor, requalify whether this explicit binding remains
necessary; it is not a new permanent publication protocol.

Previously every miss had 285 uncacheable-source messages and 303 Store-add
requests. The first explicit-resolution miss still populates native hash
entries for many embedded files; later misses reuse them despite different
application fingerprints. GC-root and validity counts INCREASE because the
native cache-hit route protects and checks those Store paths before returning.
The improvement is therefore not removal of GC or currentness protection.
File-evaluation counts remain 329/330; no reduction in physical reads is
inferred from that counter alone.

Four miss queries total 16859 ms in this receipt, versus 109586 ms in the
immediately preceding direct-input receipt. The complete AWS phase finishes at
66430 ms versus 158149 ms. These are uncontrolled local observations with
diagnostic logging enabled, not a stable speedup ratio or a claim that every
query is below one second: query 6 still takes 10119 ms. Request/multiset
controls and the focused native A/B qualify the reuse mechanism. They do not
attribute the entire wall-time difference to one RPC or remove remaining
import, Graph and evaluator costs.

Different diagnostic volume and native cache state prohibit presenting this

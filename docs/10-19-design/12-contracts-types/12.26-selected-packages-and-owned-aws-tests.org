* Root init and Scenario mount ownership

The continued second-version timeout investigation and guarded reuse boundaries
are recorded in [[file:12.27-aws-schema-transition-costs.org][AWS Schema transition costs]]. Historical timings below remain
historical; the mounted-root integration has its own completion gate.

The intended architecture is one repository root =init.ss= selecting directory
windows through the Module System. The =scenarios/= directory is mounted under
the name =Scenarios= using =rename:=; it does not require an independent
=scenarios/init.ss= which repeats the Module dependency selection. Scenario
owners and their tests use that mounted namespace and the same selected Graph.
See the [[file:../13-module-loading/13.13-root-directory-windows.org][implemented root-window boundary]] for grammar and identity rules.
Renaming a mount changes its namespace route, not its publication identity.

The historical performance receipts below used a separate single-window
qualification root. That root has been removed: current atomic and integration
callers import root =init.Scenarios=. Window parsing, source ownership and the
selected Graph implement this mount; it is not merely a Scheme import rename.
Historical timings are not re-labelled as measurements of the new mounted root.

* Test ownership is not another Scenario model

AWS atomic controls belong to [[file:../../../scenarios/aws/tests/atomic-test.ss][scenarios/aws/tests/atomic-test.ss]]. Real package qualification belongs to
[[file:../../../t/Scenarios/aws/context-publication-test.ss][Core publication qualification]]. Its private
[[file:../../../t/Scenarios/aws/fixtures.ss][fixtures.ss]] prepares a temporary version input and an explicit upstream Nix
Source over the real module publications. It imports no other test suite,
bootstrap fixture, copied Module implementation or test runner.

The existing module test projection discovers the atomic file; helper files are
observed for currentness but are not harness inputs. The standard fixture macro
owns acquisition and cleanup. The selected test uses the existing std/test and
Ops execution boundary:

#+begin_src scheme
(import :clan/poo/object
        (only-in "./init.ss" init.Scenarios))
(.call (.get init.Scenarios aws tests) .run)
(.call (.get init.Scenarios aws tests qualification) .run)
#+end_src

Publication fault injection is Core mechanism qualification, not an AWS suite.
=t/aws-context-publication-test.ss= directly selects the existing init test
object's =qualification= projection. Discovery automatically binds the Core
qualification source to its selection guard and invokes the same =.run= / Ops
path. AWS authors maintain neither that file list nor boundary
callbacks. The ordinary AWS integration projection is empty after relocation.
See [[file:../13-module-loading/13.12-declarative-module-testing.org][automatic qualification discovery and table-driven controls]].

[[file:../../../t/aws-module-test.ss][The atomic caller]] checks cold/warm execution and independent scope/integration demand.
[[file:../../../t/aws-context-publication-test.ss][The integration caller]] retains its original real-package assertions via the explicit endpoint.
Neither maintains a second test-path list or creates an
Atomic/TestingScript object. Its business scope stays cold before and after the
run; the atomic test's separate fixture is the deliberately isolated subject.
The selection Graph that chooses tests is not a replacement for that subject's
per-version package Graph.

Test discovery and execution are not package-selection responsibilities. AWS
Selection must not import test suites, fixture macros, test probes or harness
state. The dependency direction is from the module-owned test to the production
Graph, SelectedPackages and publication APIs. init owns test discovery and the
existing test object; module authors declare cases with yuanxu-test-fixture.
No second test registry, execution object or success-marker protocol is needed.
Version-switching inputs remain private test data, not exported AWS configuration.

Module ownership does not make every case an atomic unit test. The real provider
upgrade is an integration case selected through the same module test endpoint.
Small contract and publication cases retain their own focused suites; importing
those suites into AWS Selection would obscure both dependency and failure scope.

* Build demand and actual package binding

The maintained AWS Config now reuses its actual Profile:

#+begin_src scheme
(.def Config resource: (.o aws_instance: (.o web: WebProfile)))
#+end_src

The maintained AWS interface declares the existing provider capability:

#+begin_src scheme
requires:
(.o Tofu: (.o module-id: 'opentofu contract: OpenTofuScopeContract))
exports: (aws-scenario-scope Tofu config)
#+end_src

OpenTofu's existing configuration-build projects resource keys from this Config
to demand aws, without forcing Profile field values or loading the provider
catalog. The selected build Graph creates the consumer-qualified request. The
existing SelectedPackages operation realizes it; the existing .with-packages
operation binds its actual scope to the consumer's Tofu dependency:

#+begin_src scheme
(def packages
  (.call (.cc SelectedPackages.
           selection: selection directory: workspace) .run))
(def realized (.call selection .with-packages packages))
(def publication
  (.call AdmissionPublication. .for-export realized 'aws 'Scenario))
#+end_src

The AWS scope obtains provider from Tofu.modules.aws.provider, and obtains its
public input Type from that same provider. There is no provider-directory field,
directory reader or SchemaArtifact assembly in the AWS scope or user Profile.
The publication's maintained association still owns descriptor/Schema resolution.

Selecting names cannot choose a trusted package source implicitly. The upstream
OpenTofu Source is an explicit maintainer input. This fixture uses the existing
publication-reader customization hook to refine the actual OpenTofu Config and
Build module with the same Source. It does not define another publication reader
or import copied roles. Production source/default policy is not invented here.

* Guard responsibilities

SelectedPackages now exposes the sources-current callback already required by
the realized linker. It checks selected/source/generated-input identity without
re-entering package realization during linking. Its existing admit-current is the
full Nix derivation/publication guard. The realized selection's public
admit-current invokes that full guard as well as the source guard; internal link
traversal uses the narrow check. Both refer to the original selected build Graph.

Publication binds the full package guard from the realized selection and checks
it before and after admission. Contextual child checks retain source, Schema and
descriptor currentness without repeating external package effects at each child.
Failure at either publication guard must preserve the previous published value.
This separation is a production correctness boundary, not a test execution layer.

A changed version.nix causes an old generation to refuse. A fresh generation
reprojects the same Config and resolves a new package, Contract and Context.
The atomic test retains parent-cache/final-child assertions, child Context
refusal, same-name descriptor refusal, stale evidence refusal and exact previous
value retention. It also asserts the real AWS config.ss bytes never change.

The earlier direct-directory Schema-shadow control in
[[file:12.25-aws-contextual-publication-validation.org][12.25]] is historical evidence, not an automatically bound package route. This
test uses the real immutable package versions for update validation. It does not
mutate the Nix store or claim live AWS deployment validity.

* Source phase defects exposed by the real module test

The corrected path also requires these existing boundaries to agree:

- For the standard modules/ collection whose parent owns a regular gerbil.pkg,
  the declared package source root supplies kernel authority, even if init.ss
  lives in scenarios/. The manifest is observed. Arbitrary collection parents
  do not gain source authority; Module confinement checks remain.
- Public dependency source imports reuse the SDK only when the parsed non-Core
  identity resolves to that exact canonical source. A namespace label alone does
  not authorize an escaping file. Core tool reuse remains limited to exact
  SDK-observed bootstrap contexts.
- Publication and configuration role evaluation now share the same compiler-tool
  observation builder. Config can reuse its actual prelude/declaration context
  without wrapping the compiler tool again or requiring a caller-prebuilt Core.

These are build-time native expander paths, not a runtime Loader. Failed source
or authoring checks are repaired rather than disabled. In particular, the AWS
scope constructor avoids a real lexical self-reference between its Scenario
slot and the imported Scenario prototype.

* Verification boundary

** Failure-stage repair

The post-admission Context check previously ran inside the checked executor.
The public calling Contract correctly classified an exception there as source,
although the existing tests require a dependent-meaning refusal at logic phase.
The redundant executor check is removed. The bound public Contract still checks
Context currentness after the result, preserving its original logical phase and
the outer publication's source-phase cause. No assertion is relaxed.

** Bounded source work

The AWS timeout exposed repeated compiler projection and recursive source
comparisons. Package versions share one fixture-owned reader over unchanged
module source; each version still creates its own Graph, package, scope,
descriptor and Context. A source change refuses reader reuse.

SDK compiler-tool projections are retained by exact context identity in a weak
cache. Reuse validates the original path, source bytes and native package
metadata. This cache contains prepared source, never admission evidence.

Inside the existing synchronous, effect-free source observation boundary,
file kinds, bytes and repeated reader/link source checks are shared. Newly
registered reader guards change the observation key. The boundary ends before
expansion, input writes, external Nix effects or value admission; each subsequent
independent check starts fresh. Package derivation checks and publication checks
are not skipped. Replacement with a directory or symlink must still reject.

Ops now includes already-captured process output with a failing status rather
than discarding it. The original fixture/test macros and init-owned endpoint
remain the execution path; temporary profiling is not a public testing protocol.

Earlier init-owned AWS attempts returned exit 124 from the existing Ops test
endpoint. The outer harness reported ERROR CASE and ERROR HARNESS; its
MODULE-OK/HARNESS-OK markers did not establish success. Duration and memory
watchdog failures are retained as failed attempts, including one run with inner
OK markers but a nonzero process status. No timeout increase or separate runner
is used to mask these results.

One intermediate integration invocation completed with exit 0, but the final
diagnostic-free invocation again returned 124 while waiting for Nix derivation
re-evaluation. The integration gate remains failing and performance-unqualified.
The intermediate pass does not override that result. Merely avoiding one timeout
is not the required latency or repeatability evidence.

The earlier file called atomic-test actually performed two package generations,
Nix realization and full publication checks. It has moved intact to the explicit
integration projection. Default atomic controls now own the five existing small
Contract cases, using the native case macro instead of manual completion counts.
All field, nominal identity, cached-parent and stale projection assertions are
retained. No integration assertion is removed or relabeled as an atomic pass.

Two local cold/warm atomic observations through the existing Ops endpoint were
11.39/6.39 seconds and 18.02/7.65 seconds. Worker times were 5.80/6.11 and
8.15/7.39 seconds; the rest includes namespace discovery and source guards.
The latter run includes the standard case watchdogs. Scope and integration
execution remain cold; selecting integration metadata reuses the exact Graph.
These are uncontrolled local observations, not a speedup claim for equivalent
integration work. Cold source expansion and worker startup still need attention.

A Nix store output hit does not memoize repeated expression evaluation. The full
derivation guard currently re-evaluates potentially transitive inputs. Caching
that check across effects without a complete, immutable input closure would
weaken source integrity. That remains an integration design/performance gap;
atomic execution must not silently pay this cost or hide its failing gate.

** Same-Graph diagnosis: registration versus currentness

The maintained AWS path was instrumented at the existing Nix process boundary,
not inferred from a timeout. One selection and one successful publication used
six =nix-instantiate= invocations with identical arguments, plus one
=nix-store --realise=. The six evaluations came from:

1. The receiver-local initial derivation demanded by the generated guard.
2. SelectedPackages' full package currentness check.
3. The OpenTofu configuration admission's own currentness check.
4. The explicit =.with-packages= handoff to a realized selection.
5. Publication's pre-admission package check.
6. Publication's post-admission package check.

This was repeated /instantiation/, not six provider builds. The same selected
Graph, derivation and realized output were already reused. The defect was that
an identity check also requested derivation registration in the Nix database.
The first command now selects =drvPath= directly with =--read-write-mode=, so
the required derivation is registered for realization. Subsequent checks select
the same attribute without write permission:

#+begin_src text
nix-instantiate --eval --raw --attr drvPath <expression> --argstr <name> <value>
#+end_src

The existing Source dispatch, process observers, Nix realization and Graph are
retained. A dynamically bounded query mode changes the command inside the
existing instantiate function; it is not a second Source hierarchy, runner,
result cache or public configuration syntax. Flake Sources retain their own
existing =nix eval= implementation. Exceptions restore the previous query mode.
The serialized guard uses the same identity-query path.

This distinction is observable, not just a renamed command: the real-Nix control
requires the initial =.drv= to exist, requires an unseen changed query's =.drv=
not to exist, and then requires explicit construction of that changed identity
to register the same path. The expression includes a per-fixture salt to avoid
mistaking an earlier test's registered path for a newly written derivation.

The exact-input diagnostic observed 3.399 seconds for registration and 0.724
seconds for a subsequent read-only query with the same derivation identity.
A later complete successful AWS observation retained one registration, five
queries and one realization. The five queries took 1.719, 0.928, 0.535, 1.196
and 0.586 seconds. Initial registration in that run took 13.889 seconds; the
total path took 43.386 seconds. These locally variable samples establish the
command/identity boundary, /not/ an end-to-end speedup or a subsecond SLA.

The focused real-Nix control in
[[file:../../../t/nix-derivation-query-test.ss][nix-derivation-query-test.ss]] checks undeclared transitive import changes,
negative-path changes, and restoration of registration mode after refusal. A
query must not be replaced by a lookup keyed only on expression path, argv or
the expected derivation. None of those describes the full evaluation closure.

** Cold startup is a separate measured cost

[[file:../../../t/aws-startup-cost-test.ss][aws-startup-cost-test.ss]] uses existing TestingScript/Ops execution and
the original std/test harness for three import controls. In the same source-only
qualification environment, process durations were 3.014 seconds for std/test,
8.294 seconds with the standard guarded case, and 5.115 seconds for the actual
AWS atomic file. Every process was fresh; the latter controls benefited from
earlier filesystem activity, and the host was not isolated. They do not support
subtracting those numbers to assign an exact cost to the watchdog.

They do establish that multi-second startup exists without any Nix request.
The 11--18 second init-owned cold observations include metadata/source guards,
the first lazy test-executor import and a fresh source-importing Gerbil worker.
They must not be described as Nix cache misses. This qualification state has no
precompiled Core cache; a cached Nix store output does not supply that cache.
Further import/expansion profiling and qualified compiled-artifact reuse remain
open. Splitting tests does not close this performance requirement.

** Consolidating the five queries by effect boundary

The five-query observation above is historical. Two checks were adjacent on the
initial selection path: SelectedPackages checked packages, then OpenTofu's lazy
=admission= slot checked the same package before validating its configuration.
The outer owner then checked only source files after the validators returned.
The second precheck did not cover mutations performed /by/ a validator.

The current ordering separates value evidence from package publication:

#+begin_src scheme
;; OpenTofu's existing candidate publication (inside its Build role).
admission: (.call (.get scope types configuration) .admit configuration #f)

;; SelectedPackages: after writing guard.ss, for every candidate package.
(for-each
  (lambda (value)
    (when (.slot? value 'admission)
      (unless (yuanxu-validation-evidence-accepted? (.get value admission))
        (error "external package configuration admission rejected"))))
  values)
(current!) ; all package identities AND sources, after all validators
#+end_src

An =admission= slot is cached value evidence over a realized immutable artifact;
it never grants freshness authority by itself. Nix's prepared phase remains a
candidate until its explicit currentness boundary succeeds. Source preflight,
initial derivation registration and realization are retained. A cached value
receipt already did not execute a guard on subsequent slot reads; therefore
freshness must be owned by the operation publishing the package result, not an
incidental first evaluation of that receipt.

The single post-validation check replaces both pre-validation queries. No query
result is memoized around arbitrary Scheme effects. In particular, a validator
changing another package's source cannot escape merely because an earlier check
succeeded. =ops-selected-packages-test.ss= adds a negative control whose accepted
value validator invalidates package provenance: the one final package check must
reject the operation. The old precheck/source-only-postcheck order would accept
that case. Existing failed-admission and changed-guard cases remain unchanged.

| Current query | Intervening boundary | Why retained |
|---------------+----------------------+--------------|
| SelectedPackages post-validation | Nix realization and arbitrary configuration validators | Reject changed inputs before returning any selected package result |
| .with-packages handoff | Caller regains control after .run | The same Graph identity does not prove that transitive Nix inputs stayed unchanged |
| Publication pre-admission | Caller configuration and source changes | Establish current package association before checking the final candidate |
| Publication post-admission | Public value Contracts and contextual obligations | Refuse changes during admission; preserve the prior published value |

Thus one selection plus one successful publication should use one registration,
four read-only queries and one realization. =aws-publication-cost-test.ss= checks
two queries at selection completion, no extra query while binding the actual
Contract/Schema association, and four at publication completion. Existing
selected-Graph process budgets change from three evaluations to two per package
selection (registration plus final query); type read/compile and realization
budgets are unchanged. These are intended operation counts, not timing thresholds.

The handoff's check is redundant only if a caller can prove an effect-free
handoff or a complete immutable evaluation closure. The general public method
cannot assume that property merely because this fixture calls it immediately.

incremental imports, then =core-expand=, =current-expander-compile= and
=current-expander-eval= separately for a real inherited Profile. It also observes
source reads while demanding the actual =init.modules.aws.tests= projection.
No alternative harness, parser, test-discovery list or business scope is used.

Imports include their source/dependency expansion and initialization; these are
incremental costs in one process, not standalone cold-import benchmarks. In
particular, charging the whole first =core/types= import to Core would be wrong:

The comparison does not attribute all timing differences to the code changes.

Discovery made 10,468 source reads and 391 guard calls in the earlier sample,
with 7.441 seconds spent inside pure source-check scopes. The later sample made
9,912 reads and 385 guard calls, with 2.212 seconds in those scopes. These expose
repeated source validation and eager declaration/role importing during metadata
discovery; an unforced business =scope= does not mean zero declaration expansion.
Macro sugar itself is not the observed multi-second cost. Many source reads and
first-import costs remain; neither observation establishes a subsecond startup.

Two bounded duplicate operations have been removed:

- On a new test-projection cache entry, =module-test-projection= has already
  checked the full snapshot. The init owner now performs only inert POO
  composition/cache insertion before returning it. Cache hits still recheck;
  no observation is reused across caller actions or execution.
- A prepared publication retains the compiler identity determined by its exact
  header/role bytes and native package snapshot, just as prepared build sources
  already do. Its guard checks all those bytes, negative role/package lookups,
  native package metadata and prelude inputs without reopening/parsing the
  interface just to derive the same identity again. The native regression checks
  one identity read over preparation plus five independent guards, then refuses
  a changed header and a newly inserted closer gerbil.pkg. Existing manifest,
  role-byte and init-change controls remain unchanged. The later discovery
  sample records eight identity reads for its eight selected declarations.

The CLI contributes another concrete cost. The installed original Standard
Library maps =gerbil env= to =gxpkg env=, whose module imports =std/net/request=
and whose env command invokes the requested test tool as a child process.
=gxtest= itself already calls the native local-environment setup helper. A
same-file Ops control with the same heap options measured 3.715 seconds through
the package wrapper versus 2.168 seconds through =gerbil test=. This is a local,
ordered observation, not a portable speedup ratio.

TestingScript now uses the original =gerbil test= directly when the effective
environment already has GERBIL_PATH and its package-bin directory has first PATH
priority. That condition is checked inside every guarded execution, including
Ops overrides, rather than cached in a POO slot. Missing setup delegates to the
original =gerbil env gxtest= implementation, retaining its package/PATH behavior.
Explicitly different command declarations remain honored. Both routes retain
the same source guard, fixture cleanup, heap cap, timeout and completion checks;
the existing Ops completion receipt remains the result. No user initializes Context,
maintains a runner, imports gxpkg, or declares an extra function to obtain this.

The prepared environment pair is frozen into the actual Ops request so ambient
changes after the decision do not change the tested PATH priority. A native
same-source regression also changes PATH via an Ops override; the delegated
route must restore package-bin priority in the child. This tests effective
environment behavior, not an assumed argv field on Ops receipts (they do not
have one). The first probe attempted that nonexistent field and was rejected;
the corrected probe checks the actual child environment instead.

The consolidated real AWS count probe passed with one registration, four
read-only queries, one realization and final-child/parent-cache assertions.
Queries took 0.691, 0.718, 0.884 and 0.484 seconds; registration took 2.378 seconds
and realization 0.330 seconds. Selection completed at 11.089 seconds, Contract
binding at 12.143 and publication at 14.207. This receipt validates the reduced
call count, not a stable speedup ratio against observations at different load.

The launch regression passed with wrapped/direct/changed-PATH durations of
3.935/1.392/3.120 seconds for the same plain file and heap settings. A subsequent
module-testing gate passed with natural exit zero, covering lazy scope/test
selection, source guards, fixture cleanup and actual JsonSchema/Funflow tests.
The existing TestingScript policy unit gate also passed. No full build or
aggregate test run is used as a substitute for these focused controls.

An intermediate real AWS integration printed all completion markers but Ops
still received status 124. It remains a failed natural-exit gate: markers alone
do not establish successful completion. That observation preceded the direct
native test launch, and was not converted to success or assigned to Nix time.

After the native launch and environment snapshot changes, a fresh invocation of
=t/aws-context-publication-test.ss= passed through the actual init-owned endpoint
with MODULE-OK, HARNESS-OK, final OK and natural exit 0. The full existing Schema
upgrade, cached-parent/final-child, Context refusal, stale receipt, typo and
requirement-map mutation assertions were retained. This is the current functional
receipt; the earlier status-124 observation remains a separate failure.

Residual startup work is explicit: roughly ten thousand reads still occur while
discovering the eight declarations in this init. Selected declarations import
their role/dependency sources even though business scopes are not forced. More
reuse across those imports would cross macro/initialization effects; it cannot
be obtained by widening a source-read cache. A qualified compiled declaration
closure or narrower metadata/role boundary requires separate evidence. The
current change removes bounded duplicates and the unnecessary prepared-env
process, and does not claim that remaining discovery is optimal.

** File and stage attribution of declaration discovery

The existing source observer now accepts numeric events keyed by
=(file-request phase path)= and =(file-read phase path)= in addition to its
unchanged aggregate symbol keys. Requests include cache hits; reads count actual
=module-source-read= byte reads. These events are emitted only while an observer
is installed. They do not measure the SDK's own file IO or prove that filesystem
data came from disk rather than the OS cache. The native Ops startup probe emits
stage totals and the ten busiest files, rather than a complete path transcript.

The principal duplicate was not repeated Profile macro expansion. Graph closure
discovery obtained a publication, then Core-node and Feature-node assembly asked
the source resolver for the same publication again. Each lookup could trigger a
whole reader/tool-source validation even though the resolver already held that
publication object. =select-module-graph= now retains each actual publication once
for this candidate Graph and uses it for its existing nodes and dependency edges.
This index stores objects, not accepted freshness results or source bytes. No
second module namespace, resolver, execution Graph or initialization cache exists.
After lazy author slots have been evaluated, an independent source check must
succeed before the candidate Graph can be returned. The existing outer selection
guard remains. A native regression mutates source-currentness from a lazy Feature
slot, observes exactly one publication acquisition, and requires final refusal.

An un-realized selection also no longer performs the same source guard twice
with no intervening operation. A realized selection still rechecks after its
package admission, which may execute external effects. The configuration-role
reader's own pure currentness traversal now shares the existing bounded read
cache across tool and role observations. This scope ends before wrapper writes,
native imports, expansion or evaluation and begins afresh on the post-check. It
does not account for the discovery reduction above: that control did not enter
the configuration-role stage.

The configuration-role regression exposed a separate, reproducible stale-value
bug. A new role session read the edited source but returned the old imported
object (=1= rather than =2=). Removing the proposed pure observation window did
not fix it. A temporary native import trace located the problem: importing the
generated entry disabled our role interceptor before its relative imports were
expanded, so the SDK original-path registry supplied the previous role context.
The generated entry now keeps interception active; SDK/library delegation still
uses its original boundary. No upstream expander code or registry was changed,
and the temporary trace was removed. The unchanged regression then passed: the
new child sees =2=, the parent retains =1=, stale source refuses and unadmitted
imports remain forbidden. This is context isolation, not permission to reuse
expanded modules across source epochs.

The real AWS gate then exposed a previously masked dependency-closure omission:
the Build role received only owner-local private sources, so the now-active
interceptor refused an already-publication-observed Nix type dependency. Build
role evaluation now consumes those exact recorded transitive inputs as well;
it still excludes data assets, owner roles already supplied separately and SDK
tools with canonical checked contexts. This uses the existing publication input
Graph, not an arbitrary-directory exception, Core namespace exemption or a new
Loader. Inputs not present in that admitted closure remain refused. The initial
AWS failure is retained separately from any subsequent successful run.

The next AWS attempt correctly refused a source-only public POO dependency that
the configuration reader had treated as prebuilt-only. Both readers now use the
same existing canonical-library identity/path check, extracted into one private
function. A configuration import outside its recorded Core closure is accepted
only as an exact SDK-resolved non-Core library source; its byte/package guard
joins the current input observations. A Core-like name or same-name foreign file
does not qualify. The added native configuration control accepts the actual
public metadata library and rejects a foreign same-identity file before its
initialization marker can run. Parent/child isolation and the original unadmitted
local-import rejection pass unchanged. These corrections do not relax source
confinement or add another dependency resolver.

One subsequent AWS attempt reached the unchanged Ops deadline (status 124).
The single-version cost probe then failed the existing debug memory policy
before its first Nix invocation. That is a Scheme preparation failure, not
evidence that Nix evaluation is slow; neither limit was increased. Two further
duplicate traversals were identified in the corrected role path:

- Each SDK import checked every selected private role. It now uses the same
  demanded SDK dependency-subgraph check as the publication reader. Complete
  role/input checks still bracket evaluation. Every import check gets its own
  pure read window; observations never span macro expansion or initialization.
- Build evaluation re-expanded the publication's already-observed dependency
  sources. It now references the exact existing =kernel-contexts= entries from
  that reader, paired with their recorded guarded input. Owner-local roles keep

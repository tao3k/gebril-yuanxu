* Common module mechanism; domain-specific ordinary values

Build/test composition supplies artifact paths once. Each published scope is a
normal instance of the same native module prototype:

#+begin_src scheme
(.def (AWS @ OpenTofuModule.)
  config: (.o provider-artifact: aws-path))
(.def (AWSCC @ OpenTofuModule.)
  config: (.o provider-artifact: awscc-path))
(.def (Null @ OpenTofuModule.)
  config: (.o provider-artifact: null-path))
#+end_src

These declarations belong to upstream package integration. Resource authors
use only the published scope and native admission:

#+begin_src scheme
(use-module AWS as cloud
  (.call (.get cloud types resources aws_security_group) .admit
    (.o name: "web" ingress:
      (list (.o from_port: 443 to_port: 443 protocol: "tcp"
                cidr_blocks: '("10.0.0.0/16")))) #f))

(use-module AWSCC as cloud
  (.call (.get cloud types resources awscc_ec2_security_group) .admit
    (.o group_description: "web" security_group_ingress:
      (list (.o ip_protocol: "tcp" from_port: 443 to_port: 443
                cidr_ip: "10.0.0.0/16")))) #f))

(use-module Null as cloud
  (.call (.get cloud types resources null_resource) .admit
    (.o triggers: (.o release: "smoke")) #f))
#+end_src

Ordinary values require no inheritance operators. No getenv, artifact-directory
factory, manually retrieved prototype or user-authored proof enters these
resource configurations. The existing hygienic =use-module= implementation is
unchanged. The repeated =cloud= alias is local to each expression and binds that
expression's original native module object.

All three published resource Contracts retain Provider address, exact package
version and raw Schema digest. Module source is the existing generated SourceRef
for its own artifact directory, with matching native metadata. Each native
admission result identifies the Contract that actually validated its candidate.
A metadata record remains an association; the package manager owns trust in the
selected package closure.

* Genuine equal-name controls

The real resource names have different Provider prefixes. Renaming those fields
or fabricating schemas would not qualify actual same-name isolation. Instead,
the public scope now lazily publishes the real configuration node shared by all
three exports as =types.provider=:

#+begin_src scheme
(use-module AWS as cloud
  (.call (.get cloud types provider) .admit (.o region: "us-east-1") #f))
(use-module AWSCC as cloud
  (.call (.get cloud types provider) .admit (.o region: "us-east-1") #f))
(use-module Null as cloud
  (.call (.get cloud types provider) .admit (.o) #f))
#+end_src

The three =provider= Contract objects and identities are distinct. Their
Provider/version/digest metadata remains tied to their respective package.
This is also a behavioral control: the AWS configuration Contract accepts
=skip_credentials_validation: #t=; the awscc Contract rejects that unknown
field. Null's empty Provider configuration rejects =region=.

A second unmodified same-name case exists within awscc: both resource and data
exports contain =awscc_ec2_security_group=. They remain separate native slots:

#+begin_src scheme
(use-module AWSCC as cloud
  (.call (.get cloud types data awscc_ec2_security_group) .admit
    (.o id: "sg-1234") #f))
#+end_src

The data Contract requires =id= and rejects the resource candidate. The resource
Contract requires =group_description= and rejects the data candidate. Their
objects, qualified identities and cached publications remain distinct. Compiling
the data Contract does not replace the already-cached resource Contract.

This requires only the closed source-format kinds =provider/resource/data= in
the existing generic publisher. Contract cache keys include kind and name;
qualified identities include package Provider/version, kind, name and export
digest. No Provider-name switch, shared global Contract registry, public macro
or new configuration DSL was added. The private raw-export binding is named
=provider-schema=, distinct from the new native =provider= slot, so POO lexical
slot binding cannot capture it while constructing resource catalogs.

* Demand boundaries and error paths

The executed checks establish:

- Construction and bounded aliases leave all three provider slots unforced.
- AWS resource demand leaves awscc and Null modules unforced; awscc demand
  still leaves Null unforced.
- Resource use does not force its Provider configuration Contract. Selecting
  Null's configuration Contract does not construct its resource catalog.
- AWS IAM membership and awscc S3 bucket Contracts remain uncompiled while
  their Security Groups are used.
- AWS data catalog remains unforced. Other awscc data Contracts remain
  uncompiled when the Security Group data Contract is selected.
- Null has exactly one exported resource. Its resource is unforced until it is
  explicitly selected; its real =null_data_source= branch remains unforced
  afterwards. There is no invented second Null resource in the fixture.

Port type rejection retains =(ingress 0 from_port)= for AWS and
=(security_group_ingress 0 from_port)= for awscc. A numeric Null trigger is
rejected at =(triggers release)=. The real awscc nested_type list is consumed
by the same shared JSON Schema -> native Contract compiler; no private awscc
field validator duplicates that owner.

This is compilation/publication laziness, not resource-granular schema IO:
first demand still reads and decodes that Provider's complete export. There is
no cold-start or zero-first-use-cost claim. Package-time partitioning/indexing
and startup/resource cost measurements need separate design and qualification.

* Reflection and remaining design work

The reuse is concrete: three different libraries use one package producer,
one Schema converter and one native publication/admission route, while keeping
their actual vocabulary and package identity. Ordinary authoring remains plain
values; no Provider-specific import/factory/source-proof chain is repeated.
Provider configuration and resource/data Contracts have explicit separate roles.

The UX is still incomplete: raw exported resource names are long, upstream
integration still supplies each selected package scope, and first demand parses
a complete export. Domain libraries can publish maintained Profiles to shorten
ordinary configurations without renaming canonical generated types. Field
explanations, source-aware errors, supported-keyword coverage indexes and
package-time partitioning need their own designs and controls. There is no
justification here for a new public macro or an eager whole-ecosystem registry.

The next scientific questions are whether heterogeneous Profile composition
preserves these associations, how unsupported selected schemas are diagnosed,
and whether measured startup/first-demand costs remain bounded for large
selected graphs. Those questions require additional executable evidence; these
selected-schema controls do not answer them by extrapolation.

* Core principle: modular configurations

The [[file:11.63-aws-two-layer-interface.org][two-layer AWS interface analysis]] separates ordinary values from justified
executable extension, including the still-missing deep direct assignment.
The [[file:11.64-configuration-and-iac-platform-boundaries.org][configuration/platform comparison]] records real ecosystem strengths,
questions and criteria for removing unjustified abstraction rather than
rebuilding existing IaC engines or control planes.

[[file:11.32-modular-configurations-core-principle.org][Modular configurations are a core design principle]], grounded in Nickel's
official rationale and actual Omnibus AWS/Sandbox sources. Configuration must be
inspectable and composable, retain final-value dependencies and admit selected
results without exposing implementation plumbing. Functions remain first-class
for algorithms and explicit transformations. This is selective ecosystem learning,
not a goal of reproducing the Nix module system or its merge policies.

The [[file:11.33-aws-contract-composition-and-local-dependencies.org][AWS Contract composition and local dependency design]] makes that principle
concrete: configuration and mandatory Contract contributions travel together;
dependency requirements are explicit; users replace ordinary values and receive
Contract-driven discovery and source-aware resource diagnostics.

Read the consolidated [[file:scenarios/modular-configuration/contributions/aws-project/config.ss][AWS consumer config.ss]] and its [[file:11.69-aws-case-index.org][source guide]]: Module capability,
independent Profiles, named Scenario relationships and one ordinary user edit.
The reusable capability uses the established Module role shell outside the case;
shared provenance/admission stays in Core. The [[file:11.68-audit.org][source audit]] records removal of
the over-split 19-file draft. All these sources are design-only, not build inputs.

* Purpose and organization

Treat configuration-language design as a distinct research track, with evidence,
reflection and acceptance criteria, not a collection of incidental Scheme syntax
examples. Start from a maintained Profile, its consumer and a real change. Choose
ordinary assignment, data transformation, object construction or protocol extension
only after stating that intent. Native POO is an available abstraction, not an
obligation imposed on every configuration author.

This configuration-language track complements the Core-owned
[[file:../../../module-system/design/00-index.org][Module System design chapter]].
KCL comparison and scope-binding research live here; existing ecosystem evidence
remains linked at its original location. Use :config-language: for this track, plus
:comparison: for external evidence, :data-overlays: for value transformations,
and :design: for proposed POO interfaces. These are documentation tags, not runtime
module/category metadata or a new package catalog schema.

* Public names and Gerbil syntax

Use YuanxuObjectContract. for the object Contract in design examples. POO is the
normal object semantics; Native is not a second public category. The current
[[file:../../../types.ss][Core export]] still uses its earlier name, so these examples describe a pending
API rename, not an already available binding. Migrate the owning definition and
consumers directly when implementation is authorized; do not add an alias layer.

Keep Gerbil/Scheme syntax: boolean #t/#f and keyword disable: #t. Emacs Lisp t
and Doom :disable are reference-language syntax, not substitutes for Scheme
booleans/keywords. Existing yuanxu! is the bounded declaration surface; its
new mode/root/disable interpretation remains a proposed extension, not a reason
to create a second package DSL.

* Required comparison discipline

Compare both library maintainers and downstream authors using the same task and
defaults. Record operation semantics, identity/conflict rules, diagnostics, demand
and effective output. Do not compare an elaborate POO implementation with only
another language's minimal syntax, or claim superiority merely from supporting
higher-order functions. Use actual library consumers where evidence is available;
label language-only examples and pending ecosystem research explicitly.

Every comparison must end with a conclusion answering: (1) what Agentic AI Lab could
improve for the matched real task, (2) where it is worse or incomplete, (3) why the
additional abstraction is needed, and (4) what evidence would establish the gain.
Separate native mechanism, proposed ecosystem capability and measured result.
Relate Scheme functions, POO, Contracts, generics and MOP to a maintenance problem;
do not treat expressiveness itself as proof of a better user interface. The
[[file:../../../../docs/10-19-design/10.08-config-languages/11-guestbook-source-comparison.org][Guestbook conclusions]] apply this format to the three-service baseline.

Distinguish three layers: data operations describe transformations over ordinary
values; business functions encode maintained task policy; POO inheritance and
Contracts preserve object behavior and validate admissible extensions. Namespaces
organize exports. Do not repeat the namespace in each function name or create a
new DSL to select procedures that normal lexical binding can already select.

* Reflection and next evidence

Scheme can express general transformations, but that alone does not supply field
discovery, stable-key conventions, conflict diagnostics, pure execution, bounded
cost or source-qualified previews. The design must supply those deliberately.
KCL demonstrates the value of making operation intent visible; dmerge demonstrates
collection-update needs beyond append. We must retain both clarity and familiar
Scheme composition instead of hiding merge policies behind arbitrary functions.

Next qualification needs matched executable cases for replacement versus update,
missing/duplicate identities, order-sensitive composition, final-field rejection,
and unselected-demand controls. The new function publication/preview examples are
designs, not executed results. Existing native POO receipts retain their narrower
scope. Loader implementation is excluded.

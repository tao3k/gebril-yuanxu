* OpenTofu: instance identity must be known before resource actions

Primary sources:
- [[https://opentofu.org/docs/language/meta-arguments/for_each/][OpenTofu for_each]].
- [[https://opentofu.org/docs/language/state/locking/][OpenTofu state locking]].

The for_each reference requires known instance keys before remote actions and
rejects unsuitable sensitive/impure choices. This preserves stable addressing;
it is not merely a missing collection function. State locking protects applicable
backends from concurrent writers; the reference notes backend-dependent support.

In our design, rename must not accidentally change a provider's resource identity.
Module owner, Profile instance and resource address are different identities.
A lazily obtained VPC ID can remain unknown in a resource input, but it cannot
silently become the key used to discover a new set of modules during admission.

Controls: a stable named machine with an unknown VPC ID remains representable;
an unknown machine-name set is rejected or explicitly staged. Two operators
executing the same plan require a state/execution policy beyond native slot caches.

Reflection: what exactly can a configuration preview promise while some values
remain unknown? Can a user distinguish omitted, null, unknown and invalid without
learning provider internals? These distinctions belong in the platform, with
simple diagnostics at the field path.

Conclusion: continue reusing the existing OpenTofu/provider boundary rather than
reimplementing state management inside the Module loader. Scheme can improve the
composition surface without claiming to remove external planning constraints.


* Issues and Engineering Limitations

Reference marks: documented restrictions are DOCUMENTED-LIMITATION; user
reports are ISSUE-REPORTED and NOT-REPRODUCED unless stated otherwise. Upstream
state and report dates below retain their original observation scope. No new
CONFIRMED-DEFECT classification is made by this editorial update.

No platform-specific GitHub issue has been independently examined in this
dossier yet. The current observations are based on the specifically cited
primary documentation. Do not infer that all documented restrictions are bugs,
or that absence of an issue review establishes absence of user problems.

The source links above remain the authority for each report. Pin missing versions
and run an isolated reproduction before promoting an issue-reported observation
to reproduced behavior.

* Independent reflection and questions

1. Which instance keys must be known before planning, and which input values may remain unknown?
2. Does removing a configured module imply forgetting, retaining or destroying remote resources?
3. What identity does a provider lock bind, and what is outside a generated Schema Contract?

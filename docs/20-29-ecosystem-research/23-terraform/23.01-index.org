* Research purpose and result

Understand a real maintained module interface and the engine that consumes it,
then identify requirements for our Module System. HCL expressiveness, module
composition, provider Schema, instance expansion, planning and execution have
separate owners. Choosing Scheme does not collapse these responsibilities.

This source study finds useful dependency inversion and small public interfaces,
as well as concrete tradeoffs in object conversion, graph granularity and phase
visibility. These are architectural findings, not a claim of POO superiority.

* Issues and Engineering Limitations

The [[file:23.05-issues-and-user-costs.org][dedicated issue register]] and [[file:23.07-practitioner-experience-and-restrictions.org][practitioner study]] own original references, report versions, observation
states, user cost and reproduction status. Marks distinguish reported behavior,
maintainer explanation, documented restriction, open enhancement and historical
resolution. A bug label alone is not confirmation and a closed issue can still
expose an important design tradeoff.

* Evidence boundary

The study reads identified sources and recomputes one existing Schema digest.
It does not run terraform init/validate/plan/apply, authenticate a new artifact,
reproduce an issue, deploy AWS or benchmark the engine. The connected root is
complete source for its stated infrastructure case but still needs user AMI,
credentials/access decisions and runtime verification. Historical pins are
research controls, not recommended current releases.

* Conclusion

Design stable interfaces and phase-aware dependency semantics before making args
shorter. Do not expose every private slot to gain extension, or turn a uniform
namespace into global coupling. The wider comparison belongs to
[[file:../../10-19-design/10-configuration/10.04-module-system-design-questions.org][the module-system architecture study]], including official NixOS modules,
devenv and Flox as independent research subjects.

* Interpretation of the reports

Issue 2072 asks for dependency/readiness ordering: submitting one resource is not
proof that another can use it. Issue 4616 discusses who should determine readiness
and whether that logic belongs in a function rather than accumulating core rules.
Both are historical design evidence; do not present them as untouched current bugs.

Issue 6139 describes a rollout problem when composition revisions do not bind the
function revision that interprets them. Its lesson for us is that pinning config
alone is insufficient if a projector, Contract or execution implementation changes.
The issue's exact status may change; its reported scenario remains the evidence.

These are distinct requirements: ordering/readiness, ownership of readiness logic,
and versioned interpretation of configuration. A single generic dependency edge
should not be assumed to solve all three. See [[file:27.04-case-reflection-and-onwards.org][the proposed case controls]].

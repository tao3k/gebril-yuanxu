* Relating the real service workload without inventing parity

The local Core Gitea/PostgreSQL Scenario has known JSON input ports. Its default
client endpoint reads the final database object. It can validate equality and
produce a pure plan before any process runs. Our candidate/plan identity check
rejects a cached parent plan attached to the changed child.

A Pulumi version might instead consume a database endpoint that is unknown
until provider execution. That endpoint is a dependency-bearing value, not
merely an integer waiting for a lazy slot to be forced. The following is an
analyst's workload sketch, not an executable Pulumi case:

#+begin_example
provider database endpoint -> Gitea connection input
known configuration port -> local field and policy checks
unknown endpoint          -> deferred decision with dependency retained
#+end_example

Comparing only known local values would hide the harder case. A Scheme lambda
must not turn an unknown endpoint into null or discard its dependency. A POO
plan cache must not conceal whether a field was known. Secret propagation also
requires a specified adapter and redacted diagnostics; a raw object graph does
not provide that security property by itself.

* Reflection: candidate difference and cost

Our candidate contribution is one selected-module publication boundary carrying
source association, complete requirements, domain admission and final plan
identity. Ordinary users should still assign values; module maintainers own
those mechanisms. Pulumi already demonstrates rich dependency semantics and
preview/execution machinery, so claiming that adding Contracts alone makes us
more trustworthy would be unsupported.

The cost for our system includes an explicit external-value protocol, a policy
for deferred admission and a consumer that binds an admitted plan to authorized
effects. None is demonstrated by the Fixture recovery tests or by the current
pure Gitea endpoint equality check. No runtime, performance or UX superiority
claim is made by this comparison.

* Known-port comparison fragment

The following is analyst-written TypeScript using the documented
[[https://www.pulumi.com/docs/iac/concepts/config/][Config API]], not an official Gitea component, provider resource or executed
stack. It deliberately uses known values so the comparison stays within our
current local Scenario's boundary:

#+begin_src typescript
const config = new pulumi.Config();
const databasePort = config.getNumber("databasePort") ?? 5432;
const giteaPort = config.getNumber("giteaDatabasePort") ?? databasePort;
if (giteaPort !== databasePort) {
  throw new Error("Gitea database port must match PostgreSQL");
}
export const connection = {
  postgresql: { port: databasePort },
  gitea: { databasePort: giteaPort },
};
#+end_src

This demonstrates why endpoint equality is not a unique Scheme capability.
A maintainer can encapsulate the same check in a Pulumi component. This fragment
neither validates the full port range nor provisions a service. A fair advantage
experiment must compare independently supplied requirements, source association
and publication behavior, not this hand-written equality alone.

* Nickel: composition does not remove local interface obligations

Primary source: [[https://www.tweag.io/blog/2024-06-20-nickel-modules/][Nickel modules]], 2024-06-20.

The article combines a Schema field with a config field and demonstrates both
merged validation and stricter local consistency. When a fragment depends on
fields declared elsewhere, it makes that dependency explicit rather than relying
only on a globally successful merge. It also demonstrates source-located Contract
errors and editor integration. These are concrete UX expectations, not just type
system terminology.

Our response: native responsibilities/Contracts constrain published values;
the dependency graph records which owner supplies each referenced interface.
An args tree must not turn local code into an unconstrained global participant.
Schema-derived field discovery and diagnostics must reuse existing JSON Schema
Contracts rather than maintain a separate manual list of option names.

Conclusion: local checking and final composition checking answer different
questions. Remaining gap: a generic object-shape Contract on an inferred edge
does not replace an explicit domain requirement or all inherited obligations.
Test strict edge Contracts separately before claiming automatic association is
complete. How can an Agent inspect required versus optional fields without
forcing every unrelated value? That is an outstanding tooling requirement.


* Why use a general language? Accept the cost explicitly

Primary source: [[https://github.com/nickel-lang/nickel/blob/master/RATIONALE.md][Nickel language rationale]].

The rationale discusses the configuration role, effects and the tradeoffs of a
dedicated language versus an embedded one. Scheme makes library reuse and
domain-specific functions available, but it also permits effects, nontermination
and arbitrary macros. Choosing Scheme does not make those problems disappear.

For this system, assignment remains ordinary data, a transformation remains a
named function, and prototype inheritance is used only when retaining an existing
object matters. Macros own contextual/phase bindings and source-preserving
lowering; they must not grow into a second configuration evaluator.

Conclusion: the advantage sought is reusing one language and object system across
simple values and advanced extension. The cost is macro governance and effect
discipline. Declaration scanning is not a security sandbox for hostile Scheme.
We must report whether loading merely avoids published run methods or actually
constrains all initializer effects; those are different claims.

1. Which Contract requirements survive merging and derivation?
2. Can a partial contribution be valid locally while depending explicitly on another contribution?

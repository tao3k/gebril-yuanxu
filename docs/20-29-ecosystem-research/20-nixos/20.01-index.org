* Research purpose

Understand how the NixOS module library supports thousands of maintained modules,
small ordinary configurations, independent contributions and deferred values.
Nix the language, lib.modules, NixOS service integration and the package/runtime
systems have different responsibilities. This dossier does not reduce them to
one language feature or claim that POO replaces them automatically.

* Evidence baseline

The nixos-24.11 branch was resolved through GitHub to commit
=50ab793786d9de88ee30ec4e4c24fb4236fc2674=. Mechanism and case studies use that
immutable historical revision. This is not a review of the newest release.
GitHub issue metadata was refreshed on 2026-10-17; affected versions and local
reproduction status remain separate for each record.

Ten pinned upstream files were read: lib/modules.nix, lib/types.nix,
lib/options.nix, module-list.nix, PostgreSQL and Gitea service modules,
PostgreSQL VM test configuration, lib/tests/modules.sh, its conditional-presence
fixture and the module-system manual chapter. Maintained Gitea-to-PostgreSQL
integration is the real case. Analyst-written consumer variations are labeled.
No Nix evaluation, VM test, deployment or benchmark was run.

* Key conclusions and their costs

- A maintained declaration universe enables excellent integration and discovery;
  selective source loading must replace ambient availability with sound published
  requirements and a current metadata index.
- Dependency injection is phase-sensitive. Lexical bindings can improve locality,
  but cannot make source selection depend safely on its own evaluated result.
- Option types participate in merge and discovery. Native POO slot precedence
  cannot silently replace independent-contribution or requirement semantics.
- Laziness is not absence, complete validation or reuse across derived instances.
  Discovery, admitted preview and execution need different forcing boundaries.
- The real user-interface advantage comes from maintained consumer integration.
  Our framework still owes resource/lifecycle consumers, migration and diagnostics.

* Conclusion and Onwards

The design target is a more inspectable, selectively loaded and extensible module
framework, with small value inputs and deliberate native extension. Evidence
still required includes pinned issue reproductions, selected-graph cold/warm
measurements and real consumer qualification. See the concrete acceptance controls
in 20.08; this dossier now contains research and decisions, not only a map.

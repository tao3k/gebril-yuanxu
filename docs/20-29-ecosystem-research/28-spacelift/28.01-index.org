* Research scope

Research the governance and execution platform, including its own configuration inputs. It is not a replacement configuration language, and stack dependency semantics are not a module import protocol.

This dossier is the owner of Spacelift-specific observations and conclusions.
See [[file:../../30-39-research-foundations/30-method/30.01-evidence-protocol.org][the evidence protocol]] for claim classes and completion criteria.
No platform command, deployment or issue reproduction is claimed here.

* Configuration and scenario baseline

Model network, database and application as separate stacks. Record output mappings, tracked versus proposed run behavior, plan policy input and the approval boundary. A local Scheme object check does not reproduce the hosted workflow.

The current baseline is source/document review. A complete version-pinned
configuration fixture, resolved result and matched negative control remain
required before calling this an end-to-end case comparison.

* Spacelift: dependency order and policy are different boundaries

Primary sources:
- [[https://docs.spacelift.io/concepts/stack/stack-dependencies][Spacelift stack dependencies]].
- [[https://docs.spacelift.io/concepts/policy/terraform-plan-policy][Spacelift plan policies]].

Stack dependencies order related tracked runs; the documented mechanism does
not itself manage stack creation/deletion lifecycle. Output references and run
ordering are related but distinct. Plan policies inspect planned changes and
can block or require review. A successful schema check is not that policy decision.

Our design implication: Module dependency, configuration reference and execution
handoff cannot all be represented by one unlabeled requires edge. A named
Scenario can assemble these relations, but its prototype parent order cannot
serve as execution order or approval authority. Policy input must identify the
actual projected/provider plan and the source/provider generation it describes.

Reflection: should the same object that prepares a plan be able to authorize it?
How does a harmless field update invalidate an earlier approval? What prevents
a hidden function from bypassing the declared run boundary? These are authority
and lifecycle questions rather than syntax problems.

Conclusion: use workflow platforms as governance references. Do not call a Module
scope Contract an approval policy or an Ops process a deployment coordinator.


* Issues and Engineering Limitations

Reference marks: documented restrictions are DOCUMENTED-LIMITATION; user
reports are ISSUE-REPORTED and NOT-REPRODUCED unless stated otherwise. Upstream
state and report dates below retain their original observation scope. No new
CONFIRMED-DEFECT classification is made by this editorial update.

No platform-specific GitHub issue has been independently examined in this
dossier yet. The current observations are based on the specifically cited
primary documentation. Do not infer that all documented restrictions are bugs,
or that absence of an issue review establishes absence of user problems.

The source links above remain the authority for each report. Pin missing versions
and run an isolated reproduction before promoting an issue-reported observation
to reproduced behavior.

* Independent reflection and questions

1. Does a dependency order a tracked run, provide data, authorize it, or manage deletion?
2. What exact plan and source revision does a policy review cover?
3. How can a user migrate effective configuration and policies out of the platform?

* Conclusion

The reviewed material identifies a concrete design boundary; it does not establish
Scheme/POO superiority. The questions above and the matched scenario determine
what must be investigated next. Do not mark this dossier complete merely because
its organizational structure exists.

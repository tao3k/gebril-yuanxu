* Downstream use comes before implementation details

Use the [[file:164-user-interface-scenario-case-previews.org][Scenario usage previews]] as the starting point. Upstream provides
maintained Scenario objects, explicit source Modules, reusable Profiles and
optional domain Contracts for advanced authors. The target adapter details
below are not required reading for a user configuring a maintained Scenario.
These remain proposed interface examples; no new executable exports are claimed.

| Choose upstream | Downstream action |
|-----------------+-------------------|
| a maintained Scenario | inherit it using .def |
| an upstream or user-owned Module | explicitly use-module and name its selected published Profiles |
| configuration to change | native inherited refinement with =>.+ or inherited-value accessors |
| a specific configured Profile | let the admitted boundary project that derived receiver's effective values |

Placement slots identify object paths; bounded as aliases identify lexical
scopes and explicit local occurrences in the proposed adapter. Scenario defaults supply stages, proof
declarations and handoff; users do not rebuild those assemblies. No new
composition wrapper or user Case declaration is required. Contract construction
is an optional advanced path, not the first example downstream users must read.

* User configuration inherits the feature; it does not assemble its internals

The downstream LangGraph, CrewAI and Tool Calling examples above are the accepted
user-first presentation: upstream assets, Scenario inheritance, explicit Module
selection, configuration refinement, then effective selected composition.
Explicit use-module reveals ownership and intended published contributions; it
must not become an inventory of every internal component needed to make a Flow
work. The declarations above bind maintained defaults without enumerating internal
components. Maintained Scenarios already supply those bindings when unchanged.
Default contribution resolution and contextual instance naming remain proposed;
existing source selection lists are owner evidence, not a downstream recipe.

A configured Flow already owns its result interpretation, execution handoff,
normalization and core invariants. The default user surface inherits those
features and exposes task intent and meaningful business parameters. Exposing
all internal slots is not a useful definition of extensibility.

| Concern | Default user configuration | Owner or explicit extension |
|---------+----------------------------+-----------------------------|
| task identity / check-name | supplied by the maintained task, or derived from an enclosing named task slot where a contextual adapter exists | owner defines identity and collision rules; current lexical variable names do not automatically supply identity |
| command-vector, inputs, outputs | configurable when meaningful to the task | owner supplies defaults and validates changes |
| result-protocol, runtime-mode | inherited; no repeated declaration required | named native POO extension of the owning task/Flow prototype |
| profile-ref and internal component wiring | inherited from the chosen feature | publication/selection owner maintains bindings |
| dependencies, retention, retry or compensation policy | exposed only where users make an actual workflow decision | inherited defaults; advanced policies remain explicit |
| generated durable identity, receipts and runtime state | not authored as ordinary business configuration | identity/evidence/runtime owners; not fabricated by an override |

Gerbil/Rust Profiles publish complete build defaults through native contribution
objects. The [[file:164-funflow-cicd-user-authoring-design.org][native Funflow multi-Profile design]] composes them by multiple
configuration, binds Funflow once to its existing Profiles, and lets users
refine separate namespaced builds. It supersedes repeated per-task downstream
construction and an extra Module wrapping each selected Profile. New reusable
Check declarations remain optional for new contributions. Existing raw Check
values still need complete owner-provided defaults and valid identity; simply
shortening syntax does not supply them.

Changing result interpretation or the runtime mechanism is a deliberate feature
extension, potentially replacing core behavior. It remains possible through
native inheritance and slot override at the owning extension boundary, subject
to Contract admission and adapter compatibility. It is neither unrestricted
permission to bypass Flow invariants nor a reason to expose those mechanisms in
every task declaration. Overrides invalidate affected evidence; inherited proof
declarations do not prove the new behavior.

The long (.def (funflow/package @ funflow-check ...)) header in the legacy
payload is native lexical slot binding, not a list of required constructor
arguments. The .def task-authoring layer and native header bindings remain a public user
interface. The full body with every repeated owner default is an internal
reference; converge those repeated assignments without deleting the task object
layer. Users normally refine the complete Profile's inherited Checks; standalone
definitions remain optional. Scenario extension and replacing the
Flow's core mechanism have different purposes and disclosure requirements.

* Demand boundaries: default binding, refinement, admission and composition

This design builds on existing native POO lazy slot evaluation and existing
Loader plans; it does not add another loader, scheduler, cache or object system.
The declaration (use-module CrewAIModule) means a binding to that Module's
maintained default contribution, with local instance identity supplied by crew:.
It means neither all exported Profiles nor all possible internal components.
The default must be unambiguous and owner-defined; absence or ambiguity is an
error when demanded, not a reason to select every export. Scenario policy may
constrain or specialize that default and must validate the effective choice.

| Consumer/action | Demand and allowed work | Work not implied |
|-----------------+-------------------------+------------------|
| Discover a Module, Profile or Scenario | locate bounded source/interface metadata through the existing registry/collection owner | importing all implementation owners or constructing every exported value |
| Declare a default Module binding | retain Module source identity, owner-defined default reference and local slot identity | enumerate all exports, load every component, or start a runtime |
| Inherit/refine a Profile | resolve necessary parent/proto and native slot definitions; evaluate demanded inherited slots as native semantics require | force every sibling Profile or every unrelated slot |
| Inspect configuration | demand the requested effective attribute and its dependencies | materialize a complete module graph just to display one attribute |
| Resolve a selected Profile | resolve its Contract/defaults and selected dependency closure | admit every alternative Profile or every registry entry |
| Contract admission | force all facts and dependencies required by the applicable responsibilities and obligations | skip required validation merely to preserve laziness |
| Automatic selected composition | demand effective participating Module values, stages and dependency/conflict facts for that selection | append original defaults after refinement or compose every configured Profile |
| Explicit runtime Session | execute the admitted effective plan through the owned runtime boundary | execution during declaration, discovery or pure projection |

Inheritance/refinement is not guaranteed to perform zero work: computing =>.+
may demand an inherited value, and resolving an imported native parent may load
its owner. The rule is bounded demand, not a promise that every expression stays
unevaluated until runtime. Lazy POO fields and deferred source loading are
separate existing mechanisms with different triggers.

A bare Gerbil identifier already depends on its lexical import. Writing
(use-module CrewAIModule) cannot undo an eager import or turn an already
constructed Module into an unloaded reference. A scalable interface must connect
its public binding to the existing precise source/interface and Loader boundary;
facades must not eagerly reexport/import all concrete Profiles and Scenarios.
The eventual default-binding adapter must specify its syntax/runtime phase and
how it obtains that bounded binding. This connection is proposed, not proven by
the concise syntax. Current static imports still close their own dependencies.

For thousands of available assets, discovery should locate the requested source
using the existing owner indexes/collection paths; inspecting one asset must not
require importing every registered Module. Resolving one selected production
Profile may load several Module owners and all dependencies necessary for its
admission. It must not force unused development/staging alternatives unless an
explicit cross-Profile obligation requires them. A broad obligation may demand
more data; its scope must be visible and intentional rather than hidden inside
an unconditional whole-registry traversal.

Contract resolution is itself demand-driven: local slot identity, source
identity and Scenario family choose the appropriate responsibility and shared
proto. Construct only the objects needed to answer that demand, preserving
native lazy slots. Validation does not become optional: before execution, every
required responsibility and obligation for the effective selected composition
must be admitted. Existing fixed-map whole-object admission may force all its
required slots; it is not silently relabeled selective admission. Collection and
selected-Profile admission need their own defined scope.

Automatic composition is an inert projection of the selected derived receiver.
It may collect and normalize effective values to produce a candidate plan;
admission may itself demand such pure projections. Successful admission of the
same effective configuration and plan is required before execution. There is no
unconditional eager traversal at Scenario declaration and no demand to start a
Session merely to inspect a plan. Cross-Module dependencies required by a chosen
Profile remain part of that choice even when not named separately by the user.

Native lazy memoization must not leave a derived Scenario reading a parent's
previously evaluated Module Bundle, composition or evidence. Projection reads
its effective receiver; dependencies used by evidence identify that effective
configuration. Reuse only evidence whose dependency identities/revisions still
match, following existing owner rules; do not invent a second currentness cache.
Test parent-first demand followed by child refinement, not only never-forced
parents. Per-export provenance and local binding identities remain preserved
inside a default contribution even though the public component list disappears.

* Internal design and implementation specification

This section preserves Contract hierarchy, parent normalization, recursive
objectification, native expansion and evidence rules for implementers. It is
not the ordinary user interface. Public examples above are intentionally free
of scenario-profile-contract-for, %configured-module, generated self bindings
and private construction metadata. Those details are explained here, not
required as user-authored code.

** Decision and ownership

CompositionContract is the proposed common Contract foundation for all
Scenario compositions. Domain Contracts refine that foundation; Scenario values
inherit the matching Contract proto and are admitted by that Contract. A Scenario
also supplies CompositionContracts, the native POO family of concrete Contracts
and resolution rules. The plural family is not itself the singular base Contract
or the existing Core YuanxuProfileCompositionStrategy. The Scenario family owns the Project
schema, Profiles collection admission, dynamic Profile-name resolution and the
concrete responsibilities for each resolved Profile.

Project directly declares its real Profiles slot. No separate ProjectProfiles
binding is required. The paths remain Project.Profiles.<name>.<module-slot>.
Profile names are user/Scenario data, not fixed generic Project responsibilities.
development, production and staging below are SDLC examples; another Scenario
may use different names, responsibilities and composition rules.

Use existing .def, .o, brace, prototype composition and inherited slot algebra.
The proposed owned declaration adapter uses Scenario-selected Contracts for
recursive construction; it does not introduce a new public syntax. Neither
native .def nor validate currently performs that construction. Users instantiate
and extend maintained Scenario objects through native .def inheritance. No new
composition entry macro, inline type annotation, define-profiles, Override,
chain or application expander is added.
The [[file:164-core-functional-and-extend-interface-audit.org][Core audit]], [[file:164-core-interface-export-inventory.org][export inventory]] and
[[file:164-config-language-case-research.org][configuration research]] remain supporting evidence.

** Contract foundation, domain refinement and Scenario values

#+begin_example
CompositionContract
  -> SDLCCompositionContract / CICDCompositionContract
  -> LangGraphCompositionContract
  -> CrewAICompositionContract
  -> ToolCallingCompositionContract

Each domain Contract.proto
  -> new Scenario configuration
  -> maintained reusable Scenario
       -> user-derived Scenario instance
#+end_example

The first arrows are Contract descriptor refinement. The second group is value
prototype ancestry. A Scenario value must never inherit the Contract descriptor
itself. Shared proto identity matters: equal-looking reconstructed objects do
not prove native ancestry. The prototype/domain symbols below are proposed.

#+begin_src scheme
(define-type (CompositionContract @ YuanxuObjectContract.)
  identity: 'composition
  proto:
  (.o Profiles: (.get CompositionProfilesContract proto))
  responsibilities:
  (.o Profiles: CompositionProfilesContract)
  .obligations: composition-base-obligations)

(define-type (SDLCCompositionContract @ CompositionContract)
  identity: 'sdlc-composition
  proto:
  (.o (:: composition-self (.get CompositionContract proto))
    %composition-contracts: SDLCCompositionContracts
    Profiles: (%scenario-default-profiles SDLCCompositionContracts))
  responsibilities: =>.+
  (.o Profiles: SDLCProfilesContract))

(define-type (CICDCompositionContract @ CompositionContract)
  identity: 'cicd-composition
  proto:
  (.o (:: composition-self (.get CompositionContract proto))
    %composition-contracts: CICDCompositionContracts
    Profiles: (%scenario-default-profiles CICDCompositionContracts))
  responsibilities: =>.+
  (.o Profiles: CICDProfilesContract))
#+end_src

CompositionProfilesContract and composition-base-obligations are owner-provided
proposed definitions. The base admits composition structure, a typed Profiles
collection and common identity/evidence rules without enumerating SDLC names,
Modules, stage graphs or runtime handoff choices. The domain collection Contract
must refine that collection foundation and enforce its own dynamic-name and
Profile responsibilities. Domain proto inherits CompositionContract.proto;
its Profiles value must satisfy both base and domain collection admission.

Native descriptor inheritance alone does not prove monotonic constraint
strengthening. Base obligations must remain applicable to effective values;
replacing a responsibility with a domain Contract must prove compatible or
narrower acceptance. Replacing .obligations cannot discard common checks.
CompositionContracts selection/generation is protected admission context, not
a user-supplied alternate validator. This compatibility needs executable checks.

** Three user intentions and reusable upstream assets

Upstream and vertical-domain owners publish reusable Profiles, configured
Scenarios, domain Profile Contracts and CompositionContracts families. Users
may choose three independent intentions, and mix them within one composition:

| User intention | Authoring action | Reuse boundary |
|----------------+------------------+----------------|
| write several own Profiles and assemble a Scenario | publish native Profile values through an owned Module, or supply admitted inline specifications | Scenario responsibilities validate source contributions and configuration |
| inherit maintained Profiles or Scenarios | .def from the existing admitted value | preserve its prototype ancestry and maintained settings |
| initialize a new Profile or Scenario under a domain Contract | name the authorized construction Contract directly in the declaration header | adapter obtains its shared proto and then admits the new value |

These are intentions, not three runtime classes or three mandatory stages.
Profile publication, Scenario configuration and Contract construction are not
synonyms. Profile values and Module exports may be reused across Scenarios when
the destination Contracts permit them. Already closed runtime Case/Session
objects are not reusable Profile specifications.

*** Complete combined user example

All owner names here are illustrative. The chosen SDLC rules must admit
production, its inherited CI configuration, a checks Module slot, the three
selected exports and their domain data. BuildProfileContract must be an
admitted constructible Profile Contract. This is not permission for an
arbitrary Module or Type to join a composition.

#+begin_src scheme
;; 1. Author a reusable Profile as native domain data.
(.def MyBuildProfile
  identity: 'build
  command-vector: '("gerbil" "build"))

;; 2. Derive from a maintained, already admitted Profile object.
(.def (MyBuildVariant @ MaintainedBuildProfile)
  report: 'team-build-report)

;; 3. Initialize a Profile by naming its domain Contract directly.
(.def (FreshBuildProfile @ BuildProfileContract)
  report: 'team-build-report)

;; Publish all three contributions through one user-owned Module.
(def MyChecksModule
  (yuanxu-semantic-module
    (yuanxu-semantic-identity 'user 'checks)
    profiles:
    (yuanxu-module-profiles
      (yuanxu-profile-export 'build MyBuildProfile)
      (yuanxu-profile-export 'build-variant MyBuildVariant)
      (yuanxu-profile-export 'fresh-build FreshBuildProfile))))

;; Fresh Scenario: initialize from the domain CompositionContract.
(.def (FreshTeamScenario @ SDLCCompositionContract)
  Profiles: =>.+
  {production: =>.+
   {checks: (use-module MyChecksModule build build-variant fresh-build)}})

;; Alternative: inherit the maintained Scenario, using the same three Profiles.
(.def (TeamScenario @ SDLCScenario)
  Profiles: =>.+
  {production: =>.+
   {checks: (use-module MyChecksModule build build-variant fresh-build)
    CI: =>.+ {retries: 3}}})

;; Continue refining the resulting Scenario without mutating source Profiles.
(.def (ReviewedTeamScenario @ TeamScenario)
  Profiles: =>.+
  {production: =>.+
   {CI: =>.+ {timeout: 120}}})
#+end_src

FreshTeamScenario and TeamScenario illustrate alternative root parents, not
two mandatory steps. Both incorporate the three Profile creation/reuse
intentions. ReviewedTeamScenario follows the maintained-parent route and will
be selected below. The same three Profile objects are not themselves relabeled
with a production-specific Contract family or cached local proof.

*** Corresponding native expansion

The ordinary declarations and Module publication need no new grammar. The
direct Contract parent is normalized to its shared proto; existing Profile and
Scenario parents remain the actual objects. The following expands every parent
and every configured slot in this combined example, retaining proposed pure
helpers where domain admission/projection still needs implementation:

#+begin_src scheme
(def MyBuildProfile
  (.o identity: 'build
      command-vector: '("gerbil" "build")))

(def MyBuildVariant
  (.o (:: @ MaintainedBuildProfile)
    report: 'team-build-report))

(def FreshBuildProfile
  (.o (:: @ (.get BuildProfileContract proto))
    report: 'team-build-report))

(def MyChecksModule
  (yuanxu-semantic-module
    (yuanxu-semantic-identity 'user 'checks)
    profiles:
    (yuanxu-module-profiles
      (yuanxu-profile-export 'build MyBuildProfile)
      (yuanxu-profile-export 'build-variant MyBuildVariant)
      (yuanxu-profile-export 'fresh-build FreshBuildProfile))))

(.def (FreshTeamScenario @ (.get SDLCCompositionContract proto))
  (Profiles => .+
    (.o
      (production (inherited)
        (let ((profile-contract
               (scenario-profile-contract-for
                 SDLCCompositionContracts 'production)))
          (.+ (inherited)
              (.o checks: (%configured-module
                             profile-contract 'checks MyChecksModule
                             '(build build-variant fresh-build)))))))))

(.def (TeamScenario @ SDLCScenario)
  (Profiles => .+
    (.o
      (production (inherited)
        (let ((profile-contract
               (scenario-profile-contract-for
                 SDLCCompositionContracts 'production)))
          (.+ (inherited)
              (.o
                checks: (%configured-module
                          profile-contract 'checks MyChecksModule
                          '(build build-variant fresh-build))
                (CI => .+ (.o retries: 3)))))))))

(.def (ReviewedTeamScenario @ TeamScenario)
  (Profiles => .+
    (.o
      (production => .+
        (.o (CI => .+ (.o timeout: 120)))))))
#+end_src

%configured-module obtains the checks responsibility Contract from the resolved
production Contract. Its source-selection step is the existing operation:

#+begin_src scheme
(yuanxu-select-module-profiles
  MyChecksModule 'checks '(build build-variant fresh-build))
#+end_src

The local instance name checks comes only from the configured slot. No repeated
as appears. The helper preserves a configured collection with all three source
Profile objects, export identities, provenance and selection proofs. Do not
use car or mix their same-named identity/report fields into one flattened object.
It must bind the exact source Module and alias to the effective collection.

*** Identity, Contract and evidence boundaries

| Fact | Owner in this example | Admission requirement |
|------+-----------------------+-----------------------|
| source Module identity | user/checks semantic identity of MyChecksModule | preserve and validate SemanticModuleContract |
| published Profile identities | build, build-variant, fresh-build export records | distinct indexed exports and source-bound revision/generation |
| inherited source ancestry | MaintainedBuildProfile for MyBuildVariant | preserve compatible parent and derivative origin, not reattest parent proof as child proof |
| constructor Contract | BuildProfileContract for FreshBuildProfile | shared proto plus actual Profile admission |
| local Module instance | checks slot in each selected application Profile | match generated module-instance and binding, case-sensitively |
| outer Profile | production selected under this Scenario | re-resolve concrete Contract and family generation |
| effective Scenario | ReviewedTeamScenario | common and domain composition admission after all refinements |

A published export name is not the same namespace as a Profile object's own
identity slot. Inherited identity fields cannot be silently rewritten to make
an export label appear to match. Any required relationship is the publication
and destination Contract's responsibility. Current Core selection keys use
module-instance plus exported Profile identity inside one Bundle; original
Module/source evidence and Scenario-local scope must remain attached. Do not
claim those local keys alone provide global Scenario provenance.

The demonstration export calls omit revision/generation/provenance arguments,
so current functions use their declared defaults. Those defaults are not a
source-currentness or semantic-proof receipt. A production publication/admission
path must bind actual source versions and owner declarations as required by its
Contracts. Publishing these objects proves neither command safety nor workload
correctness, and does not run the command vector.

Profile values are reusable across Scenarios when destination Contracts permit.
Each embedding obtains an admitted local occurrence/derived view and new local
evidence without mutating the source object, globalizing checks or carrying
another Scenario's validation cache. Existing objects must preserve ancestry;
incompatible destination Contracts fail instead of coercing arbitrary values.
Protected context belongs to the binding, not to a universal fixed identity of
every reusable Profile. A registered Module is not granted Scenario authority
merely because it has exported Profile names.

from TeamScenario and timeout=120 from ReviewedTeamScenario. Scenario-owned

Scenario defaults or substitute an original cached Bundle after modifications.
FreshTeamScenario is a separate composition, not another operand to append.

The Scenario collection admission re-resolves the actual Profile name and
validates source/alias/export/constructor relationships and the owner's
responsibilities. It generates fresh effective Module and stage derivation
evidence, then delegates to the admitted combination policy and existing Core
composer. Initial source selections remain provenance, not proof that edited
configuration is unchanged. Raw user Profile data and declared source proof

%composition during validation.

Only a selected admitted Bundle/plan proceeds to the current inert root/Case
projection. A fresh runtime Session is a separate explicit lifecycle step.
Object construction, Profile publication, validation and selected composition
start no Session or resource execution. The declaration-parent adapter,
configured multi-export view and fresh-evidence projection are all still
unimplemented design requirements.

** Parent recognition and shared-proto normalization

The three intentions use two explicit parent-normalization branches:

| Declared parent value | Meaning in admitted configuration declaration | Native parent |
|-----------------------+-----------------------------------------------+---------------|
| authorized domain CompositionContract or constructible Profile Contract | initialize a fresh typed configuration value | that Contract's shared proto |
| existing admitted Scenario or compatible Profile object | derive from configured value | the same object itself |

#+begin_src scheme
;; User: initialize directly from a domain Contract, without mechanical .get.
(.def (FreshScenario @ SDLCCompositionContract)
  Profiles: =>.+
  {production: =>.+ {CI: (use-module FunflowProfileModule github-ci)}})

;; Corresponding native parent: the descriptor itself is not inherited.
(.def (FreshScenario @ (.get SDLCCompositionContract proto))
  Profiles: =>.+
  {production: =>.+ {CI: (use-module FunflowProfileModule github-ci)}})

;; User and native parent agree when inheriting an existing Scenario.
(.def (MyScenario @ SDLCScenario)
  Profiles: =>.+
  {production: =>.+ {CI: =>.+ {retries: 3}}})
#+end_src

The first case receives domain-proto defaults; the existing-object case also
receives that object's maintained changes. They may have equal fields today if
the maintained object adds nothing but are not interchangeable parent identities.
=>.+ requires inherited slots; new Profile names go through dynamic resolution
and objectification. No third user-facing composition macro is introduced.

Profile Contract initialization follows the same bounded normalization:

#+begin_src scheme
;; Native expansion of FreshBuildProfile's direct Contract parent above.
(def FreshBuildProfile
  (.o (:: @ (.get BuildProfileContract proto))
    report: 'team-build-report))
#+end_src

Current native .def directly uses the supplied parent. Direct Contract headers
therefore require a new bounded declaration-parent adapter; they are not already
supported as Contract constructors. The @ symbol remains a self binding name.
The adapter must recognize admitted Contract descriptors by owner-provided
role/Contract evidence and the expected construction context, not suffixes,
variable names, object? or mere presence of a proto slot. Profile constructors
must not be accepted where a composition root is required, or vice versa.
Existing objects keep their actual identity/ancestry and are not reset to an
inferred base proto. Missing, ambiguous or unauthorized parents fail explicitly.

Parent expressions evaluate exactly once, with binding/source preservation.
Statically admitted descriptors can lower directly to .get; dynamic recognition
stays at native value evaluation rather than running user expressions in the
macro phase. Only owned configuration declarations use this adaptation; generic
POO descriptor manipulation and global .def/brace semantics remain available.
No arbitrary Type is automatically converted into a constructor.

Shared-proto objectification is followed by admission under the selected domain
Contract and common CompositionContract invariants. Obtaining a proto is not a
successful validation receipt. Protected Scenario/Contract-family metadata must
be bound to the admitted construction source. Effective combination reads the
resulting derived values and regenerates evidence; neither initialization nor
inheritance creates or runs a Session.

** Scenario family and dynamic contract resolution

The following is an illustrative upstream family expressed as a native POO
object. These names/rules/helpers are proposed, not existing public exports:

#+begin_src scheme

  Profiles: SDLCProfilesContract
  profile-rules: SDLCProfileRules
  generation: 'sdlc-contracts-v1)

;; The owner publishes one reusable Scenario object, not a descriptor wrapper.
(.def (SDLCScenario @ (.get SDLCCompositionContract proto))
  %composition-contracts: SDLCCompositionContracts

SDLCCompositionContract refines CompositionContract and has a Profiles
responsibility pointing to the domain SDLCProfilesContract. The family's Project
slot denotes this root composition Contract; Project is a family role key, not
another independent universal Contract hierarchy. The generic Project layer must not enumerate development,
production or staging. A different Scenario supplies its own family and base.
Family association is admitted upstream, never inferred from a variable name,
trailing dot, global registry or arbitrary prototype search. A user's attempted
family substitution must be admitted as a Scenario change, not a harmless
configuration edit.

Profiles collection admission needs a proposed named pure function:

#+begin_src scheme

(scenario-profile-contract-for SDLCCompositionContracts 'production)
#+end_src

Resolution uses the Scenario's explicit rule values. A Scenario may allow
arbitrary valid names under a common schema, specialize selected names or
require a defined subset. Generic Project code imposes none of those policies.
Unknown/disallowed names, ambiguous matches and incompatible rules fail with
name, Scenario/family generation and source location. There is no permissive
fallback inferred merely from familiar names such as production.

Current responsibilities admission iterates a fixed slot-to-Contract map; it
does not already resolve arbitrary Profile names. The Profiles collection
Contract therefore needs Scenario-owned collection obligations/admission to
walk effective Profile slots, resolve each concrete Contract and delegate to
its existing native responsibility admission. Required names, if any, are
Scenario policy. Empty collections and extra names are likewise explicit policy.
Do not represent an open collection by an empty responsibilities map that
accepts arbitrary unchecked objects.

Resolution must return stable admitted Contract/proto objects for a family
generation and name. Construction and later validation must use those same
objects; reconstructing equal-looking proto objects fails nominal ancestry.
Any cache includes family/rule generation and all resolution inputs.

** Objectification, admission, projection and Session

| Phase | Responsibility | Runtime effects |
|-------+----------------+-----------------|
| objectification/native derivation | build typed native configuration values using admitted responsibilities and shared proto values | no resource execution; source selection stays inert |
| Contract admission | validate ancestry, dynamic names, module/source bindings, effective constraints and evidence | no Session creation or workload execution |
| selected composition/plan projection | read the chosen derived Profile, generate consistent evidence/Bundles and closed plan/root | pure/inert projection, not an executing Session |
| Session lifecycle | create fresh per-run state and perform explicit prepare/admit/run handoff | mutations and resource execution only under runtime owners |

The .def syntax and existing inheritance are available today; automatic nested
objectification and new effective-evidence adapters are still proposed.
Existing Core validation does not construct parents. A successful reader or
object construction is not admission. A valid closed plan is not an executed
Session. Native .def instantiates a configuration object, not a running job.
Current Case representation and fresh Session protocol remain unchanged.

the resolved concrete responsibilities, applies owner constraints and combination policy, regenerates

profiles where that is the Scenario's selected strategy. Retained original
selection proves source provenance only. Reselecting unchanged exports or
reusing old proofs cannot attest to updated configuration. New evidence
representation and its admission into Core remain to be designed.

the other one's name. Declaration, resolution and projection perform no runtime
actions; resource execution remains behind the explicit runtime boundary.

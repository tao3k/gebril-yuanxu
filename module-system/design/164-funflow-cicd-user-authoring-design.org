* Purpose before syntax: real origin, native scope, natural laziness

The stable design is an admitted native Module scope, not the spelling
use-module. Its purpose is to resolve maintained/upstream/user contributions,
make their actual origins distinguishable, expose native configured Profiles and
prototypes, and connect to one Loader/admission path. Do not make upstream
objects or user composition less expressive merely to preserve an existing
macro's parsing shape. The bounded as form below is implemented over an existing
native scope, not a second runtime object model or a requirement to abandon native
functions/let/POO operations.

Origin is a resolved source/owner/revision relationship. Maintained defaults and
user overrides can coexist in one effective value; record both the source of
the base and the contribution that changed it. A local alias ff is not proof of
upstream ownership. User-supplied names/labels cannot manufacture source evidence.
Built-in, upstream and user-owned sources all use the same admitted protocol.

Natural laziness is the default requirement, not an opt-in defer flag. Creating
a binding must not load its full implementation or enumerate/instantiate every
Profile. Nor may a nominal lazy wrapper simply move a monolithic initialization
bill to the first field access. Source/interface/prototype granularity and
bounded dependency demand must be designed in the owners, not just the syntax.

* Shared object abstraction and ownership of Check composition

Maintained local Agentic AI Lab Modules, third-party Modules and User Interface
Modules use the same authoring abstraction: admitted native Module scopes,
POO Profile/Check/Pipeline objects, prototype inheritance and effective slot
refinement. Upstream owners create and publish defaults through that scope;
downstream users inherit and refine them through target paths. There is no
separate user-side extraction/assembly model or required list DSL for the same
configuration. Common object semantics do not erase distinct Profile/Module
Contracts, source ownership, capabilities or runtime authority.

The Pipeline object owns the selected Check list. Its checks slot computes the
ordered list from the effective Profile receiver, using that Profile's build,
test and package slots. This relationship is part of the native object layer,
not a post-configuration repair or a user step that copies parent Check values.
The list representation exists to serve current consumers; it is a projection
of effective objects, not a second configuration source of truth.

| Layer | Responsibility | Ordinary user requirement |
|-------+----------------+---------------------------|
| upstream Module/Profile owner | publish admitted prototypes/default objects and the receiver-aware Pipeline relationship | use the common module scope when authoring reusable defaults |
| downstream Scenario | bind a Module once if needed, inherit existing values and refine target paths | specify desired attributes of build/test/package/Pipeline |
| Pipeline object | calculate checks from its effective enclosing Profile and retain native receiver-local cache behavior | no manual extraction, concatenation, reinsertion or cache refresh |
| internal selected-plan adapter | select the final Scenario's effective Pipeline, admit it and consume its checks projection | no separate config collector or user assembly procedure |
| validation probe | hold parent/child Pipeline/list references and inspect values/identity/counters | test-only local variables, not a public configuration protocol |

In particular, (def child-checks (.get child-pipeline checks)) in the native
probe records an observation so assertions can compare cache identity. It is
not a declaration that every user must write, not another Module API and not
the mechanism that makes inheritance current. The Pipeline's native computed
slot already supplies that mechanism. Reading/inspecting checks remains allowed;
requiring a user to assemble it just to apply an ordinary path refinement does
not satisfy this design.

Do not add a second automatic checks getter or synchronization layer on top of
this relationship. The new Module/scope/Loader adapters must preserve it as they
connect publication, source admission and final-plan consumption. Native
receiver/cache semantics have isolated execution evidence below; the common
Concrete Module publication and authenticated source integration still require implementation
and their own admission/validation. The path-syntax adapter is now implemented
separately in Core, as documented below.

* Upstream dispatch and MOP ownership under the project Coding Style

The common abstraction above must be backed by the actual dispatch laws in
[[file:44-current-project-programming-style/02-poo-dispatch-and-extension.org][Style 02 POO Dispatch And Extension]] and
[[file:44-current-project-programming-style/03-functional-kernel-and-runtime-projection.org][Style 03 Functional Kernel And Runtime Projection]]. Concise downstream paths
are only the presentation layer. The upstream owner must maintain prototype
behavior, effective-slot computation, Contracts and extensible boundary methods;
these must not be replaced by a user-side sequence of Check extractions, list
assembly and adapter calls. Check remains a real domain object, but user code
need not manipulate its implementation identity or test variables to configure it.

| Behavior | Upstream abstraction and owner | Downstream surface |
|----------+--------------------------------+--------------------|
| effective Profile -> Pipeline -> checks | native receiver-bound computed slots, with slot .defgeneric when one receiver family needs replaceable behavior | refine existing business slots by path; no list assembly |
| Check/Profile/Pipeline boundary shape | define-type, responsibilities and obligations against effective POO objects, integrated with existing admission | inherit valid defaults; diagnostics for invalid changes |
| pure dependency checking and list/plan projection | named pure functions consuming admitted final objects | no manual adapter choreography |
| authoring admission executor x source-role kind | existing CLOS generic/method bundles, not a symbol-based role switch | same native authoring abstraction for maintained and User Interface sources |
| source resolver/provider x publication-kind Contract | proposed upstream CLOS crossing where resolver kinds and prototype/Profile publication families are independently extensible | one module scope; no provider-name switch or owner import plumbing |
| runtime/plan consumer x domain object kind | upstream CLOS crossing where consumers and domain kinds independently grow; lower to existing explicit handoff | configuration only; no direct provider execution |

For each new multiple-dispatch crossing, name both independent axes, concrete
specializers and method-bundle owner before implementation. The proposed
source/publication crossing has resolver-provider families owned by the source
adapter and publication-kind families owned by Module publications; its method
bundles belong to their integration owner. Default unsupported crossings fail
closed. Use poo-clos-prototype-specializer for native POO prototypes and
poo-clos-class-specializer only for real ClosClass values. Method registration
must use admitted bundles at the existing composition boundary, preserve canonical
prototype identity, and must not create an eager global collection of every
Module's methods or evaluate all Profiles during expansion.

Do not introduce multiple dispatch merely because a getter is nested or a list
has three elements. Pipeline checks has one effective Profile receiver and needs
no new CLOS layer to satisfy this example. Native slot computation already has
the executed cache evidence; generic dispatch is for actual independently
extensible boundary axes. Existing Loader backend callbacks need not all be
replaced to comply with this design. module-owner-export is the internal adapter
boundary: it should use an admitted provider/publication crossing when that
crossing exists, while source bookkeeping and pure projection retain their
existing owners, not a central case on provider names or a second interpreter.

The current [[file:../../../modules/module-authoring/module-source-admission.ss][source-admission owner]] already defines
ModuleAuthoringAdmissionProtocol/Generic, specializes ModuleAuthoringExecutor.
and ModuleSourceRole./ConfigSourceRole., and composes ModuleAuthoringCoreMethods
with .defmethod-bundle. This is an existing structural reference, not proof that
Funflow's proposed source/publication or consumer crossings are implemented.
[[file:../../poo-clos/interface.ss][Core's POO-native CLOS/MOP facade]] supplies the extension vocabulary; its
existence is not a reason to add new Class/metaclass abstractions for a simple
Profile. MOP-backed classification/admission and native effective slots carry
object semantics; no parallel record/list model is exposed to user modules.

Upstream Maintained and User Interface module owners may publish reusable
objects through the same scope/Contract protocol. Only owners extending core
mechanisms need to maintain the relevant slot generics or boundary method
bundles. Ordinary downstream configuration remains the four path refinements
shown below, with no child-checks variables, dispatch frames, MOP metadata or
method-table management. These proposed integrations remain design-only; the
native 32-assertion probe did not test a new CLOS method bundle or Loader adapter.

* Decision: one Module binding, refine its existing Profiles

Gerbil and Rust are published native configuration Profiles of the same Funflow
Module. The user binds that Module once, then refines both inherited Profiles
under funflow.profiles. A different Module, GitHub Actions, has its own binding.
Do not make downstream users redeclare Gerbil/Rust Check objects, separate
per-language module-binding wrappers or default-and-computed source slots.
Scenario is the user configuration root. No imports/compose slot, public Case,
config wrapper or mandatory repeated task construction is introduced.

The Scenario's .def layer remains public. Native multi-parent inheritance stays
available for intentionally reused independent configuration contributions, but
is not a prerequisite for using multiple Profiles already provided by one Module.
No user source-comment/role annotation is added; visible use-module binding and
real owner provenance supply the source relationship.

* Upstream publication boundary, without manual user imports

The maintained Module owns the Check prototype and is designed to publish complete
Gerbil/Rust default objects with their contracts. It publishes them through the native module scope:
profiles exposes configuration values; prototypes.check exposes the admitted
parent object for deliberate new Check authoring. Ordinary users do not repeat
raw Check construction to use existing defaults, nor import/rename a separate
funflow-check identifier after binding the Module.

Only module-system/bootstrap implementation needs native Gerbil import internally;
Profile authors use the same bounded module scope as Scenario authors. This language mechanism
is not the user configuration model, and a bounded source-scope adapter must not
load all exports or inject naked lexical symbols. The user sees native values
from the actual admitted module binding. Detailed old constructor/import payloads
are in [[file:164-funflow-cicd-legacy-source-reference.org][the separate historical/owner reference]], not this current user recipe.

** Complete upstream Profile object (future source-owner presentation)

Upstream Profile authors and downstream Scenario authors use the same bounded
Module scope. Neither author imports config-prototypes.ss or expects an
unqualified funflow-check binding. The prototype lookup is explicitly
(.get ff prototypes check), from the admitted funflow source, and the Pipeline
prototype comes from the same scope. The low-level native prototype declarations
remain in the existing Funflow bootstrap owner; that owner alone uses ordinary
Gerbil imports to implement the module system's foundation.

The bounded body is ordinary Scheme and may return a newly authored Profile,
not only a configured Module. Source binding/prototype capability admission is
common to both routes; result admission follows the authoring context. This
upstream result must satisfy its published Profile Contract, while a downstream
funflow placement must satisfy its configured Module Contract. Do not force a
Profile to inherit a Module prototype merely to pass a generic scope-result
check. The alias and source evidence are lexical dependencies, not proof that
all returned objects have Module identity. This result-aware admission is part
of the new adapter, not today's Bundle behavior.

The compound-body grammar is now implemented for an already bound native
Funflow scope. Capability-aware source resolution and actual Funflow publication
remain proposed. The complete object below replaces the earlier direct-constructor
Profile recipe; it is not yet a complete Loader integration. Check/Pipeline native
prototypes and attributes already exist. The primitive .o/.get/def language
bindings are supplied by the authoring environment; this surface does not require
handwritten imports of Funflow implementation identifiers.

*** Core rule: preserve native outer-slot lexical binding

POO's native outer-slot lexical binding is a required authoring rule, not a new
module-system feature. build/test/package above are slot identifiers introduced
by the enclosing native .o. In the nested Pipeline body they continue to read
the effective enclosing Profile. They are not copies of already-forced parent
Check values, fields of the inner Pipeline, or unbound symbols to be injected
by use-module. Therefore checks can directly be (list build test package).

Do not replace those slot identifiers with a fixed parent list, eager def-slots
extraction, a global prototype reference, or an ad hoc lambda (self super) hook.
No manual let-bound Profile and repeated .get chain is needed for this ordinary
lexical relationship. Where a nested object deliberately declares a same-named
slot, native lexical shadowing applies; an unrelated helper must not rewrite
identifier scope or capture a same-spelled binding. Moving this code into a
helper/macro requires preserving syntax bindings or passing the effective
receiver explicitly; mere textual substitution is not equivalent.

The pinned object.ss uses %with-shared-slot-bindings and syntax parameters to
retain receiver-aware lexical slot access, including nested objects. Its native
test "nested object methods retain the outer lexical slot scope" covers outer
capture and inner shadowing. The executed 32-assertion lexical-slot probe below
also verifies parent-first caching, child refinement and sibling isolation for
this Pipeline use. The direct lexical form is canonical; the earlier explicit
receiver form remains a preserved comparison/control, not a mandatory wrapper.
Reading pipeline-name does not require forcing checks; demanding checks reads
all three selected effective Check slots. No parent mutation/backpatching occurs.

** Future Loader publication and upstream Contract responsibilities

The module itself is now explicitly defined below. There is no undefined
FunflowModule. parent supplying hidden behavior. The complete Gerbil scope has
two focused owner declarations and native computed export slots. The module
bootstrap publishes this structure without evaluating the Gerbil Profile.
These paths are source-relative owner facts, not absolute imports or a new
public module-role selector.

#+begin_src scheme
(.def FunflowOwners
  prototypes:
  (.o (:: @ PrototypePublication.)
      role: 'objects
      relative-path: "config-prototypes.ss"
      exports: '(funflow-check funflow-pipeline))

  gerbil-scheme:
  (.o (:: @ ProfilePublication.)
      role: 'config
      relative-path: "profiles/gerbil-scheme.ss"
      exports: '(GerbilSchemeCIProfile)))

(.def (FunflowModule. @ [])
  source: #f
  owners: FunflowOwners

  prototypes:
  (.o check:
      (module-owner-export source (.get owners prototypes) 'funflow-check)
      pipeline:
      (module-owner-export source (.get owners prototypes) 'funflow-pipeline))

  profiles:
  (.o gerbil-scheme:
      (module-owner-export
        source (.get owners gerbil-scheme) 'GerbilSchemeCIProfile))

  contracts:
  (.o gerbil-scheme:
      (funflow-profile-contract
        (.get prototypes check)
        (.get prototypes pipeline)
        (.get profiles gerbil-scheme))))

;; Internal binding design, not a public constructor requirement.
(def (funflow-scope admitted-source)
  (.o (:: @ FunflowModule.)
    source: admitted-source))
#+end_src

The existing config-prototypes.ss is the native Check/Pipeline owner; the new
profiles/gerbil-scheme.ss would contain the complete scoped Profile definition
above. role objects/config states existing ownership roles; it does not rename
these focused files into mandatory objects.ss/config.ss shell entrypoints or
introduce a public profiles role. Source-to-owner resolution needs an admitted
bridge compatible with the existing shell/authoring rules.

The old FunflowCICDDefaults wrapper that directly referenced an already-bound
GerbilSchemeCIProfile is superseded: publication is now the lazy
profiles.gerbil-scheme getter on the fully defined FunflowModule. Native catalog
extension can still refine profiles with =>.+; no second registry is introduced.
The source descriptor binds funflow to this lightweight scope construction
protocol and its inert owner metadata, not to a module that eagerly imports
profiles/gerbil-scheme.ss. FunflowModule.'s own declaration dependencies must
contain only bootstrap/language facilities and its owner declarations.

source is an abstract required slot, not a writable string proving origin.
funflow-scope must receive a validated source handle from the binding adapter.
Admission rechecks that handle and the expected Module/source relationship;
copying a same-shaped object or overriding owners to a different source cannot
manufacture provenance. ff is local naming, not source authentication. The
native source field and owners are configuration values; authority remains with
the actual admitted source owner and its publication policy.

The source/owner export crossing and Contract factory are expanded as concrete
native declarations in [[file:164-funflow-contract-and-dispatch-design.org][the Contract and Generic method-bundle design]]. Its publication
prototypes are defined before FunflowOwners; its functions accept native values
rather than import the complete Profile during bootstrap. Prototype-specializer
declarations, Generic protocol clauses and deferred method-bundle declarations
are now implemented in Core's working tree. The actual source/Loader adapters
still require implementation. Upstream authoring uses .defgeneric/.defmethod and a private defrules frame; low-level specializer
lists/lambdas are retained only as expansion references, not the normal recipe. source/owners/prototypes/profiles in the nested views are native enclosing Module slot identifiers, just as build/test/package
are enclosing Profile slot identifiers in Pipeline.

contracts.gerbil-scheme is demanded only for selected Profile admission, after
that Profile value exists. It constructs a descriptor against the actual
admitted Check/Pipeline/Profile ancestry; it is not a parent of those values.
The upstream Profile body reads prototypes only and never contracts/profiles,
so Contract construction does not participate in Profile initialization reentry.
Creating the scope does not force this contract getter or admit every Profile.

** Exact module-owner-export boundary and Loader integration

module-owner-export is a proposed internal function, not an existing Core API:

#+begin_src scheme
;; Contract illustration only; no function implementation is supplied here.
;; (module-owner-export admitted-source owner export-name)
;;   -> admitted native export value, or typed load/admission failure
#+end_src

| Stage | Required behavior and existing boundary |
|-------+-----------------------------------------|
| validate request | verify handle/source revision/currentness, publication membership, supported role, export allowlist and ownership; strings/alias labels alone are insufficient |
| locate focused owner | resolve relative-path inside the admitted source root, reject traversal/escape and wrong-source substitutions; retain the owning Module identity alongside the focused owner reference |
| construct demand | use existing source-ref and make-lazy-load-plan data; retain a precise owner demand rather than replace it with the coarse import-all interface |
| guard reentry | record canonical source/revision + owner/capability and current demand path before entering resolution/evaluation; reject a repeated active dependency with its path |
| force when needed | delegate to existing force-lazy-load-plan / load-source-receipt backend ordering; absent backend or failed owner remains a typed failure |
| obtain export | through a product-owned descriptor/activation bridge, obtain the named native value and validate export shape/ancestry/provenance; a Core load receipt alone does not evaluate a Gerbil file or retrieve its export |
| complete | preserve actual load/source evidence, return the admitted value, and release active state on success/failure/cancellation according to owner lifecycle rules |

The precise source-ref mapping and descriptor/activation bridge are new
adaptation; the current static backend only returns already-built descriptors.
Do not claim it is already a per-file evaluator or bypass public role validation
to load arbitrary internal paths. The existing product activation boundary must
be extended/reused under source policy rather than introducing another evaluator,
Loader, registry or cache. Low-level bootstrap imports remain implementation
bindings, not an authoring task for Profile/Scenario users.

Core source-ref equality currently uses kind plus value, not version metadata.
Scope reuse/cycle admission must therefore carry and validate the actual admitted
revision/owner context; merely putting a version in metadata does not change
existing equality. Repeated force is not automatic once-only initialization.
Reuse, concurrent requests, failures and currentness must be integrated with
existing owners and produce distinct loading/admission evidence as appropriate.

The two prototype exports share one physical owner today. Demanding check can
load the native declarations for both check and pipeline in that owner. It must
not load Gerbil/Rust Profiles or runtime implementations. Further splitting this
owner is an optional measured optimization, not an existing per-export loading
guarantee. Constructing prototypes/profiles view objects does not read their
export getters; mandatory selected admission may demand the required getters.

When evaluating the Gerbil Profile owner, its use-module funflow as ff is resolved
against that owner's admitted source context. It must not select a same-named
Module from a newly shadowing global load path. It creates/obtains the same
source's lightweight scope protocol, without demanding its Profile catalog.
Source identity can be reused while lexical occurrence identities remain distinct;
this is not a promise of one global mutable Module singleton.

| Upstream responsibility | Required design / admission |
|-------------------------+-----------------------------|
| Module scope | real admitted source/revision, compatible Funflow base and prototype exports; no source identity inferred from alias ff |
| profiles.gerbil-scheme | native reusable Profile with named build/test/package and pipeline; applicable domain Contract associated by the publication owner |
| build/test/package | native Check classification, required business fields and existing attribute admission; unchanged baseline slots inherited from funflow-check |
| pipeline | native Pipeline classification; checks is the ordered list of the effective selected Check objects, metadata retains the original pair values |
| dependencies | build -> test -> package dependency closure, unique selected qualified identities, no missing or cyclic local references |
| profile-ref | resolve ci/build and ci/check through admitted Scenario/Profile bindings; these are original binding references, not a claim of literal catalog paths |
| compensation | cleanup/package-artifacts must resolve to an admitted supported compensation owner before runnable admission; naming it alone does not supply that implementation |
| durable-task-id | preserve the original configured task keys; qualify occurrences for composition, and keep runtime Session/attempt identity separate |
| Scenario selection | upstream CICDScenario selects this Profile and its pipeline; catalog availability alone is not execution selection |

These are concrete responsibilities for the proposed Profile/publication and
Scenario adapters. They are not already guaranteed by native ancestry or the
current generic composition Contract. This document does not invent a successful
cleanup implementation, missing profile binding or runtime receipt to make the
example pass. Unresolved required references reject runnable admission.

force-lazy-load-plan is functional: it leaves the deferred input intact. It does
not implement a shared once-only cache or a loading-state machine. Repeated
force calls must not be advertised as automatically deduplicated. Scope demand
must integrate any valid owner reuse with existing source/currentness rules,
without creating a competing Loader, global registry or cache.

Current shell validation also expects interface import/re-export relationships
for public role files. Loading an interface with an eager transitive import
closure may therefore load more than the requested prototype owner. The new
bridge needs a reviewed metadata/publication boundary and compatibility with
those shell rules; it cannot bypass validation, quietly change interface
semantics, or claim that wrapping the existing import-all path makes it lazy.
Internal focused owner files may live under existing roles. Bootstrap retains
normal precise Gerbil dependencies; Profile/Scenario authors use module scope.

** Non-circular publication and demand graph

The following are owner/capability dependencies, not a new public module tree:

#+begin_example
funflow source/interface metadata (no Profile evaluation)
  -> lightweight native Module scope
       prototypes.check / prototypes.pipeline
         -> existing focused native prototype owner
       profiles.gerbil-scheme
         -> focused Gerbil Profile owner
              -> use-module funflow as ff
                   -> same admitted source's prototypes capability only
              -> complete GerbilSchemeCIProfile value
       execution capability
         -> selected runtime owner, at explicit Session/handoff only
#+end_example

The bootstrap scope/descriptor must be independently available before any
Profile is evaluated. Reentering the same Module identity for an independent
ready prototype capability is allowed; re-demanding an active Profile or a
bootstrap owner that depends on that Profile is a cycle. Thus banning every
same-Module request would reject valid authoring, while allowing all same-Module
requests would hide a recursion bug.

The proposed resolver records active demand by canonical admitted
source/revision + capability/owner identity, not alias or user-supplied label.
It checks the owner dependency path, including cross-Module edges. If resolving
profiles.gerbil-scheme requires that active Profile again, reject with a typed
cycle diagnostic containing the owner path before calling its evaluator again.

*** Why it works and what has actually been verified

In the pinned object.ss, apply-slot-spec binds slot methods to the effective
self; .ref consults and fills that object's own instance cache. Deriving a new
Profile through nested =>.+ does not copy the parent's cached Pipeline into the
child. The inherited Pipeline getter runs against the child Profile, creates a separate
Pipeline, and its native outer-slot bindings preserve that effective receiver.
The earlier explicit-receiver variant records it in a let-bound profile; the
canonical lexical variant directly refers to build/test/package.
Each Pipeline's checks is then cached on that Pipeline object. The parent's
cached Pipeline/list remains unchanged. This is functional derivation of new
objects, not a claim that mutating a cached parent invalidates dependencies.

smoke-tests.ss is a project-owned illustration, not an asserted existing file.
The proposed named-task adapter derives its local identity from the smoke slot
and resolves Profile/durable occurrence context before qualified legacy
projection. It does not infer identity from Scheme variable spelling or mutate
a shared proto. The scope owner must provide valid result/runtime defaults;
today's raw funflow-check does not already make the shortened object valid.
The selected Profile task Contract enumerates admitted named task entries,
including smoke, rather than hard-coding build or treating metadata as tasks.

same-named variable. Pinned POO source/tests establish native slot scope and

Those require separate implementation qualification, including same-named Module
slots, outer aliases, sibling scope non-leakage and deliberate nested shadowing.

* Critically borrowing from Doom without copying its behavior

The [[https://github.com/doomemacs/core/blob/master/docs/getting_started.org][Doom configuration guide]] separates module selection, package declarations,
configuration and delayed package use. Its use-package! can still load eagerly
without appropriate triggers; private same-named modules can replace built-ins.
The [[https://github.com/doomemacs/core/blob/master/lisp/doom.el][core module search-path definition]] records ordered lookup roots. These are
comparison facts, not our defaults, a shared Scenario object model or proof of
natural laziness. Reading consulted on 2026-10-15.

Our inference is to keep origin resolution, acquisition, configuration and
execution separate. Do not copy delay flags users must remember, silent source
replacement without provenance/admission, or eager package initialization hidden
inside a convenient wrapper. Default request/scope construction stays light;
actual dependencies and selected obligations define demand. User-owned overrides
are supported under an explicit deterministic source policy that records the
resolved origin and overridden base. No new source category syntax is mandated.

* Existing native slot shapes; no default-slot workaround

#+begin_src scheme
;; Initial source binding.
(.def BindingExample
  funflow: (use-module funflow))

;; Refine an existing bound value.
(.def (RefinementExample @ BindingExample)
  funflow: =>.+ {profiles: =>.+ {}})

;; Bind and immediately extend with an ordinary native expression.
(.def BindAndExtendExample
  funflow: (.+ (use-module funflow)
               (.o profiles: =>.+ (.o))))
#+end_src

The source expression cannot simply be followed by a stray =>.+ token. That
operator accepts an overriding object, whose named slots may refine multiple
Profiles. It is not a new arbitrary-arity Profile composition syntax.
Native ? remains a valid lower-precedence default-value facility, but is not
needed for this ordinary route and is not a lazy-loading guard. Repeated per-
language ? bindings and mandatory Profile-to-Scenario inheritance are superseded.

Existing [[file:../../types.ss][Core responsibilities]] admit effective candidate slots and then
obligations. The named domain Contracts/collection admission and Scenario
selection connection are proposed. Users do not repeat responsibilities or raw
funflow-check ancestry at every override. Existing ancestry alone does not prove
source provenance, changed configuration admissibility or runtime support.

Binding one Module once avoids redundant local source requests; it does not
remove conflict handling when a user intentionally inherits multiple configured
parents or replaces a Module. Retain and compare selected source requests and
publication origins, not merely the highest-priority effective metadata slot.
Reject incompatible source/revision/proto/capability combinations unless an
explicit admitted replacement policy resolves them. Native precedence is not a
source compatibility check. Source evidence belongs to the existing owner, not
a user-authored string field. Do not add a second registry, loader or cache.

* Natural laziness, phase boundaries and first-demand cost

| Operation | Default demand | Work not implied |
|-----------+----------------+------------------|
| expand bounded binding syntax | parse once, preserve syntax/source context, emit native let/POO | source IO/loading, installs or runtime registration during expansion |
| evaluate Scenario module-binding slot | bounded source metadata/request and lightweight native scope; evaluate the configuration expression once | whole implementation/catalog initialization |
| access existing Profile attribute | that native value and necessary inherited dependencies | activate all published Profiles or project a whole plan |
| construct/admit smoke | required prototypes.check owner and selected task context/obligations | unrelated prototypes, other modules or build execution |
| request selected Scenario plan | all participating qualified tasks and mandatory graph/source/runtime facts | unused catalog entries or unrelated scenarios |
| explicit Session/handoff | needed admitted implementation/current permissions and receipts | unselected assets |

The syntax has no opt-in defer requirement. Scope creation, interface metadata,
prototype lookup, domain admission, pure plan projection and runtime execution
are distinct demands. Use existing [[file:../loader/objects.ss][Loader deferred plans]] behind a valid native
scope object; a raw plan is not automatically a .+ base. POO operators can demand
parents and construct bounded objects; no guarantee of zero computation is made.

Natural laziness also requires bounded work on first access. A getter must not
force a monolithic implementation or enumerate the full registry just to return
one task field. Split precise source/prototype/config owners, reuse stable
admitted references through existing owner mechanisms, and do required build-
time indexing/compilation only at explicit preparation boundaries. Never move
those expensive operations into expansion or scope construction. Do not invent
a duplicate scheduler/cache, silently auto-install dependencies, or manufacture
admission evidence to avoid latency.

Static Gerbil imports still load their own dependency closure. Precise owner
interfaces are necessary for this protocol; a thin scope wrapper around an eager
import-all module is not compliance. The body is ordinary Scheme: generated
binding paths and owned configuration are pure by default, while explicitly
demanded operations or user effects cannot be advertised as magically lazy.
Mandatory selected admission is allowed to force all required facts and should
report missing dependencies at the earliest boundary supported by already
available metadata, rather than hiding an invalid selection until execution.

A delayed bill is not an optimization receipt. Future qualification must measure
scope creation, first metadata/Profile read, first prototype construction,
selected admission/plan projection and warm repeat separately, including loaded
owners, allocations/memory and unrelated-source counts. Compare equal effective
configuration and evidence under the existing performance policy. Cold/warm
latency budgets remain to be established; this design makes no numerical speed
claim. It must show work eliminated or bounded, not merely shifted from startup.

Parent-first forcing must not leave a derived Scenario with stale selected
values, plans or evidence. Provenance/currentness stays with existing owners.
Pure lookup, admission and projection do not run a command or Session. No
user-visible deferred flag or optional loader bypass is needed for correctness.

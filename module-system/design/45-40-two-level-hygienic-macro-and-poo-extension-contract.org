#+title: Two-Level Hygienic Macro and POO Extension Contract
#+status: Accepted
#+language: en

* Decision

Every public Profile and module family follows one project-wide interface law:

- ordinary users may use a bounded, domain-specific hygienic macro surface;
- advanced authors use runtime =gerbil-poo= objects, prototypes and operations;
- all macro surfaces expand completely to the same POO semantic core.

POO object and prototype syntax is the sole advanced semantic extension
interface.

No domain macro may create a second runtime language, extension registry,
provider protocol, compatibility layer or macro-family-specific object model.

* One semantic core, two presentation levels

#+begin_src mermaid
flowchart TD
  U["Ordinary user concepts"] -->|"expressed through a bounded domain macro"| M["Hygienic macro surface"]
  M -->|"fully expands at compile time"| P["Runtime gerbil-poo objects and prototypes"]
  A["Advanced extension author"] -->|"uses the sole semantic extension interface directly"| P
  P -->|"owns composition, fixed points, contracts and reflection"| S["Single module semantics"]
  S -->|"produces unified identity, evidence and receipts"| E["Inspectable system object"]
#+end_src

The macro surface reduces cognitive load.  It does not reduce, replace or
reinterpret POO semantics.

* Ordinary user surface

Domain macros name stable user concepts:

#+begin_src scheme
(observability-profile production-observability
  (visibility operator)
  (retention 30-days)
  (redaction causal))
#+end_src

This form illustrates the cognitive shape only.  The project chooses its exact
surface grammar from Gerbil and Agentic AI Lab requirements rather than copying the
syntax of a reference system.

The resulting Profile is consumed as one named object:

#+begin_src scheme
(user-composition my-system
  (compose profiles
    wendao-episteme
    production
    production-observability))
#+end_src

The consumer does not need to understand internal prototype lineage,
slot-contract composition, retention bounds or redaction attenuation merely to
select the Profile.

* Advanced extension surface

Advanced authors use the runtime =gerbil-poo= surface, including:

#+begin_example
.o
.def
.mix
=>
=>.+
?
.ref
.get
.@
.call
runtime reflection
runtime lifecycle operations at explicit effect boundaries
#+end_example

Advanced extension MUST NOT require:

#+begin_example
register-profile-extension
define-custom-clause
profile-provider
raw-extension-hook
runtime-policy-token
compatibility adapter
#+end_example

An advanced author defines an ordinary POO object and exposes one stable
Profile binding.

* Complete expansion law

A public domain macro must disappear completely into POO during Gerbil
macro expansion.

#+begin_src mermaid
flowchart LR
  S["Domain macro form"] -->|"hygienic compile-time expansion"| N["POO definition"]
  N -->|"runtime receives only ordinary POO objects"| R["POO evaluation"]
  S -->|"must not leave clause tags, tokens or registries"| X["No second runtime"]
#+end_src

Macros may call other hygienic macros.  The transitive expansion endpoint must
still consist of POO definitions, composition and access.

Runtime code MUST NOT interpret the source macro clauses.

* Canonical equivalence law

A macro-produced Profile and a handwritten Profile with the same canonical
expanded POO definition have the same semantics.

They share:

- prototype lineage;
- slot-contract behavior;
- priority and authority decisions;
- fixed-point behavior;
- runtime reflection;
- semantic identity;
- evidence and receipt shape;
- incremental reuse eligibility.

The runtime cannot branch on whether the object originated from a domain macro
or handwritten =.def= and =.mix= forms.

* Bounded macro law

Each domain macro covers a deliberately bounded set of stable ordinary-user
concepts.

It MUST NOT grow catch-all clauses such as:

#+begin_src scheme
(extension ...)
(raw ...)
(custom-handler ...)
(plugin ...)
#+end_src

When a requirement exceeds the macro's standard concepts, the author defines a
POO object and composes its binding:

#+begin_src scheme
(def advanced-policy
  (.mix
    specialized-prototype
    standard-policy))

(user-composition my-system
  (compose profiles
    production
    advanced-policy))
#+end_src

The macro is not required to expose every possible POO abstraction.

* POO-value law

Macro clauses have one stable value position that supports both ordinary and
advanced users.

An ordinary bounded shorthand:

#+begin_src scheme
(observability-profile production-observability
  (retention 30-days)
  (redaction causal))
#+end_src

is hygienically lifted at expansion time into standard POO policy objects.

An advanced value:

#+begin_src scheme
(observability-profile production-observability
  (retention specialized-retention)
  (redaction specialized-redaction))
#+end_src

uses POO objects created by the author.  The same public macro and clause
shape applies at both levels.

Every supported shorthand has a bounded hygienic lowering.  The interface MUST
NOT become an open runtime token table, arbitrary alist or dynamically
registered enum system.  After expansion, every clause is represented by a
POO object and governed by the same slot contracts.

* Hygienic binding law

Macro clauses, slots and Profile identities use Gerbil hygienic bindings.

- No string-path dispatch.
- No runtime symbol registry.
- No collision with industry-object slots.
- Binding origin and phase participate in definition identity.
- Local generated bindings are alpha-normalized.
- Source clauses retain provenance to their expanded runtime slots.

Equal printed identifiers with different binding origins remain different
semantic identities.

* Explainable expansion law

The system preserves the causal relation from a user-facing macro clause to its
expanded POO definition.

#+begin_src mermaid
flowchart LR
  C["User macro clause"] -->|"source and phase provenance"| S["Expanded POO slot"]
  S -->|"definition identity participates in demand"| D["Slot result"]
  D -->|"change propagates through actual dependency edges"| R["Successor receipt"]
  R -->|"projects the causal chain back to the user concept"| X["User-facing explanation"]
#+end_src

An explanation may state:

#+begin_example
retention clause changed
-> runtime retention policy slot changed
-> observability-policy receipt changed
-> canonical business receipt remained unchanged
#+end_example

It must not expose only expander gensym names or raw hashes.

* No macro-family runtime type law

Domain macros do not create runtime types such as:

#+begin_example
observability-profile-runtime-object
governance-profile-runtime-object
deployment-profile-runtime-object
#+end_example

Every result is an ordinary POO object.  Domain capability is expressed
through POO prototype lineage, slots and contracts.

#+begin_src mermaid
flowchart TD
  O["Observability domain macro"] -->|"expands to an ordinary POO Profile"| C["compose profiles"]
  D["Another bounded domain macro"] -->|"expands to an ordinary POO Profile"| C
  H["Handwritten POO definition"] -->|"already is an ordinary POO Profile"| C
  C -->|"uses one contract and fixed-point semantics"| S["Unified system object"]
#+end_src

Macro-generated and handwritten objects therefore interoperate without
adapters.

* Composition macro law

=user-composition= and =compose profiles= are themselves ordinary-user macro
surfaces.

They must:

- expand to POO Profile composition;
- preserve the declared Profile identities;
- use the POO contract and precedence semantics;
- avoid a separate merge evaluator;
- avoid nested duplicate composition syntax;
- retain expansion provenance for reflection and explanation.

=compose profiles= is the user-facing description of system composition.  It
does not replace runtime prototype construction used inside a Profile.

#+begin_example
user-composition
`-- compose profiles
    |-- domain-macro-generated Profile
    |-- domain-macro-generated Profile
    `-- handwritten POO Profile
        `-- one POO semantic graph
#+end_example

* Domain-specific naming law

Macro names identify their stable domain rather than claiming to be another
language.

Prefer names shaped like:

#+begin_example
observability-profile
governance-profile
deployment-profile
#+end_example

Avoid vague names such as:

#+begin_example
language
custom-profile
extension-language
#+end_example

A macro is a comprehensible entry into one domain of the POO module system.  It
is not a new language namespace.

* Design-reference learning law

Mature Lisp configuration systems, including Emacs and Doom Emacs, are design
and implementation references rather than syntax templates.

Agentic AI Lab learns:

- one concise declaration can hide substantial internal machinery;
- a small stable vocabulary improves discoverability;
- simple values and advanced Lisp expressions can share one value position;
- compile-time macro validation produces better feedback than runtime token
  dispatch;
- source-aware expansion can explain errors in the user's vocabulary;
- advanced users should not be trapped by the simplified interface.

Agentic AI Lab does not copy:

- macro names, bang suffixes or keyword punctuation;
- foreign package-management ownership;
- foreign initialization and configuration phases;
- mutable global configuration semantics;
- side-effectful configuration bodies;
- compatibility behavior or runtime interpreters from the reference system.

The learned properties are reconstructed through Gerbil hygienic macros,
POO objects, pure fixed-point composition, semantic evidence and
explicit realization boundaries.

* Compile-time validation law

A bounded domain macro SHOULD reject at expansion time:

- unknown clause names;
- duplicate clauses;
- malformed clause shape;
- unresolved required hygienic bindings;
- nested duplicate =compose= or =user-composition=;
- source forms that request runtime registration;
- clauses that syntactically perform external effects.

Compile-time validation concerns syntax and binding shape.  POO
slot-contract objects still own semantic validation.

* Advanced-dimension law

When an author introduces a new domain dimension:

1. define its POO contract object;
2. define the relevant runtime slot or nested object;
3. compose it with =.def=, =.mix=, ==>=, ==>.+= or another runtime operation;
4. expose a named Profile;
5. retain canonical definition and explanation evidence.

There is no runtime macro-clause registration step.

A standard domain macro may later add a hygienically bound clause after the
dimension becomes a stable ordinary-user concept.  That change adds
convenience, not semantics.

* Phase and identity law

Every macro participates in the phase-aware definition-identity model.

- Transformer changes invalidate expansion execution identity.
- Fresh expansion may preserve POO semantic identity.
- Runtime binding changes invalidate affected expanded slots.
- Opaque compile-time dependencies fail closed for cross-process reuse.
- Handwritten and macro-generated canonical definitions share one identity
  model.

The macro name itself is not a substitute for expanded definition identity.

* New-architecture boundary

This is a new architecture.  The public interface selects one canonical macro
form for each ordinary domain and one POO extension surface.

The design does not require:

- compatibility aliases for rejected interface forms;
- migration wrappers around nested or redundant composition;
- deprecation stages for runtime DSLs that were never accepted;
- fallback dispatch to old alist or provider representations.

Incorrect experimental forms are removed from the RFC rather than preserved as
legacy architecture.

* Conformance evidence

A domain macro family is conformant only when evidence demonstrates:

- its complete expansion terminates in POO forms;
- a handwritten canonical equivalent has the same semantic identity;
- macro-generated and handwritten Profiles compose together;
- reflection sees the same runtime object structure;
- unknown and duplicate clauses fail during expansion;
- no runtime clause interpreter or registry is present;
- invalidation explanations map runtime deltas back to user clauses;
- external effects remain behind explicit runtime boundaries.

* Required failure conditions

The interface MUST fail closed when:

- a macro leaves a runtime clause representation;
- macro origin changes Profile semantics;
- a domain macro introduces a custom runtime object model;
- an unbounded raw value bypasses hygienic lifting or POO contract validation;
- a catch-all escape clause becomes a parallel advanced interface;
- string or token dispatch replaces hygienic binding;
- =compose profiles= uses a non-POO merge evaluator;
- expansion provenance is unavailable for invalidation explanation;
- a rejected experimental form is retained as a compatibility layer;
- an external effect occurs during macro expansion or pure composition.

* Acceptance checklist

- [X] Every public module family follows one two-level interface law.
- [X] Ordinary users may use bounded domain-specific hygienic macros.
- [X] POO is the sole advanced semantic extension interface.
- [X] All macro expansion terminates in POO forms.
- [X] Macro and handwritten canonical definitions are semantically equivalent.
- [X] Catch-all escape clauses and runtime extension registries are forbidden.
- [X] Macro clauses accept bounded ordinary shorthand and advanced POO values,
  lowering both to POO objects.
- [X] Hygienic bindings replace string and token dispatch.
- [X] Expansion provenance supports causal invalidation explanation.
- [X] Domain macros create no macro-family-specific runtime object type.
- [X] =user-composition= and =compose profiles= use the same POO core.
- [X] New advanced dimensions are introduced through POO.
- [X] The new architecture carries no compatibility or deprecation burden for
  rejected experimental forms.
- [ ] Validate the contract with executable expansion-termination,
  handwritten-equivalence, mixed-origin composition, reflection, clause-error,
  phase-identity, causal-explanation and no-runtime-registry scenarios before
  implementation begins.

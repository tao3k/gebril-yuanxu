* 10.06.17 Unified Graph Operations
** 10.06.17.10 Decision
=core/graph/= owns the single topology representation and structural algorithms.
Module schemas and source selection project into ordinary =graph-node= and
=graph-edge= values. There is no separate extension-node type or resolver tree.

=yuanxu-graph-rooted= assembles a containment graph with path IDs and
=contains= edges. Payloads remain caller-owned. A rooted child is a view of the
same standard graph facts, not a second node representation. Shared graph
reachability selects contained facts; replacement removes the entire old subtree.
Path IDs distinguish equal local names in different branches. A contribution
may select an exact path; a scalar identity selects matching local roots, with
a matching ancestor owning its whole subtree.

** 10.06.17.20 POO operations and ordering
=core/graph/operation.ss= owns native POO operation prototypes. Each receiver
owns its application and batching methods. Scalar override, distinct list
append/prepend, list removal, child merge and subtree removal are explicit
operations consumed by =core/graph/apply.ss=; ordinary configuration continues
to use native POO inheritance and slot algebra.

Contributions execute exactly once, in declaration order. Only adjacent local
operations with the same target may coalesce. Structural changes preserve their
contribution boundaries so a later contribution can target a newly inserted node.
Batching child extensions must preserve inherited payload and descendants.

** 10.06.17.30 Receipt boundary
=yuanxu-graph-resolve= returns =root=, =changed-passes= (0 or 1), and =applied?=.
Completion of one pass does not establish convergence. For example, a contribution
targeting an absent child followed by insertion leaves that child unchanged in the
first pass; replay can change it. No fixed-point loop or general idempotence law
is implemented or claimed.

** 10.06.17.40 Executable correspondence
=core/t/graph-operations-test.ss= checks standard graph/node identity, shared
reachability, path selection, subtree deletion, inherited child merge and the
non-convergent one-pass example. Module schema/source and consumer suites check
the direct migration; no forwarding imports or legacy API aliases remain.

=core/dev/proofs/quint/GraphOperations.qnt= models a bounded ordered program over
standard nodes, edges and payloads. Independent expected fixtures check order,
path isolation, delete closure, insertion followed by targeting, and honest
single-pass receipts. Five matched mutants must violate their named invariant.
These finite checks do not establish arbitrary-size correctness or prove that
Scheme refines the model. Native tests remain an independent gate.

** 10.06.17.50 POO Shared Objects
NixOS is useful as an interface reference because many modules can contribute
to one final =config= graph. Its =options= layer is also partly a workaround
for a DSL without native Scheme objects, contracts, and POO inheritance.

=agentic-ai-lab= should keep the good part and avoid copying the hack:
- modules export shared POO module objects, not ad-hoc option alists;
- module objects carry identity, inherited objects, field contracts, and
  metadata;
- field contracts are object-internal slot contracts: slot identity, value
  kind, merge strategy, default value, and metadata;
- explicit graph contributions are small POO objects that target a module
  object and carry a field contract plus a value;
- =yuanxu-module-field-contributions-resolve= projects those explicit
  contributions to extension operations. Ordinary inherited configuration
  follows native POO prototypes instead of this graph resolver.

The user-facing shape is native POO composition. Multiple modules can extend
prototypes without a second configuration evaluator; targeted graph operations
remain an explicit mechanism for changes that inheritance cannot express.

Explicit object-graph contribution example:
#+begin_src scheme
(def shared-sandbox
  (yuanxu-module-object
   'sandbox/shared
   '()
   (list
    (yuanxu-module-field-contract
     'backend 'Symbol 'override 'sandbox '())
    (yuanxu-module-field-contract
     'runtime-args 'List 'append '() '()))
   '((domain . sandbox))))

(def nono-sandbox
  (yuanxu-module-object
   'sandbox/nono
   (list shared-sandbox)
   (list
    (yuanxu-module-field-contract
     'backend 'Symbol 'override 'nono '()))
   '((backend . nono))))

(yuanxu-module-field-contributions-resolve
 root-node
 (yuanxu-module-object-contributions
  nono-sandbox
  '((runtime-args . ("--trace-nono")))))
#+end_src

The shared namespace contains reusable module objects, and each object owns
its slot contracts. Nono, CubeSandbox, workflow pipelines, cacheable tasks,
and similar domains should extend POO objects instead of duplicating option
maps or invoking the graph resolver for ordinary configuration.

** 10.06.17.60 Objects File Layout
Module files use a Doom/NixOS-like shape, but the meaning is POO-native:
- =config.ss= declares module activation and user-facing module rows;
- =objects.ss= declares reusable POO module objects for that namespace;
- top-level =modules/objects.ss= owns =objects.shared.*=;
- module-local object files own =objects.<module>.*=;
- all object files contribute to the final =objects= attribute graph.

Concrete sandbox shape:
#+begin_src text
modules/objects.ss
  objects.shared.sandbox

modules/nono-sandbox/objects.ss
  objects.nono-sandbox.sandbox inherits objects.shared.sandbox

modules/cubeSandbox/objects.ss
  objects.cubeSandbox.sandbox inherits objects.shared.sandbox
#+end_src

Directory placement is only authoring organization. The merge key is the object
identity under the =objects= attribute. Any module can contribute an object, and
any object can inherit another object as long as its stable identity is known.

** 10.06.17.70 Loader Tree Projection
=modules/loader.ss= is the bridge from file-tree authoring to module-system data.
It supports two related layouts.

Upstream module roots use the compact module layout:
- =<module-root>/config.ss= for activation and module rows;
- =<module-root>/objects.ss= for POO object prototypes and object contributions.

User roots use the profile layout:
- =init.ss= for the Doom-style enabled-module declaration;
- =objects.ss= for user-owned shared POO objects;
- =config.ss= for the tool-facing user facade;
- =modules/config.ss= for user-facing configuration macros and helpers.

User-facing object contracts live in =objects.ss=. That file is intentionally
narrow: only POO module objects, field contracts, object inheritance, and object
extension belong there. Sandbox profile recipes and other non-object config
belong in =config.ss= or another role-specific entrypoint, not =objects.ss=.
A separate =modules/types.ss= layer would duplicate the same responsibility and
should not be part of the user-root contract.

The loader attaches role policies to each user-root entrypoint. =init.ss= is
=init-switches-only=: it may select a profile and toggle modules/features, but
it may not define objects, sandbox profile recipes, settings, package sync,
descriptor realization, or runtime execution. Those responsibilities belong to
=objects.ss=, =config.ss=, or upstream implementation owners.

The loader still does not evaluate files or activate modules. It emits source
refs and lazy load plans, so core code and user projects can share tree
contracts while preserving the existing resolver boundary.

** 10.06.17.80 Auto Import Graph
Directory entrypoints can be projected into an =auto-imports= POO graph:
- each =config.ss=, =objects.ss=, or helper entrypoint is a child node;
- the child identity is the stable source-ref value;
- node slots keep the source ref, entrypoint role, tree kind, and enabled flag;
- =module-system.ss= can stay small by reexporting loader/graph APIs instead
  of naming every concrete module object file.

Disabling an automatically discovered entrypoint is also POO-native:
#+begin_src scheme
(yuanxu-graph-contribution
 'auto-imports
 (list
  (yuanxu-graph-node-remove
   "user-interface/custom/my-module/config.ss")))
#+end_src

This keeps discovery, enablement, and removal in the same extension model.
Gerbil compile-time imports remain explicit at build boundaries, but module
selection and user-facing auto imports are data driven through loader source
refs and POO graph edits.

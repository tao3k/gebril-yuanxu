defaults, separate Contract objects with responsibilities and obligations, and
the projection consumed by planning. Downstream inherits values and refines
declared attributes. A Contract validates a value; the value does not inherit
from its Contract. No options declaration language, imports language, or new
configuration macro is introduced.

* What is learned from Nickel and NixOS

For the complete documented dmerge operation inventory, small-function definitions
and shared/Funflow/user scope publication, see
[[file:164-funflow-public-configuration/29-functions-and-overlay-use-cases.org][29 Functions and overlay use cases]]. It separates native function application
from proposed library exports, final admission/preview and Loader work.

The primary product comparison is the actual Omnibus NCL CI/matrix and sandbox
libraries and HiveBus host/POP consumers, not language feature lists alone.
[[file:164-funflow-public-configuration/09-consolidation-and-ecosystem-gaps.org][Module 09]] connects their concrete authoring/output paths to this design;
the linked comparison modules retain full source extractions. Language manuals
below explain mechanisms, not evidence of delivered ecosystem behavior.

Nickel separates reusable record contracts from configurations and integrates
field documentation, contracts and defaults into its merge model. NixOS options
give maintainers a discoverable declaration of types, defaults and descriptions.
We adopt the separation of authority and the discoverability, while retaining
POO inheritance semantics. We do not claim that POO composition is Nickel's
commutative merge or NixOS's typed definition merge.

References: [[https://nickel-lang.org/user-manual/types-vs-contracts/][Nickel types and contracts]],
[[https://nickel-lang.org/user-manual/merging/][Nickel merging and field metadata]], and
[[https://nixos.org/manual/nixos/stable/#sec-writing-modules][NixOS module/option declarations]].

Defaults have one executable owner: the value prototype/Profile. Contract field
metadata describes them through that owner; it must not embed a second default
that can drift. Describing a field is different from forcing its getter. A
static documented default and an effective computed default must be labelled
differently in any future inspection UI.

* Scope of the redesign

Ordinary values use direct assignment; inherited-value transformations use native
refinement. [[file:164-funflow-public-configuration/11-direct-path-assignment-and-refinement.org][Module 11]] specifies the proposed dotted-assignment lowering and
its shared-prefix/ambiguity rules. Current dotted syntax only accepts =>.+;
do not describe the new direct path forms as implemented or executed.

That module also owns the user-intent disclosure rule: ordinary replacement,
deep-field assignment, transformation of an old value, new-object construction
and core protocol extension expose progressively the native mechanisms needed
for the task. [[file:164-funflow-public-configuration/10-discovery-conflicts-and-plan-preview.org][Field discovery]] must explain the appropriate operation,
derived-output boundary, prototype origin and supported/proposed syntax. One
native value/Contract model serves both configuration and extension authors.

The current public naming decision is commands, with CommandsContract owning its
representation and constraints. This supersedes command-vector in earlier
proposed user examples; it does not rename historical source extracts or claim
a runtime migration. The complete target defaults, Contract and diagnostics use
the same field. See [[file:164-funflow-public-configuration/01-surface-and-schema.org][module 01]] for the direct-migration boundary and
[[file:164-funflow-public-configuration/10-discovery-conflicts-and-plan-preview.org][module 10]] for concrete discovery, diagnostic and preview renderings.

The existing build/test/package objects remain the CI/CD example. Public field
admission, field documentation projection, selected-checks, dynamic Profile
admission and qualified identity projection are proposed adaptations. Existing
native slot inheritance, path expansion, bounded module scopes and Contract
primitives are reused. No Loader, runtime, method registration or executable
configuration source is changed by this document.

The domain behavior is now specified through concrete structural Contract
declarations, the narrow recipe capability value, selector source shape and
normative admission algorithms and complete Scheme design bodies, including
internal helper definitions. Implementation/consumer qualification remains
future work. Shape-only field acceptance is explicitly weaker than consumer
capability admission, and both are weaker than authenticated runtime readiness.

The earlier [[file:164-funflow-cicd-user-authoring-design.org][authoring design]] and local publication remain evidence for their
implemented paths. For the proposed public schema and Check membership policy,
this document supersedes their incomplete admission assumptions. It does not
rewrite historical source examples or their execution receipts.

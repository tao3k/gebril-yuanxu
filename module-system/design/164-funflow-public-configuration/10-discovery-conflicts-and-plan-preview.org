* Corrected publication model

[[file:13-independent-profiles-and-scenario-composition.org][Module 13]] supplies the independent Profile and Scenario publications used
here. gerbil is a normal Scenario reference to a Profile occurrence; funflow is
its configured feature binding. Neither Profile ownership under a Module nor a
Scenario.Profiles container is implied. The lexical Check-container receiver is
effective-config, distinct from the enclosing Profile occurrence.

* Scope and owners

This makes three gaps in [[file:09-consolidation-and-ecosystem-gaps.org][module 09]] concrete, using the actual
[[file:../164-module-interface-comparison/07-ecosystem-task-interfaces.org][Omnibus AWS/Sandbox/CI, HiveBus and BAML task-interface comparison]].
The [[file:13-independent-profiles-and-scenario-composition.org][independent Profile/Scenario case]] is the current configuration authority.
No new command, public macro, field registry, Loader or runtime is implemented.

The configuration, descriptor, diagnostic and preview are native POO values.
Named pure functions own their projections. The inspector does not become a
second evaluator or writable configuration model. UI/JSON rendering is a final
projection. Requirements below describe result slots, not a newly implemented
API or another schema language. Owners publish metadata as ordinary native slots.

* One user journey: discover, refine, add smoke, inspect, admit, publish

Upstream supplies Funflow, prototypes, complete Gerbil build/test/package and
Pipeline defaults, field Contracts and policy declarations. Downstream binds
the module once, assigns ordinary values and takes the Check
prototype from the same bounded ff scope only for a genuinely new Check.

The target assignments inside that scope follow
[[file:11-direct-path-assignment-and-refinement.org][module 11's proposed deep-path lowering]]. The current path adapter only
supports dotted =>.+; these ordinary dotted assignments are not yet supported:

#+begin_src scheme
gerbil.funflow.build.commands:
'("gerbil" "build" "release")
gerbil.funflow.build.artifact-outputs:
'(release-build-log)
gerbil.funflow.smoke:
(.o (:: @ (.get ff prototypes check))
   check-name: 'smoke
   profile-ref: 'ci/check
   commands: '("sh" "./ci/smoke.sh")
   artifact-outputs: '(smoke-receipt)
   result-protocol: '(read :lines)
   dependency-refs: '(package)
   durable-task-id: 'task/smoke)
gerbil.funflow.pipeline.selected-checks:
'(build test package smoke)
#+end_src

This contextual excerpt is not a standalone executable form. The complete case
and module 11 show surrounding source bindings. Scripts are recipe requirements,
not verified files. Adding smoke without selecting it changes available tasks,
not the execution membership.

* Field discovery: inspect the declared interface before evaluating values

** Authoritative descriptor projection

Project the effective Contract's responsibilities and native field metadata.
Resolve documented defaults through their owning prototype/Profile paths rather
than copying executable defaults into a second table. Check fields are closed;
Configured Funflow extension positions accept named Checks according to the owner policy.
An inspector must explain this distinction before suggesting a new object.

| Descriptor slot | Meaning for smoke.commands |
|-----------------+----------------------------------|
| path | Qualified selected occurrence ending in smoke/commands |
| contract-identity | The current effective field Contract identity |
| audience | Ordinary configuration versus advanced extension or derived output |
| description | Executable and argv, with no implicit shell |
| default-owner-path | Where the executable default lives; not a forced value |
| constraints | Admitted structural/semantic description supplied by the owner |
| provenance | Source/revision and available declaration locations |
| demand-state | Description-only, unevaluated, evaluated, or failed |
| configuration-role | Value, derived output, existing-object extension, new-object position or core protocol extension |
| configuration-guidance | Intent-specific native assignment/refinement advice, target owner and actual support status |
| prototype-owner-path | Module-scoped prototype origin when constructing a new domain object is appropriate; otherwise not applicable |

These are proposed descriptor fields. Descriptions are owner metadata, not a
purity or executability proof. Predicate names alone cannot automatically supply
human-readable constraints. Missing descriptions/locations must be reported as
unavailable, not guessed. Immutable owner metadata is required for description-only
inspection; arbitrary computed metadata may need a separate explicit demand.

** Tell the author how to configure the field

Present four intent choices: assign a complete value, transform an inherited
value, create a new object, or extend a core mechanism. A deep path is still an
assignment, with implicit native intermediate inheritance. Do not first suggest
an object-extension operator simply because an ordinary field is nested.

The [[file:11-direct-path-assignment-and-refinement.org][intent/disclosure rule]] governs advice. Configuration-role and guidance are
proposed ordinary owner metadata/projections, not a new options DSL or security
permission system. The effective Contract and semantic owner determine the role;
do not infer it merely from object? or list?. If classification is not supplied,
show unavailable guidance and do not invent an editing action. Do not maintain
an independent writable-field registry that can drift from responsibilities.

| Selected field/position | Discovery advice | Boundary shown to the user |
|-------------------------+------------------+----------------------------|
| build.commands | Assign the full command value; no extension operator needed | CommandsContract; proposed deep-path syntax, native ordinary assignment exists |
| build.artifact-outputs | Assign to replace; native => append to retain and add | UniqueSymbolsContract; no automatic append |
| pipeline.selected-checks | Assign the desired membership list | Selected-name and dependency admission; declaration alone does not select smoke |
| pipeline.checks | Derived output; configure selected-checks and the named Checks | No ordinary editing suggestion; final effective-object identities must match |
| Configured Funflow's named Check extension position | Create smoke from the current module's prototypes.check | Scoped origin, new-object fields and Check admission; arbitrary unknown fields remain errors |
| An upstream-declared existing strategy | Use paths for ordinary field changes; =>.+ for explicit object extension | The strategy's own Contract and the current source-role policy |
| An upstream-declared core protocol boundary | Use native method/Contract extension; Generic only where axes independently vary | Consumer support and explicit admission; not a callback in commands |

An existing strategy need not be exposed just because a normal field's getter
uses it internally. Core rows apply only to boundaries actually declared by the
upstream owner; this table does not add an imaginary Funflow strategy slot.
Derived means not an ordinary config target, not runtime object immutability.
Descriptor advice cannot substitute for actual field/obligation checks.

At ecosystem scale, field help must navigate through qualified publication and
selected Profile metadata, not force every module to discover its attributes.
Show category, maintained owner/revision and configured occurrence separately.
If independent roots publish the same short name, request qualification at the
selection boundary rather than picking the first search path. An explicit paged
catalog search is broader than describing a known field. These are proposed
requirements of [[file:12-ecosystem-organization-and-demand.org][module 12]], not implemented Loader/index behavior.

* Conflict diagnosis: distinguish refinement from competing ownership

Native precedence remains native lookup semantics. The domain boundary adds an
explanation and admission policy for independently contributed business facts;
it does not reinterpret =>.+ or reject ordinary explicit child overrides.

| Contribution situation | Required result |
|------------------------+-----------------|
| User refines inherited build.artifact-outputs | Accept explicit replacement and show inherited/local contributions |
| User appends via native functional refinement | Record the transformation and resulting order; do not call it replacement |
| Two independent sources claim the same qualified smoke identity | Refuse ambiguous composition unless the owner relation explicitly resolves it |
| Two modules each publish local build | Preserve qualified identities; a shared local spelling is not itself a conflict |
| Different qualified tasks project to the same consumer key | Refuse the output collision before publication |

Qualification includes Scenario occurrence, module occurrence, Profile occurrence
and Check name, correlated with source identity. Printed paths alone do not
authenticate a source. A durable runtime identity also needs a specified consumer
mapping; slash-concatenating local task names is not a substitute.

The proposed native diagnostic contains code, qualified-path, stage, contributions
and repair. Each contribution retains source/revision, location when available,
original value or an explicitly unevaluated description, and operation kind.
Repairs identify the exact ambiguity: separate identities or explicitly choose
and refine an owner. Parent order must not silently choose business intent.
Do not force conflicting arbitrary values merely to print a diagnostic.

This requires retained contribution/provenance data before native lookup hides
the losing definition. Existing source-ref identity checks and module 07's issue
objects do not provide that history. No conflict collector is implemented here.
Owner resolution is a relationship of ordinary POO values, not a proposed new
resolution macro or imports language.

Example rendering for two hypothetical independent contributors; these are
illustrative source labels, not existing repository publications:

#+begin_example
BLOCKED: ambiguous contribution
Target: ReleaseCI.gerbil.funflow.smoke
Stage: composition conflict admission
A: team-a Profile -> smoke [source/revision/location when retained]
B: team-b Profile -> smoke [source/revision/location when retained]
Repair: separate identities, or explicitly choose an owner to refine
Publication: refused; parent order does not resolve business intent
#+end_example

* Effective plan preview: show results and exactly what is established

** Demand levels and native result slots

Description-only inspection lists metadata. Effective-value preview evaluates
only requested selected configuration. Admitted preview additionally performs
selected domain admission and consumer-plan validation. None executes commands.
The UI must label levels explicitly rather than display one vague valid badge.

| Stage | Established | Not established / permitted action |
|-------+-------------+------------------------------------|
| described | Owner metadata and interface descriptions are available | Effective values and domain/consumer validity are not established |
| projected-unadmitted | Requested values were resolved and a candidate projection is available | Configuration or consumer admission is missing; display for inspection only, no publication or execution |
| admitted-preview | Selected configuration and consumer-plan Contracts accepted this same stable input-view, with current correlated evidence | Not published merely by previewing, and not executed; the publication owner may separately commit the complete plan |
| blocked | Evaluation, composition, admission or projection has a blocking diagnostic | No current admitted plan for this edit; a retained previous plan must be labelled previous |

Do not infer admitted-preview from successful name resolution, an empty local
error list, object construction or a configuration Contract alone. With no
consumer-plan adapter/evidence, the most a candidate projection can claim is
projected-unadmitted. The current design has not implemented that consumer path.

| Preview slot | Required content |
|--------------+------------------|
| input-view | Effective Scenario/Profile objects, selected names, owner and Contract/policy revision identities |
| stage | Described, projected-unadmitted, admitted-preview, or blocked |
| tasks | Qualified identities with final argv, artifacts and declared runtime policy |
| edges | Admitted dependency relationships, not parent-prototype order |
| order | Consumer-supported stable order respecting dependencies |
| diagnostics | Errors/warnings with paths, stage and available provenance |
| validation | Current correlated configuration and consumer evidence, or explicitly absent |
| runtime-executed | False for every inspection/preview result |

An input-view must be stable for the projection/admission interval. Capturing
object references or revision strings does not freeze mutable getters. If the
owner cannot establish the supported immutable view, refuse publication or
re-prepare under a supported boundary; do not reuse stale evidence. Secrets and
sensitive payloads require redacted preview projections, not environment reads
or credential resolution just to display a task.

** Parent cache, admission and publication

The upstream getter remains checks: (funflow-selected-checks effective-config
selected-checks). Its outer native receiver binding must refer to the effective
child Profile. Force the parent Pipeline first as a control; the child preview
must still resolve its refined build and newly selected smoke. Pairwise current
Check identities are validated. A fixed parent list must block admission, not
produce a plausible three-task preview labelled admitted.

Make the negative control visible rather than quietly falling back:

#+begin_example
BLOCKED: effective-checks-mismatch
Expected: current child build, test, package, smoke objects
Received: fixed parent Check list
Reason: child membership/identity does not match the effective Profile
Publication: refused; previous admitted plan retained if one exists
#+end_example

The successful child preview must show the release build command, release-build-log and smoke while the
parent remains build/test/package with its original build. Check actual versus
expected objects pairwise by native identity, in addition to membership/order;
matching printed names or commands does not establish final-receiver identity.
No scenario is marked admitted while using a stale parent's validation evidence.

ContextSlot does not turn a changed receiver/selection into a same-context hit.
ConstructionCache skips actual work only under established unchanged dependencies;
ContractConsequence transports proof only under a supplied valid implication.
See [[file:08-leanpoo-reuse-and-performance.org][the pinned LeanPoo conditions]]. No old candidate evidence becomes a current
preview receipt merely because displayed values happen to match.

The plan owner must consume the selected graph order, qualify and project tasks,
validate the consumer format, then publish one complete admitted plan from that
same input-view. Current ff-selected-graph order is not yet a published plan;
the reference obligations consume its problems. A blocked preview may explain
partial configuration but must never publish a partial new plan. Refusal retains
the previous admitted plan and labels it as previous, not current to the edit.
Publication is separate from explicit runtime handoff and execution receipts.

* Task-oriented tooling without copying BAML syntax

Borrow BAML's task/input/output focus and discover-before-run workflow. A future
editor or CLI may render the same descriptor/diagnostic/preview objects; this
revision defines neither a new command spelling nor an alternate evaluator.
Keep ordinary CI edits in native paths, extension in native prototypes, and
validation in the existing Contract boundary. A preview never implicitly runs
smoke or activates all module methods, Profiles or external services.

* Acceptance matrix and implementation status

| Control | Required observation |
|---------+----------------------|
| Describe a known field | Owner metadata appears without unrelated Profile construction |
| Ask how to configure a value | Show ordinary assignment first and native transformation only for inherited-value intent; label proposed syntax |
| Ask how to change derived checks | Point to selection/named tasks; do not suggest a manually assembled checks list |
| Ask how to add smoke | Show the current module's prototype origin and admission requirements without leaking a global alias |
| Missing operation guidance | Show unavailable metadata; do not infer editability from the runtime value type |
| Demand an effective field | Final value and provenance are labelled separately from a default description |
| smoke.commmands | Qualified unknown-field diagnostic and suggestion; no publication |
| selected smkoe | Missing-selection diagnostic before checks demand |
| Add smoke without selecting it | Availability changes; membership stays build/test/package |
| Select valid smoke | Four current task identities and package-to-smoke edge |
| Parent Pipeline cached first | Child preview contains refined build and smoke; parent remains unchanged |
| Freeze parent checks into child | Effective identity/membership refusal |
| Independent same-identity contributions | Both sources shown; no accidental precedence winner |
| Consumer output-key collision or schema failure | Blocked publication, previous plan retained |
| Mutable/unsupported input view | No stale admitted preview or cache-proof shortcut |
| Preview any case | No commands, cloud changes, sandbox execution or Loader activation |

These are future acceptance cases, not new passing test receipts. Native slot
inheritance/path expansion and bounded scope support are reused; discovery
projection, provenance retention, rich diagnostics, preview evidence and atomic
consumer publication remain proposed adapters. No runtime or Loader change is
made by these documents.

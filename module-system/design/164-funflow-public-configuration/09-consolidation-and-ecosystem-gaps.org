* Corrected publication model

[[file:13-independent-profiles-and-scenario-composition.org][Module 13]] supplies the independent Profile and Scenario publications used
here. gerbil is a normal Scenario reference to a Profile occurrence; funflow is
its configured feature binding. Neither Profile ownership under a Module nor a
Scenario.Profiles container is implied. The lexical Check-container receiver is
effective-config, distinct from the enclosing Profile occurrence.

* Decision and evidence boundary

Consolidate repeated preparation, traversal and declarations, not semantic
requirements. The 31 functions in [[file:07-admission-source.org][the complete reference source]] are an
auditable decomposition, not a target public API or an optimal function count.
They remain design code. This revision neither replaces their bodies nor claims
that Lean proves the Scheme adapter. It adds no Loader or runtime integration.

Keep one native POO model for upstream libraries and downstream configuration.
Use named pure functions for selection and graph algorithms, native slots for
receiver-dependent behavior, and private defrules only for repeated declarations.
Generic dispatch belongs at independently varying consumer/protocol boundaries.
No new options DSL, cache DSL or configuration wrapper is introduced.

* Compare maintained ecosystems, not just language mechanisms

The evidence below is the actual configuration/library split in our existing
projects. The [[file:../164-module-interface-comparison/01-omnibus-ncl-cases.org][Omnibus case study]] and [[file:../164-module-interface-comparison/02-hivebus-nixos.org][HiveBus case study]] retain the larger
extractions and limitations. These fixed source cuts are not claims about a
newly queried upstream HEAD, measured scalability or completed executions.

** Omnibus NCL: CI intent, reusable matrix generation and output admission

At [[https://github.com/tao3k/omnibus-ncl/blob/c5d37eb51961fd7bd32f775843044ca7f8191715/github/nix/ci.ncl][github/nix/ci.ncl]], the author supplies configs, matrix.job and steps. The
file ends with this actual library/schema boundary (MIT source):

#+begin_src nickel
& (import "../matrix.ncl")
|> std.serialize 'Json
|> std.deserialize 'Json
  | (import "../github-workflow.schema.ncl")
#+end_src

The maintained [[https://github.com/tao3k/omnibus-ncl/blob/c5d37eb51961fd7bd32f775843044ca7f8191715/github/matrix.ncl][github/matrix.ncl]] hides intermediate configs/matrix with
not_exported, maps configurations into jobs, derives names and merges outputs.
Its per-configuration refinement includes this actual expression:

#+begin_src nickel
(
  matrix & { config = config' }
).job
#+end_src

This is already a reusable CI library, not merely a language capable of records.
Our selected-checks mechanism must be judged against its usable authoring and
output path. A short POO refinement does not yet supply matrix expansion,
collision handling, workflow-schema checking or a GitHub Actions adapter.

The sandbox ecosystem also has a concrete build/to_profile consumer. In
[[https://github.com/tao3k/omnibus-ncl/blob/c5d37eb51961fd7bd32f775843044ca7f8191715/sandbox/seatbelt/interface.ncl][sandbox/seatbelt/interface.ncl]], named NetworkConfig/FsConfig coexist with
inline build defaults; their mere declaration does not establish that build
attaches every named constraint. The same contract-attachment risk applies to
our responsibilities. Require a negative test at the actual consuming boundary.
to_profile calls build again; source repetition alone is not a measured duplicate
evaluation cost. Our preparation/validation/emission ownership must be explicit.

** HiveBus: ordinary data and an advanced object extension surface

The actual [[https://github.com/tao3k/hivebus/blob/edc6095bed63a3c14f9f7147c931378d3e9d1609/hosts/host-3/meta.nix][hosts/host-3/meta.nix]] lets a host author set system and deployment
attributes while upstream supplies inputs/self. The maintained
[[https://github.com/tao3k/hivebus/blob/edc6095bed63a3c14f9f7147c931378d3e9d1609/units/self/pops/hosts.nix][units/self/pops/hosts.nix]] centralizes source/input binding:

#+begin_src nix
omnibus.pops.load {
  src = projectRoot + /hosts;
  inputs = {
    inherit (inputs) nixos-unstable;
    inputs = inputs;
  };
}
#+end_src

The actual [[https://github.com/tao3k/hivebus/blob/edc6095bed63a3c14f9f7147c931378d3e9d1609/units/self/flakeOutputs.nix][units/self/flakeOutputs.nix]] publishes normal configurations and pops,
and refines a naming policy before reading exports:

#+begin_src nix
renamerHiveExports = (super.pops.hive.setNixosConfigurationsRenamer "asd").setHomeConfigurationsRenamer "myHm";
#+end_src

That is already progressive disclosure implemented by a library: ordinary
values for common tasks, object extension for specialized ones. Our two layers
are not an invention absent from the Nix ecosystem. HiveBus consumes external
POP machinery; these call sites do not establish its cache internals or cost.
Nor may a generic NixOS options example be described as HiveBus's own validator.

** Consequences for our upstream and downstream interfaces

| Authoring task | Existing ecosystem lesson | POO design response and remaining cost |
|----------------+---------------------------+----------------------------------------|
| Maintain many recipes | Omnibus owns matrix transforms; HiveBus centralizes source/input loading | Publish complete defaults, contracts and pure projections; static source imports and catalog scale still need measurement |
| Change one business value | Omnibus CI and HiveBus host files expose intent rather than provider machinery | Refine native paths; provide discovery so users need not inspect internal source |
| Extend behavior | HiveBus exposes POP extension before exports | Keep native prototype/strategy extension; define its admitted source role and conflicts |
| Produce a useful artifact | Omnibus checks serialized workflow shape; HiveBus publishes deployment configuration outputs | Admission must feed a checked consumer projection; object construction alone is insufficient |

Scheme higher-order functions and private macros can factor upstream families
without exposing an internal component inventory. POO lexical slots keep derived
values attached to the effective receiver. LeanPoo can constrain valid reuse.
These are useful mechanisms; better user experience and performance remain
claims requiring consumer tests and matched measurements.

* Consolidate the 31 reference functions

| Reference group | Count | Permitted consolidation | Required semantic boundary |
|-----------------+-------+-------------------------+----------------------------|
| Diagnostics, reflection, evidence and unknown fields | 10 | Shared diagnostic construction and prepared declared-field membership index | Preserve evaluation/classification/admission failure distinctions and current evidence correlation |
| Context and source occurrence | 3 | Shared native Context/capability structural Contracts | Effective Scenario/module/Profile and source association must match |
| Preflight and selection checks | 4 | Reuse one established preparation within admission | Missing, duplicate, reserved and non-Check selections fail before checks is forced |
| Native Check recognition and selection | 2 | One named pure selector | Resolve the requested order on the effective receiver; retain object identities |
| Guarded admission and three adapters | 4 | Private defrules may generate the three thin wrappers | Preserve preflight-before-inherited-traversal and fail-closed evidence |
| Capability, reference, metadata and payload helpers | 4 | Factor common traversal and field descriptors | Shape, supported policy, reference resolution and payload admission remain distinct |
| Domain obligations | 3 | Consume established preparation/proofs without repeating work | Check, Pipeline and Profile requirements still apply |
| Selected dependency graph | 1 | Reuse only under unchanged selected graph and policy premises | Missing dependencies, cycles and duplicate durable task IDs remain errors |

The counts sum to 31. Adapter generation reduces source duplication, not
necessarily runtime cost. Native .all-slots already caches slot/precedence data;
a prepared membership index removes repeated membership scans, not a supposedly
uncached complete native schema rebuild.

** LeanPoo reuse conditions

Use the exact [[file:08-leanpoo-reuse-and-performance.org][pinned LeanPoo study]] for definitions and proof scope:

- ConstructionCache permits actual builder skipping under its unchanged-resolver
  premises. An immutable effective Contract revision may support a shared field
  index. A digest, a matching name or a candidate-owned validated flag alone does
  not prove unchanged behavior. Failures are reusable outcomes too, but relevant
  edits require fresh preparation.
- ContextSlot binds data to the exact factory family and context. A different
  effective receiver or selected membership is not automatically a hit. Its
  consume operation may still run on a hit. Parent getter caches and explicit
  cross-revision construction caches are different mechanisms.
- ContractConsequence transports a proof under an explicit implication for the
  same data family. A weaker old Contract cannot establish a stronger new one.
  Transported results still need current candidate/context occurrence evidence;
  never return an old ValidationEvidence unchanged for a new candidate.

Guard/obligation duplication can be eliminated only within an established
unchanged view. Arbitrary mutable objects, effectful getters or opaque reads
require conservative revalidation or an explicitly supported dependency model.
The Lean typed computation model does not infer arbitrary Scheme dependencies.

* Minimum CI/CD example: cache the parent, then add smoke

The ordinary user surface below follows proposed direct dotted assignment in
[[file:11-direct-path-assignment-and-refinement.org][module 11]], with native intermediate inheritance underneath. That adapter
remains future work. Explicit enclosing-object =>.+ belongs in its native
lowering or in an intentional inherited-object extension, not every value edit.

The [[file:13-independent-profiles-and-scenario-composition.org][independent Profile/Scenario wiring]] is authoritative. Independent Profile owners supply
build/test/package defaults; pure Module owners supply prototypes and Contracts.
The essential relationship in that existing Profile constructor is:

#+begin_src scheme
;; Inside the configured Funflow's (.o (:: effective-config ...)) body:
pipeline:
(.o (:: @ (.get ff prototypes pipeline))
  pipeline-name: 'default
  selected-checks: '(build test package)
  checks: (funflow-selected-checks effective-config selected-checks))
#+end_src

This is a contextual excerpt, not a separate executable form. effective-config
is the native outer receiver binding; selected-checks is the Pipeline lexical
slot binding. No manual Check collector belongs in the user configuration.

#+begin_src scheme
(.def (ProjectCI @ CICDScenario))

;; Verification-only demand: fill the parent receiver's Pipeline cache first.
(def parent-checks
  (.get ProjectCI gerbil funflow pipeline checks))

(def ReleaseCI
  (let ((module-scope (.get ProjectCI gerbil funflow)))
    (use-module module-scope as ff
      (.o (:: @ ProjectCI)
        gerbil.funflow.build.artifact-outputs:
        '(release-build-log)
        gerbil.funflow.smoke:
        (.o (:: @ (.get ff prototypes check))
           check-name: 'smoke
           profile-ref: 'ci/check
           commands: '("sh" "./ci/smoke.sh")
           artifact-outputs: '(smoke-receipt)
           result-protocol: '(read :lines)
           dependency-refs: '(package)
           durable-task-id: 'task/smoke)
        gerbil.funflow.pipeline.selected-checks:
        '(build test package smoke)))))
#+end_src

The script is a downstream recipe requirement, not a claim it exists or ran.
Selected admission checks names before traversing checks. The child getter must
resolve all four names on its effective Profile: the refined build, inherited
test/package as resolved there, and new smoke. Check obligations use that same
selected owner/context. Actual checks must be pairwise eq? to those effective
objects; a copied parent list is refused. Merely adding smoke does not select it.

The parent cache remains valid for the parent. The child is not entitled to use
it as its own Check list. Changing selected-checks changes membership and the
selected graph; it requires fresh construction or a justified transport. Reusing
unaffected component work is a separate optimization. Fixed checks: parent-checks
is the negative control: it lacks smoke and retains the parent's build.

Native receiver probes have executed historical controls. The complete domain
adapter, four-member selected admission and Lean-to-Scheme reuse correspondence
are not thereby validated. No new execution receipt is created by this example.

* Six remaining design gaps and acceptance requirements

[[file:12-ecosystem-organization-and-demand.org][Module 12]] adds the ecosystem organization and demand-stage requirements,
based on actual NixOS and Doom sources. The number of possible combinations must
not cause eager creation of every possible Profile/Scenario instance.

[[file:10-discovery-conflicts-and-plan-preview.org][Module 10]] develops discovery, conflict diagnosis and effective-plan preview
into concrete native result requirements and a smoke acceptance journey. Its
[[file:../164-module-interface-comparison/07-ecosystem-task-interfaces.org][ecosystem evidence]] adds actual Omnibus AWS/Sandbox/CI and HiveBus examples
and borrows BAML's task-tooling experience without copying its syntax.

** 1. Field discovery and provenance

Project field names, descriptions, audience, constraints and default-owner paths
from the effective responsibilities. Do not maintain a second schema/default
table. Inspection must distinguish documented defaults from computed effective
values, and avoid forcing getters merely to list available attributes. Show the
source location and inherited/local contribution for an effective value.

Acceptance: a CI author discovers commands without reading implementation,
sees where release-build-log came from, and receives a qualified path and useful
suggestion for commmands. These inspection/diagnostic facilities are not
implemented by naming a Contract or by the current unknown-field issue alone.

** 2. Merge conflicts and order

Keep native replacement, functional list refinement and nested =>.+ distinct.
Prototype precedence determines native lookup; it is not a complete policy for
independent publishers. Explicit downstream refinement of one inherited value
is allowed. Ambiguous independent contributions to the same qualified business
identity require a source-aware conflict or explicit owner resolution, not an
accidental parent-order winner. Retain both contribution locations.

Acceptance: explain scalar replacement, append versus replacement, and same-name
Check conflicts. Qualify separate publishers' build identities. Define collisions
after matrix/name projection too; lexical separation alone cannot prevent output
key collisions. Parent order never supplies task execution order. selected-checks
sets membership and deterministic tie preference; dependencies constrain order.
The full contribution/provenance conflict policy still needs an adapter design;
module 07 does not retain all contribution history or implement that policy.

** 3. Open extension versus spelling mistakes

Check attributes are closed against effective responsibilities. Profile Check
names are an open extension point, not a reason to allow arbitrary Check fields.
Do not close a Profile to its pipeline responsibility alone, and do not accept
every added slot merely because native objects are open. The owner must specify
which extension positions contain Check objects and which contain metadata or
other declared roles. Selecting a new Check requires explicit membership.

Acceptance: new smoke succeeds through its prototype and field/domain Contract;
smoke.commmands fails; smkoe in selected-checks fails before checks demand.
A valid but unselected new name cannot reveal whether the author intended a
different spelling. Discovery should show unselected declarations without
silently selecting, renaming or executing them. Current selected admission does
not validate every unselected object in the catalog; full linting is an explicit
separate demand, not an implicit eager scan.

** 4. Library release identity and evolution

Retained source identity is not authentication, a version lock or compatibility.
Specify publication revisions, Contract compatibility, default changes and
migration policy before claiming reproducible upgrades across thousands of
modules. Keep these owner facts out of ordinary user boilerplate.

Acceptance: a pinned CI recipe is explainable; an incompatible Contract/default
upgrade produces a targeted migration failure. No Loader or release mechanism
is implemented here, and no current source-handle check proves these properties.

** 5. Effects, demand and first-access cost

Scheme expressiveness permits effects, recursion and opaque dependencies. Native
lazy getters alone prove neither purity nor cheap first access. Separate catalog
discovery, source/compile work, scope construction, prototype demand, Profile
construction, admission, projection and warm reads. Include memory and actual
factory counts. Test small selected K against 1000/10000 catalog descriptors.

Acceptance: selecting one recipe does not force unrelated Profiles, and failures
remain bounded and attributable. Benchmark cold and warm paths separately.
Unsupported dependency analysis uses conservative recomputation. No scale or
first-access advantage over either ecosystem is established by this study.

** 6. Contract admission, plan projection and publication

Object construction, selected configuration admission, consumer-plan admission,
atomic plan publication and runtime execution are separate facts. Apply:

1. Resolve the selected effective Profile and preflight its selected names.
2. Admit its fields, policy support, references, effective identities and graph.
3. Project qualified tasks/edges in the consumer's supported order and format.
4. Check that projection against the consumer Contract and current input identity.
5. Publish the complete accepted plan atomically; refusal retains the old plan.
6. Execute only behind the explicit runtime handoff and produce runtime receipts.

At present ff-selected-graph returns order, but pipeline obligations consume
problems. This is configuration validation, not an implemented plan publisher
or scheduler. A future projection must use admitted effective values and ordering
without rereading a changed configuration or inventing a second semantic root.
LeanPoo StagedPublication supplies a relevant model, not an installed Scheme
publication transaction. A serializable plan and authenticated capability/readiness
evidence remain consumer responsibilities. Admission does not prove commands
succeed, artifacts exist or compensation can actually execute.

Acceptance: a typo, graph error or consumer-schema failure publishes no partial
new plan; a successful smoke selection yields a four-task plan with the refined
build. A separate execution receipt is needed to claim CI ran successfully.

* Delivery boundary

This module records design decisions and acceptance cases. Complete default
objects, native expansion and historical cache probes remain in their existing
owners. Source consolidation, prepared indices, diagnostic discovery, conflict
history, dynamic domain admission, plan publication and cross-revision reuse
must not be reported as newly implemented by this document. Loader work remains
outside this change.

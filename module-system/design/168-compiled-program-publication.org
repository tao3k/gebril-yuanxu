#+title: Compiled Program Publication Boundary

* Ownership

The init-owned =std-make-spec= selects the admitted Module and Feature closure.
Gerbil owns compiler identities, imports, export aliases, initialization and
linking. A compiled consumer must use that closure; it must not reconstruct a
directory selection from the producer checkout at runtime. Rust consumes the
resulting program through one Scheme VM. AITIA does not provide another loader.

Source publication retains its byte, source-owner, dependency and generation
checks. Compiled publication does not turn an earlier source check into live
permission to read a checkout. Its exported values must retain the same POO
composition, Contract, Feature selection and error semantics. The bridge owns
packaging and VM lifecycle, not Module selection or a second dependency graph.

* Build projection interface

Module Build declarations and the selected dependency Graph own targets,
compiler parameters and dependencies. =std-make-spec= is their projection to
Gerbil Make data. It does not define a separate target policy or another
command dispatcher. Production =exe:= targets do not require a test demand.
Native imports and the retained package-library closure select the declaration
that contains =yuanxu!=, regardless of its filename. The admitted projection
lowers that reached declaration into its compiled publication. Obtaining a
specification from an init-owned selection does not itself add another compile
target; generic Graph projection must preserve the selected native closure.
The projection preserves their native target kind, binary name and compiler
options, including in a cross-package source view. A source shared with a
library has one compiler-input identity and two distinct Make products.
Source currentness and safe target naming still apply; projecting a program
does not issue the test publication protocol's execution authority.

An ordinary consumer can import the projection directly:

#+begin_src scheme
(import (only-in :yuanxu/module-system/building/script defbuild-script)
        (only-in "./init.ss" std-make-spec))
(defbuild-script std-make-spec)
#+end_src

The exported identifier demands the SAME init-owned projection in the shared
build extent. It does not build a second Graph or retain another approval.
The qualified init namespace remains useful for Module composition; a build
consumer need not know its generated container name. Gerbil's =build= and
=test= commands remain the execution entrypoints. An application build script
must not recreate argument dispatch, load-path restoration or static-input
ownership after receiving the projection.

The compiled init is the compiler publication of the selected namespace root.
It enters the existing prepared-input routing and Make freshness record,
including the emitted import/binding forms. A changed closure must regenerate
that publication even when the original init declaration is unchanged. Normal
libraries continue through their existing native imports; no directory loader
or contributor-supplied strategy flag is introduced.

* Role projection

The compiler's existing =for-template= import identifies the prepared role
context. Re-resolving its public name can select an unwrapped source role or
stale installed interface. =compiled-role-values= therefore reads that admitted
context directly during expansion and resolves public aliases to canonical
runtime identifiers. It rejects missing or non-runtime exports then, rather
than postponing the error to a deployed binary.

The emitted runtime expression uses the creating static unit's registered
descriptor to distinguish a linked program from a dynamic library. Linked role
demand activates the registered Gambit descriptor and refuses a missing unit
before any file lookup. Dynamic library demand retains Gerbil's ordinary load
protocol. It then reads the canonical globals. It does not import an expander context, capture a function
value during compilation, or create a value/approval cache. Optional =Config=
retains its existing absence semantics. Interface inclusion owns the hygienic
resolver binding; generated role data does not supply executable loader code.

Source value factories retain the invoking reader's import owner. Replacing
=current-expander-module-import= with =core-import-module= bypasses the reader's
dependency enrollment, especially when the imported context already exists.
The factory may supply a fresh lexical frame; it must not replace that owner.

This role correction alone does not establish standalone program acceptance.
An init which still reconstructs a source selection, or an archive which omits
its selected role objects, remains an open failure of the program boundary.

* Observed AITIA delivery gap

The current AITIA program manifest contains its =lambda-aitia/init= unit but
no =lambda-aitia/modules/= units. This is a property of that existing artifact,
not a result for a rebuilt candidate. Its draft operation first demands
=modules/project-config= through the imported init export. The emitted init
still calls =yuanxu-init-build=; its first namespace demand reads the original
init declaration and constructs a directory selection. Linking the init alone
therefore does not deliver the selected Module closure.

There are two distinct obligations. The compiler must publish the init's
selected Module/Feature namespace as compiled bindings, preserving POO
composition, dependency contracts and lazy demand. Packaging must include the
native units actually referenced by that publication, including deferred roles.
Supplying more SSI metadata alone does not discharge the first obligation.
Changing the consumer's load path or adding direct business imports discharges
neither obligation. Source publication and its mutation controls remain intact.

The source adapter has a further explicit filesystem obligation:
=admit-module-publication!= checks a root-qualified declaration against
=core-read-module/sexp=. A deployed publication cannot use that adapter and
silently replace its check with a successful callback. Compilation must bind
the verified native Module identity and public export to the emitted value;
runtime value admission must preserve the same owner, dependency and Feature
Contracts without reopening the producer file. Scope composition remains the
existing POO/Module linker, not a second evaluator or merge algorithm.

A native Gerbil import binds a public value; a subsequent =.get= consumes an
object capability. These are not duplicate loads. Nevertheless an ordinary
build consumer should not need a generated =package.init.exports= container
merely to obtain its already selected build procedure. The owning export
boundary must expose that capability directly. This API obligation is separate
from delivering the complete compiled namespace; shortening its spelling cannot
be used as evidence of standalone deployment.

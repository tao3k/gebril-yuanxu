* Source audit before interface design

This is a design proposal, not an implemented domain API. All business slots,
policy prototypes and domain Contracts below are proposed names. Examples use
existing native .def, .o and =>.+ forms, plus the proposed bounded
use-module scope adapter. No implementation, source export or runtime changed.

|-----------------+------------------+--------------------------------|

| [[file:../../../user-interface/profiles/crewai.ss][CrewAI publication]] | native semantic Profile values and Module export index | configured crew business slots or executable scheduler/guardrail override |
| [[file:../../../user-interface/profiles/tool-calling.ss][Tool Calling publication]] | native semantic Profile values and Module export index | configured tool business slots or executable validator override |

The existing libraries' contract and policy symbol slots are semantic claims.
Changing one symbol does not replace code or implement a new algorithm. Existing
name metadata is not a substitute for meaningful business configuration.
Existing fuel examples show effective stage data; they do not demonstrate an
end-to-end mapping from those Scenario labels to an executing domain runtime.

* Public configuration is a consumer-owned product

The proposed configured graph, crew and tool values own business configuration
and a small set of documented POO policy extension points. They do not expose an
inventory of implementation components. Ordinary users inherit defaults; domain
extension authors may inspect the policy Contract/proto and override it natively.
No new public method syntax, patch DSL, callback slot or component-list syntax
is introduced. Ordinary values and native POO objects remain the slot values.

Every new slot must have a Contract and a named consumer. Merely preserving an
unknown slot in a Bundle is not support. Unsupported fields/strategies must
produce admission diagnostics rather than be silently ignored. The following
scope is deliberately bounded; defaults are proposed product choices, not facts
from the current libraries or external LangGraph/CrewAI APIs.

* LangGraph: business state selection versus routing policy

| Public slot | Proposed default / Contract | Proposed actual consumer |
|-------------+-----------------------------+--------------------------|
| checkpoint-key | #f, or nonempty string | graph execution adapter resolves a checkpoint in the admitted session/workspace namespace |
| resume? | #f, Boolean | graph session preparation restores the selected checkpoint; true requires a key and supported backend |
| routing-policy | shared LangGraphRoutingPolicy. proto; LangGraphRoutingPolicyContract | graph route adapter reads effective policy when selecting among declared eligible edges |

LangGraphConfiguredModuleContract admits the two business values and the policy
object. Cross-obligations reject unsupported restore, incompatible checkpoint
identity and routes outside the declared graph. The proposed routing policy has
selection: 'declaration-order by default; 'priority selects admitted edge
priority, with declaration order as a deterministic tie break. selection is an
extension-policy field, not a normal business checkbox. No selector may invent
edges, bypass branch-target admission or reset loop progress evidence.

  (use-module LangGraphModule as lg
    (.+ lg
        {profiles: =>.+

#+end_src

These changes use inherited =>.+ throughout. Keep the existing policy object
and its previous refinements; no scoped prototype lookup or .o construction is

The shared proto and policy Contract are maintained upstream. A strategy
unsupported by the route adapter fails admission. Adding an algorithm beyond
these admitted strategies requires extending the owner implementation and its
Contract; it cannot be accomplished by inventing a policy symbol in config.

* CrewAI: task intent and capacity versus scheduling policy

| Public slot | Proposed default / Contract | Proposed actual consumer |
|-------------+-----------------------------+--------------------------|
| goal | #f, or nonempty string; may be required by a selected Scenario | crew task preparation passes literal goal context into admitted task inputs |
| max-concurrency | 1, positive integer within provider/runtime limits | crew execution adapter bounds dispatch of dependency-ready tasks |
| scheduling-policy | shared CrewSchedulingPolicy. proto; CrewSchedulingPolicyContract | crew dispatch adapter orders dependency-ready tasks |

CrewConfiguredModuleContract owns these responsibilities. Goal text cannot grant
permissions or redefine task dependencies. The scheduling policy defaults to
ordering: 'fifo; 'priority changes ordering to admitted task priority with FIFO
ties. max-concurrency is a capacity bound, not permission to schedule dependent
tasks concurrently. Unsupported dispatch concurrency fails admission, rather
than silently being ignored by a sequential backend. This does not select a
CrewAI implementation automatically; a compatible handoff adapter is required.

* Tool Calling: allowed use and budget versus argument validation

| Public slot | Proposed default / Contract | Proposed actual consumer |
|-------------+-----------------------------+--------------------------|
| allowed-tools | empty symbol list by default; unique admitted tool identities | tool plan/permission adapter narrows the session-authorized tool set |
| timeout-ms | 30000, positive integer within runtime bounds | tool runtime adapter enforces per-call deadline and cancellation handling |
| argument-validator | shared ToolArgumentValidator. proto; ToolArgumentValidatorContract | tool validation adapter checks arguments before any runtime call |

ToolConfiguredModuleContract checks the business slots and validator object.
An empty allowlist denies calls. Listing a tool cannot authorize it: effective
permission is the intersection of requested tools, session grants and sandbox
policy. A runtime without enforceable cancellation/deadlines cannot claim this
timeout is supported. Failed/uncertain execution still follows receipt rules.

The validator policy defaults to maximum-depth: 64. Extension may tighten to a
positive bound no greater than the admitted parent limit. The consumer measures
structural argument depth with a specified root convention and rejects excessive
nesting before dispatch. The schema, authorization and untrusted-output rules
remain mandatory; this POO object configures the validation mechanism and is
not a replacement for permission checking.

* Inline strategy slots preserve native ancestry and demand

A one-off policy does not need its own top-level name. Use policy-slot: =>.+
inside the configured Module. Its inherited value must already be an admitted
native POO object from the stable shared upstream proto; false, an unbound slot,
or a symbolic policy label is not enough. Upstream responsibilities validate
this shape; the proposed contextual adapter does not silently turn symbols into
behavior implementations. Do not synthesize a fresh unrelated policy object.

For one strategy slot, the explicit native inherited-slot form is:

#+begin_src scheme
(routing-policy (inherited)
  (.+ (inherited)
      (.o selection: 'priority)))
#+end_src

This explains (routing-policy => .+ (.o selection: 'priority)): obtain the
inherited value for this slot, then derive its override. The same principle
applies at Profiles, production and the configured Module, not just the policy.
Do not replace this with construction from the bare policy proto: that would
lose refinements already present on the inherited policy instance.

Native nested =>.+ extends the inherited policy value, retaining its inherited
slots and proto ancestry. It does not mutate the shared upstream policy and does
not need a new inline-policy syntax or Contract annotation. Reusable policies
can still be named deliberately, but naming is optional, not a prerequisite for
configuring one Scenario. No anonymous behavioral callback slot is introduced.

Business slots and policy slots remain distinct responsibilities even when
written in one brace. The concrete Module Contract admits the policy through its
own policy Contract and cross-obligations. Native ancestry alone is not proof
of valid strategy, capability, permission or execution evidence.

On demand, resolving the configured Module may demand its inherited base. On
demanding the policy refinement, native =>.+ obtains the inherited policy and
derives the refined value. The syntax does not promise zero work when the parent
is needed, nor does it justify forcing other policies, Profiles or sources.
Admission forces required policy facts; selected composition and handoff read
the same effective derived value. A parent-first force must not cause the child
to reuse stale composition/evidence. The refinement never starts a Session.

* Contract wiring and effective consumption

Proposed upstream responsibilities are scoped to concrete configured objects:

| Profile responsibility | Concrete Module Contract | Native policy responsibility |
|------------------------+--------------------------+------------------------------|
| graph | LangGraphConfiguredModuleContract | routing-policy -> LangGraphRoutingPolicyContract |
| crew | CrewConfiguredModuleContract | scheduling-policy -> CrewSchedulingPolicyContract |
| tool | ToolConfiguredModuleContract | argument-validator -> ToolArgumentValidatorContract |

Each concrete Contract inherits the common configured Module identity/provenance
rules and supplies a stable shared native proto with owned defaults. The
Scenario family resolves its dynamic Profile names and responsibility map.
A native instance inherits its proto, never its Contract descriptor. User
configuration does not repeat the upstream responsibilities or current-profile
annotation. Generic collection admission and objectification remain proposed.

Native policy inheritance gives a real ancestry relation; it is not sufficient
admission by itself. Value predicates, strategy support and semantic obligations
must pass. Existing Core Contract machinery can express these checks, but the
new predicates, domain obligations, policy protos and consumer wiring do not yet
exist. Ordinary refinements also require admission: business attributes are not
an unchecked route around policy.

The current paths are graph.profiles.state-graph, crew.profiles.crew-workflow
and tool.profiles.tool-loop. The [[file:164-bounded-domain-module-scope-examples.org][canonical bounded examples]] replace earlier
direct Module policy paths and global constructor names.

| Contract boundary | Proposed responsibility |
|-------------------+-------------------------|
| Scenario.graph / crew / tool | native configured Module scope Contract; source and occurrence compatibility |
| Module.profiles | admitted native catalog/selected contribution view |
| selected state-graph | checkpoint/resume fields and routing-policy -> LangGraphRoutingPolicyContract |
| selected crew-workflow | goal/capacity fields and scheduling-policy -> CrewSchedulingPolicyContract |
| selected tool-loop | requested tools/deadline fields and argument-validator -> ToolArgumentValidatorContract |

Existing yuanxu-object-admit reads effective slots, admits each through its
responsibility Contract and then checks obligations. The domain view/collection
Contracts and proto publications remain proposed. All mandatory selected facts
must be checked; whole-object fixed responsibility checks are not magically
selective. Source, support, dependency/permission and runtime constraints still
apply to new objects and inherited refinements.

#+begin_src scheme
(.get MyGraphScenario graph profiles state-graph routing-policy selection)
;; Expected configuration: priority
(.get MyCrewScenario crew profiles crew-workflow scheduling-policy ordering)
;; Expected configuration: priority
(.get MyToolScenario tool profiles tool-loop argument-validator maximum-depth)
;; Expected configuration: 16

Pure adapters read those exact derived receivers and user business attributes.
They preserve source/occurrence evidence and qualified reference relationships,
rather than reattaching default Profile/policy objects. The refined policy retains native
ancestry from its actual inherited instance; a valid ancestry relation is not a
runtime enforcement receipt. checkpoint restore, ready-task dispatch and tool
validation/deadline adapters must actually consume these values. The old
semantic symbol Profiles do not implement those consumers.

* Demand sequence for the current bounded examples

Expansion preserves syntax and source context without runtime loading. Evaluating
the selected Module slot creates its bounded alias scope and derived native value.
Individual Profile/attribute/prototype access follows actual native demand;
new-object parent lookup can load the precise prototype owner. Selected domain
admission/plan projection forces its necessary facts and required dependencies,
then an explicit Session is the only execution boundary. Unselected catalog
entries are not implicit operands, and unknown/unsupported policy fails admission.

Natural laziness is default, not a defer flag; a hidden import-all or monolithic
first getter is not compliant. Measure scope creation, first Profile read,
inherited policy demand, selected admission/plan and warm repeats separately.
Measure prototype construction separately only for genuine new-object authoring.
Verify parent-first memoization does not restore stale child configuration or
evidence. No cold/warm latency or runtime behavior is claimed by this update.

* Native user objects do not require repeated default declarations

User .def inheritance remains public. When a maintained Profile already owns
Check objects, users refine those inherited slots; they need not recreate each
Check or repeat check-name/Profile/runtime defaults. Standalone Check declarations
remain useful for new/reusable contributions, subject to identity and contracts.
See [[file:164-funflow-cicd-user-authoring-design.org][the complete inherited Funflow example and named Checks projection]].

* Compatibility and acceptance before implementation

The current [[file:../../../modules/module-authoring/semantic-module.ss][UserConfigSourceRole.]] forbids .def/.o in ordinary user roots. The target
native extension examples require an explicit governance decision: admit the
bounded native declaration route in that role, or place extension definitions
in the existing maintained/vertical owner role and import them into a narrower
root. This document does not silently relax admission or assert these examples
already pass the current user-root checks. The final source-role decision must
preserve the authorized native user extension route.

Before implementation, finalize domain defaults, exact policy support, depth
counting, checkpoint isolation and adapter ownership. A real implementation
must prove each slot affects its named consumer, reject unsupported/unknown
configuration, preserve contracts under override, keep other Profiles unloaded,
handle parent-first lazy forcing, and enforce runtime bounds. Add method-level
extension only when the owning POO protocol and runtime adapter exist; raw
callbacks or fresh selector symbols do not substitute for that work.

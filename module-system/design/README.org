* Ownership

This is the owner of shared Module directory Contracts, publication/selection
protocols, baseline Core versus optional extension boundaries, lazy namespace
projection and generic selected build contributions. The implementation is not
changed by these documents. Existing Core mechanism owners remain where they are.

| Design | Owner |
|--------+-------|
| Standard published Module source roles | [[file:01-source-roles.org][Source-role Contract and assembly boundary]] |
| Directory snapshots and native lazy namespace | [[file:02-directory-sources.org][Directory Contract and projection design code]] |
| interface publication, init selection and Module/Feature boundary | [[file:03-publication-selection.org][Publication and selection protocol]] |
| Selected module closure and build contribution projection | [[file:04-selected-build-view.org][Pure selected build view design code]] |

Core remains independent of POO Flow, its JSON Schema bridge, current product-specific adapters, ASP build policy and deployment providers. Optional-extension and
build protocols may be implemented by consumers; Core must not import product
owners to implement a shared primitive. The reusable Feature System is targeted to Core under
[[file:../../feature-system/design/README.org][its extraction design]]; the current product implementation cannot simply be
imported back into Core. Moving documentation is not a source/API
migration or proof that an adapter has been implemented.

Core owns init selection semantics, directory/source-role Contracts, publication,
Core/Feature integration and selected build graph design, including their research
and validation material. POO Flow retains actual module implementations, source
policy adapters, concrete Profiles/Scenarios and end-to-end resource qualification.
Examples from those consumers do not create a Core runtime dependency.

* Complete chapter and migration boundary

The [[file:00-index.org][complete Module System design chapter]] now lives beside this guide.
The former product chapter contained 694 files, including Scheme/Lean probes,
diagrams and historical receipts; all were relocated, not replaced by links to
product-owned design. The 131 non-document files were byte-preserved. Historical
commands, source identities and measured results remain historical; moving them
does not establish current acceptance or authorize execution.

Read [[file:ownership-and-migration.org][ownership, remaining source boundaries and validation limits]] before treating an
old product integration proposal as a current Core requirement. Shared mechanisms
are maintained here; concrete application integration may remain downstream.

* Existing and pending

Existing: native POO object/slot semantics; [[file:../graph/funs.ss][module-closure]]; Module/source/schema
values and static Loader mechanisms; bounded scope syntax in profile-composition.
Pending: the stronger published-Module role shell, hierarchical directory source
adapter, publication metadata admission, retained disable integration and selected
build-view protocol. The object Contract's proposed shorter public name still
requires a separate rename of the existing Core export; no alias is added here.

Use exact source/currentness evidence and selected-demand controls before claiming
performance, completeness or automatic discovery. No runtime/Loader is implemented.

#+title: Validating Model Understanding, Reasoning, and Execution in Scheme
#+date: 2026-10-03
#+status: User-defined validation objectives. New model experiments pending at the initial design stage. MRR deferred.

* Why the earlier experiment supplied a prompt

The earlier implementation measured JSON restatement after supplying rules and
native answers. =runtime_accuracy= combined natural-language RULES with task
data and appended the complete Scheme result for the Runtime group. The model
ran in non-thinking mode. This clarified the rules and response format, but
supplying the interpretation and answer changed the experiment's objective.

The increase from 25% to 91.67% measures restatement on those historical inputs.
It establishes no result for Scheme understanding, logic syntax, reasoning, or
learning from live feedback. The non-thinking setup also cannot qualify the
requested Reasoning capability. Those runs have been removed from design
acceptance. The active prompt construction and paid invocation paths were
removed. Preserve original request plans and responses as auditable history.

* Validation objectives

Evaluate whether the model understands actual Scheme programs in the repository,
reasons independently, and generates executable Scheme. The native Runtime
executes the artifacts and checks them afterward. Correct native solving,
answer copying, and Guard rejection provide supporting evidence only. Keep
independently computed ground truth outside model inputs.

| Capability | Existing code interface | Observable result |
|------------+-------------------------+-------------------|
| Scheme understanding | ASCENT =program/scheme-language.ss=, =relational-program= and =relational-fragment= | Correct lexical capture, variable and scope handling, fresh names, and behavior after macro expansion |
| Logical and relational reasoning | =relation=, =rule=, =limits=, =relational-op-join=, and =relational-op-fix= | Correct joins, recursive closure, boundaries, and resource limits on inputs supplied without answers |
| Syntactic and semantic admission | ASCENT =program/scheme-admission.ss= | Generated programs pass actual admission, with verifiable failure codes and source locations |
| Evidence and currentness | ASCENT =candidate/reasoning.ss= and =temporal/lens.ss= | Distinguish =complete= from =valid= and detect changes in generation, cut, window, or source withdrawal |
| POO composition | POO =src/scenario/composition-syntax.ss=, =src/graph/types-core.ss=, and =src/graph/algorithms.ss= | Compose actual objects, topology, and execution paths with verifiable results |
| Python Runtime collaboration | POO semantic ABI and the Python graph executor | Scheme-checked artifacts reach actual scheduling, I/O, and persistence, with effects that match computation |

Each task must bind to the existing logic syntax and module version specified
by the user. Leave the meaning of “Pro” open pending that concrete binding.

* Model input and evaluator separation

The new experiment excludes authored system or developer tutorials about the
semantics, RULES templates, few-shot solutions, step-by-step derivations,
answer keys, and solutions precomputed by the native solver. The same exclusion
applies to content labeled context, tool description, Guard text, or protocol
instructions. Historical source Q&A, preset seed repair, and answer restatement
runs cannot serve as acceptance evidence for this protocol.

Record the provenance and original bytes of the actual source code, the user's
original task, and the execution input separately. The experiment adds no
natural-language solution instructions. Validate the minimal task envelope
against the actual provider API before claiming prompt-free integration.
Source can serve as task material with explicit provenance and scope. Keep
answer keys, native answers, and evidence derived after execution on the
evaluator side.

Require model artifacts to use the existing Scheme interface. Keep execution
semantics in Scheme and use the ABI byte projection for cross-language
transport. A Python-owned interpreter or a second JSON semantic DSL would
fall outside this validation protocol.

* Execution and independent verification

1. Pin exact POO and ASCENT source commits and native artifacts. Generate tasks
   from existing syntax and operations, with answers withheld and coverage
   across sizes, topologies, and boundaries.
2. Preserve the model's initial Scheme artifact or observable prediction.
   Record first-attempt performance before compiling, admitting, and solving
   with Scheme. The evaluator must leave missing model logic unfilled.
3. Cross-check execution with an independent finite oracle, a native
   qualification test, or a different algorithm. Comparing the response with
   an answer supplied in its input cannot establish independent verification.
4. Check invariance under renaming, input permutation, and irrelevant facts.
   Also check the expected changes when withdrawals, generations, windows, or
   reachable edges change. Require new judgments for tasks with answers withheld.
5. Send admitted artifacts through the actual Python Runtime and verify traces,
   actions, file I/O, cancellation, and persistence. Require observed effects
   for end-to-end acceptance.

Task generation rules can be fixed in advance to prevent cherry-picking.
An isolated evaluator computes the answers and keeps the evaluation procedure
separate from the model's task input.

* Live teaching through Guard

Guard computes feedback from the current Scheme artifact, current source, and
actual execution state. It may report source locations, actual admission
diagnostics, binding changes, execution observations, or computed
counterexamples. Every item must trace to the current computation. Preset
natural-language tutorials fall outside this feedback channel.

The experimental scorer recomputes the current task natively and reports
difference paths and counterexamples. The production Runtime also provides
task prediction and per-attempt observation. Transfer after feedback still
requires evidence. Preparation, stage evidence, and qualification are recorded
separately. [[file:model-scheme-validation-record.org][Execution record]]

The historical =render_temporal_answer= restatement interface was removed.
=temporal.verify= remains a lazy candidate check. After the model responds,
=temporal.observe= computes differences and delivers them to caller-owned I/O
through =observation_sink=. The caller controls retries. Runtime structured
feedback and online weight updates are distinct deliverables. Evidence of
learning remains open for both and requires more than a correct or rejected
attempt.

Evaluate live teaching on fresh tasks with answers withheld. Record
first-attempt and post-feedback performance, cross-task transfer, and error
propagation separately. Count repeated attempts honestly. Treat feedback from
an earlier source or generation as historical after the source or generation
changes.

* Reasoning, benefit, and completion criteria

Record the Reasoning configuration and the provider's reported usage. Historical
runs with reasoning disabled cannot qualify Reasoning. Evaluate reasoning with
executable artifacts, outcome predictions, boundary judgments, and transfer to
new tasks. Base the result on observable performance.

| Metric | Report separately |
|--------+-------------------|
| Understanding and reasoning | First-attempt syntax pass rate, semantic accuracy, outcome precision and recall, boundary judgment |
| Live teaching | First-attempt score, score after computed feedback, transfer to held-out tasks, feedback latency |
| Actual execution | Agreement across native computation, admission, traces, and I/O, with error and refusal coverage |
| Cost and performance | Tokens and cost, reported reasoning usage, Runtime and I/O duration, total latency, resource use |
| Validation gate | Correct acceptance rate, coverage, false acceptance, and false refusal. Refusal does not count as task success |

The new protocol completed 24 independently authorized runs. The original
interface scored 0/24. Supplemental lazy extraction produced 5/6 for =high=
initial predictions and 5/6 for each of the two transfer conditions. This
post hoc analysis leaves the frozen acceptance result in place. Teaching
accuracy gains remain unproven. The previous 48-run budget was unused in
these experiments. The execution record contains the detailed results, budget,
failures, and native engineering qualification.

Retain ABI engineering evidence from RFCs 63, 120, and 150. Model understanding,
prompt-free integration, live teaching, and its effectiveness remain open.
MRR Rust Runtime integration follows completion of those objectives and passing
CI for the corresponding commit.

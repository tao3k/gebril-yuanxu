* Cedar capability grant closure

** Cedar grant requirement

A profile contributes capability *requests*.  It never manufactures policy
grants.  A grant consumed by =use-composition= MUST be an =allow= decision from
the Cedar dual-engine boundary and MUST be bound to all of the following:

- the exact profile origin identity;
- the active runtime generation;
- one shared Cedar authorization subject for both engines and the grant;
- the current authority, policy, authorization, and revocation validation
  context;
- a valid, versioned subject-context bridge receipt whose registry identity and
  generation are bound to both request and grant, and whose mapping from Cedar
  policy-set digest to policy snapshot identity is functional;
- an authority-owned validation result whose authority identity equals the
  current receipt-validation context and whose registry semantic identity is
  bound to both request and grant;
- an authorized capability set that is a subset of the profile request, and a
  granted set that is a subset of that authorized set.

The grant is therefore evidence owned by the policy/admission plane.  Neither a
Mix object nor the composition macro may copy requested capabilities into a
granted slot.

** Observation and counterexample

The existing dual-engine theorem proves that two distinct engines decide the
same Cedar subject consistently.  The existing capability-envelope theorem
proves confinement of granted capabilities to an authorized set.  Their plain
conjunction is nevertheless insufficient for composition: it does not state
that the grant belongs to the profile identity and runtime generation currently
being composed.

=legacyAdmissionAcceptsCrossProfileGrantReuse= constructs two valid, distinct
Cedar =allow= receipts and a capability-confined grant issued for the
origin-aware identity =(module 42, slot 7, lineage 100)=.  The legacy
conjunction still admits it for =(module 42, slot 8, lineage 101)=.
=legacyAdmissionAcceptsCrossGenerationGrantReuse= constructs the analogous
replay from generation =11= into generation =12=.  These are architectural
counterexamples, not Cedar engine failures.

The first bridge draft still used the higher-order predicate
=AuthorizationSubject -> ReceiptValidationContext -> Prop=.  The predicate
=fun _ _ => True= inhabits that type while providing no registry owner,
generation, lookup receipt, or uniqueness evidence.  Worse, an accept-all
validator can admit two receipts mapping the same registry generation and
policy digest to different snapshots.  The theorem
=acceptAllBridgeReceiptsAreNotFunctional= is the executable counterexample.

Functionality is still not authority.  A validator that accepts exactly one
forged receipt is trivially single-valued.  The theorem
=forgedSingletonIsFunctionalButUnauthorized= constructs such a validator: its
claimed authority is =999= while the current validation-context authority is
=17=.  Consequently, bridge closure now consumes the existing generic
=AcceptanceAuthority= and =AuthorityBoundNode= contract instead of trusting a
self-reported =valid= predicate.

#+begin_export typst
$
  G_(closed)(q, g, l, r) :=
    D_(dual)(l, r)
    and l.subject = q.subject
    and g.subject = q.subject
    and l.decision = allow
    and g.profile = q.profile
    and g.generation = q.generation
    and g.context = q.context
    and V_(bridge)(b)
    and A.validate(b.receipt) = b.binding
    and A.accepted(b.binding)
    and b.authority = q.context.authority
    and b.semantic-id = q.bridge-semantic-id
    and b.registry = (q.bridge-id, q.bridge-generation)
    and b.policy-digest = q.subject.policy-digest
    and b.policy-snapshot = q.context.policy-snapshot
    and F_(bridge-registry)(V_(bridge))
    and g.granted subset.eq g.authorized subset.eq q.requested
$
#+end_export

The formula deliberately keeps profile identity separate from the Cedar
subject.  The subject binds policy evaluation inputs; the profile identity
binds the result to the precise composition operand.  Collapsing either one
into the other would lose a required replay dimension.

** Cedar grant decision

- =CompositionCedarGrantClosed= is the formal admission contract joining the
  existing Cedar dual-engine, receipt-context, and capability-confinement
  models.
- A closed grant rejects profile mismatch, generation mismatch, Cedar-subject
  mismatch, and stale policy/authority context independently.
- Because Cedar uses content digests while the receipt context uses snapshot
  identities, closure requires a valid bridge receipt from a named registry
  generation.  Sharing one request record does not by itself prove that those
  two namespaces denote the same policy snapshot.
- =SubjectContextBridgeRegistryFunctional= makes the mapping single-valued for
  every =(authority identity, registry semantic identity, registry identity,
  registry generation, policy digest)= key.  An arbitrary proposition or
  accept-all receipt validator is not admissible.
- The bridge reuses =ReceiptAuthorityBindingClosure.AcceptanceAuthority= and
  =AuthorityBoundNode=.  The receipt artifact is validated into an exact
  binding; self-reported acceptance is never sufficient.
- Every granted capability is proven to belong to the original requested set.
- The parent proof owns this cross-plane contract.  The
  =lambda-episteme= child may publish profiles and requests, but it does
  not own the parent Cedar admission lifecycle and is never scanned or executed
  implicitly to validate the proof.
- This theorem does not claim that the current Scheme composition runtime has
  implemented the admission call.  That concrete POO runtime owner
  remains open together with =compose-proto*= and =instantiate-proto=; the proof
  prevents an incomplete implementation from being described as closed.

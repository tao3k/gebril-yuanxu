* Internal POO shapes

The three semantic projections use named internal predicates:

#+begin_src text
mix-module-object?
mix-module-identity?
mix-module-imports?
mix-module-capabilities?
module-capability-demand?
#+end_src

The minimum shape is:

#+begin_src text
mix-module-object?(x):
  object?(x)
  and x has slots identity, imports, capabilities
  and mix-module-identity?(x.identity)
  and mix-module-imports?(x.imports)
  and mix-module-capabilities?(x.capabilities)
#+end_src

=mix-module-identity?= accepts the immutable POO identity value emitted by the
module declaration/expansion.  It does not accept a local alias, filesystem
path, gitlink, =gerbil.pkg= record, build target, or runtime-context identity.

=mix-module-imports?= validates a POO container of declared
=ModuleCapabilityDemand= objects.  A demand has internal POO slots:

#+begin_src text
moduleIdentity
capabilityIdentity
computation
#+end_src

=computation= must be a procedure and is invoked only through
=resolve-module-capability=.  Users never construct or call a demand directly.

=mix-module-capabilities?= validates a POO capability container.  Each declared
capability owns a named shape predicate.  The container predicate validates
slot declarations without forcing every capability value; the capability value
predicate runs when that capability is demanded.

Shape validation MUST NOT call =force-object=, traverse arbitrary nested POO
objects, or eagerly invoke import computations.  Validation itself must not
turn lazy composition into eager global evaluation.

#+begin_mermaid
flowchart TD
    Module["Candidate MixModuleObject"] --> Slots["Check identity/imports/capabilities slots"]
    Slots --> Identity["Validate immutable identity"]
    Slots --> Imports["Validate import demand declarations<br/>without invoking them"]
    Slots --> Capabilities["Validate capability declarations<br/>without forcing values"]
    Imports --> Runtime["Demand-time resolve-module-capability"]
    Capabilities --> Runtime
#+end_mermaid

* Parser and macro phases

The phase boundary is:

#+begin_mermaid
flowchart LR
    Source["Canonical user syntax"] --> Parse["Existing canonical parser"]
    Parse --> Plan["Hygienic composition plan"]
    Plan --> Emit["Emit ordinary POO Gerbil code"]
    Emit --> Runtime["Runtime context + G0 gate"]
    Runtime --> Resolve["Capability resolution"]
    Resolve --> Result["Composed user object"]
#+end_mermaid

Compile time performs only:

- exact grammar validation;
- hygienic identifier and alias binding;
- bounded Profile/module declaration normalization;
- generation of named POO predicates and prototype compositions;
- generation of ordinary calls to the pinned API.

Compile time does not:

- run G0;
- inspect the active runtime context;
- import-probe a dependency;
- resolve a capability;
- emit a DecisionReceipt;
- consult GSLPH, Gerbil-Bazel, or =gerbil.pkg= runtime state.

The macro expansion follows this semantic sequence:

#+begin_src text
canonical use-composition syntax
  -> parser-owned composition plan
  -> hygienic module alias bindings
  -> internal MixModuleObject prototypes
  -> ordered selected Profile prototypes
  -> compose-proto*
  -> instantiate-proto with explicit base
  -> mix-module-object? validation
  -> runtime publication
#+end_src

The expansion may generate raw self/super procedures because they are ordinary
internal POO implementation code.  It may not expose those procedures as
Profile-author syntax or accept raw user compute hooks.

This phase structure follows
[[file:../88-phase-aware-composition-macro-architecture.org][88]] and the bounded
macro style in
[[file:../44-current-project-programming-style.org][44]].

* Author surface

Profile authors continue to use:

#+begin_src text
.def
.mix
@
super
slot:=
~=>
~=>.+
#+end_src

Raw self/super lambdas may be generated by hygienic macros but are not ordinary
user syntax.

* Recursive modules

#+begin_mermaid
flowchart LR
    A["A Profile"] -->|"A.imports.b"| B["MixModuleObject B"]
    B -->|"B.imports.c"| C["MixModuleObject C"]
    C --> Cap["Capability"]
    Cap --> User["Composed user object"]
#+end_mermaid

All descendants share the active runtime context and do not repeat parent G0.

* Alias hygiene

=use-module MODULE as ALIAS= creates a hygienic composition-local binding.
The alias:

- must be an identifier accepted by the canonical parser;
- must be unique within that composition scope;
- does not mutate =MixModuleObject.identity=;
- is not converted through string/symbol =eval=;
- cannot access =resolve-module-capability=;
- does not enter Requirement, Observation, Policy, DecisionReceipt, package
  identity, or runtime-context identity.

Generated internal identifiers are hygienic and cannot be captured by Profile
slot names.  Runtime capability resolution uses the alias-bound module object,
then the module's semantic identity and capability identity.

* Invalid module objects

Syntax that lacks canonical =use-module MODULE as ALIAS= fails through the
existing =composition-invalid-module-form= parser contract.

A resolved binding that is not a valid =MixModuleObject= raises
=InvalidMixModuleObjectCondition= under the 45-03
=CompositionEvaluationCondition= family.  Its bounded reasons are:

#+begin_src text
missing-identity-slot
invalid-identity
missing-imports-slot
invalid-imports
missing-capabilities-slot
invalid-capabilities
capability-shape-mismatch
identity-overridden
#+end_src

This is a runtime composition condition, not a G0 semantic rejection.  It
creates no DecisionReceipt.  45-04 owns its detached diagnostic presentation.

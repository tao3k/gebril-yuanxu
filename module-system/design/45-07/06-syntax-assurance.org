** Proof-discovered binding, identity, and demand constraints

=UseCompositionBindingIdentityDemandGapModel= separates constraints that the
previous prose had conflated.  The public macro head, lexical binding, runtime
lineage identity, profile coordinate, provenance identity, demand generation,
and mutable demand state are different semantic dimensions.

The current expression macro requires
=(def my-system (use-composition my-system ...))=.  The Lean countermodel proves
that this does not satisfy the RFC's direct-binding contract even though its
parser head is canonical.  Reintroducing =user-composition= would repair the
binding only by violating the single-head contract, so it is not an admissible
solution.

Alias spelling cannot own profile identity: renaming an alias would change an
alias-derived identity for the same module profile.  Slot name alone is also
insufficient because two modules may export the same slot.  The candidate
identity for an exported profile must therefore contain module semantic
identity and slot identity, while the fresh =gerbil-poo= lineage root remains
explicit and alias independent.

That coordinate is not valid for every profile origin.  A local POO Profile,
Mix, or prior composition has no intrinsic module-export coordinate.  The
current mandatory =use-module= syntax can wrap such a value in a presentation
module, but the wrapper identity MUST NOT become the local value's semantic
identity: renaming =local-profiles= would otherwise rename the same POO object.
The proof model therefore uses an origin sum: =moduleExport(module, slot)= or
=localLineage(lineage-root)=.  Both alternatives retain the explicit fresh
lineage root.  This is a proof constraint, not yet the selected concrete Gerbil
prototype or a decision to keep/remove the mandatory module clause.

The current lowerer already supplies the necessary distinction.  An imported
=(profiles NAME ...)= object retains its source module identity.  An existing
or locally declared =(profile NAME)= value does not receive the enclosing
wrapper module or alias as object fields; those values survive only in the
composition-level module-binding and profile-binding metadata.  The future
identity prototype MUST derive local identity from the local POO value and
lineage, never from that lookup metadata.

Consequently wrapped and direct local syntax form one semantic equivalence
class.  Two wrapper spellings may be syntactically different yet elaborate to
the same local identity; a direct local reference is the normal form of that
class.  This quotient does not apply to imported profiles: changing a real
source module changes =moduleExport(module, slot)= and therefore changes
identity.  The proof makes the two interface options comparable without
prematurely selecting one.

Demand state cannot participate in profile identity because a normal
=pending -> realizing -> realized= transition would mutate identity.  Demand
lookup also cannot use profile identity alone: the same profile in two runtime
generations would alias a stale realization.  The candidate demand key must
bind profile identity and runtime generation while keeping mutable demand state
outside semantic identity.

** Reserved-slot projection and authority noninterference

The parser currently admits =(profile NAME)= when =NAME= is merely an
identifier.  The lowering path passes the resolved value through unchanged and
does not prove that it is a POO Profile object.  A higher-order Mix therefore
enters the ordered profile list as the whole Mix value; no concrete projection
currently strips its =identity=, =imports=, or granted =capabilities= slots.
Semantic prototype composition is still deferred, so this is an admission and
future-composition gap rather than evidence of a currently executed takeover.

=UseCompositionReservedSlotProjectionGapModel= makes the unsafe future path
explicit.  Directly composing a complete Mix object with an ordinary
right-biased prototype operator lets the Mix replace the target module
identity, import closure, and granted capabilities.  The counterexample changes
=identity= from 42 to 99, =imports= from 5 to 77, and grants from 1 to 255.

The safe path is a named POO projection from Mix to =ProfileContribution=.
That contribution contains ordinary domain refinements and /requested/
capabilities only.  Composition preserves the target's sealed authority slots;
requested capabilities remain evidence for a later policy decision and never
become granted capabilities by prototype composition.  Existing operands must
fail closed unless the identifier resolves to a POO object with an admitted
Profile projection.

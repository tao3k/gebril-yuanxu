* Start here: what upstream provides

These are target user examples, not shipped interface receipts. Scenario objects
and their automatic nested construction/admission adapters remain proposed.
The source Modules and default stage payloads are grounded in the repository.
No implementation or runtime behavior is changed by this document.

| Upstream asset | What downstream users do with it |
|----------------+----------------------------------|
| maintained LangGraphScenario, CrewAIScenario, ToolCallingScenario | inherit one with .def and override desired configuration |
| LangGraphModule, CrewAIModule, ToolCallingModule | explicitly use-module to bind the maintained default contribution |
| maintained reusable Profiles | reuse or derive compatible native values; publish user-owned contributions through a Module |
| domain composition/Profile Contracts | optionally initialize new typed values when maintained Scenarios are insufficient; constructor adaptation is proposed |

The normal reading order is: choose a Scenario, derive a value, explicitly
select/rebind Modules if needed, refine configuration, then choose a configured
Profile for the later admitted execution boundary. You do not need to read
Contract-resolution helpers or generated object code to author the examples.
A Scenario already supplies stage, proof-declaration and handoff defaults.

When the maintained Scenario's Module choices already fit, omit the explicit
rebinding and write only the refinement. When introducing or changing a Module,
keep use-module visible: it shows source ownership and default binding. Placement slots supply object paths; as names a bounded lexical scope and
explicit instance alias in the proposed adapter.
There is no scenario-profile assembly field or second composition call.

native ancestry remain inherited. No raw constructor or prototype lookup is
needed for this ordinary change. Inherited Scenario graph/stage/proof/handoff declarations
remain configuration defaults, not executed runtime evidence.

** Scope: one user-facing Scenario model

These are source-grounded design outputs, not migrated or executed files.
Scenario bases, default proto wiring, CompositionContracts and helpers below
are proposed owner exports. Existing Module selections, stage defaults and
legacy workflow payloads are retained. The [[file:164-profile-module-targeting-design.org][main design]] owns recursive construction,
dynamic Contract resolution, slot-owned instances and fresh effective composition.
No user-interface implementation is changed.

Profiles can be reused across Scenarios. Users or vertical-domain companies
maintain reusable Scenario objects already carrying composition/defaults and
CompositionContracts. Consumers instantiate and extend them with native .def.
They do not call a second composition wrapper or repeat assembly in a separate
public Case. Current user-composition already
returns an internal Scenario Case with plan/admission and Session behavior;
that runtime representation is retained. Legacy custom Case files also provide
workflow data, which is shown as Scenario-owned configuration below.

Keep use-module explicit: it shows Module introduction, source binding and
selected exports. Hide only redundant aliases, prototype headers and default
assembly objects. Source imports show built-in versus user-owned Modules.
Default stages, proof declarations and handoff come from the concrete Scenario
Profile proto; users do not write a scenario-profile slot.

Multi-export selections below require an identity-preserving configured collection,
not car or flattened identity/name/contract fields. This adapter is unimplemented.
Source proof booleans are declarations, not passing verification receipts.

** Common Contract and domain-specific Scenario Contracts

The [[file:164-profile-module-targeting-design.org][main design]] defines the proposed CompositionContract foundation. All
three root Contracts below refine it; CompositionContracts (plural) remains a
family of related Contracts/rules, not a substitute for the root base Contract.
Scenario values inherit a domain Contract's proto, never the descriptor itself.

#+begin_example
CompositionContract
  LangGraphCompositionContract -> LangGraphCompositionContracts.Project
  CrewAICompositionContract -> CrewAICompositionContracts.Project
  ToolCallingCompositionContract -> ToolCallingCompositionContracts.Project
#+end_example

#+begin_src scheme
;; Proposed library-owned domain Contracts, not existing public exports.
(define-type (LangGraphCompositionContract @ CompositionContract)
  identity: 'langgraph-composition
  proto:
  (.o (:: composition-self (.get CompositionContract proto))
    %composition-contracts: LangGraphCompositionContracts
    Profiles: (%scenario-default-profiles LangGraphCompositionContracts))
  responsibilities: =>.+ (.o Profiles: LangGraphProfilesContract))

(define-type (CrewAICompositionContract @ CompositionContract)
  identity: 'crewai-composition
  proto:
  (.o (:: composition-self (.get CompositionContract proto))
    %composition-contracts: CrewAICompositionContracts
    Profiles: (%scenario-default-profiles CrewAICompositionContracts))
  responsibilities: =>.+ (.o Profiles: CrewAIProfilesContract))

(define-type (ToolCallingCompositionContract @ CompositionContract)
  identity: 'tool-calling-composition
  proto:
  (.o (:: composition-self (.get CompositionContract proto))
    %composition-contracts: ToolCallingCompositionContracts
    Profiles: (%scenario-default-profiles ToolCallingCompositionContracts))
  responsibilities: =>.+ (.o Profiles: ToolCallingProfilesContract))

;; Maintained configured Scenario values: they may add owner refinements here.
(.def (LangGraphScenario @ (.get LangGraphCompositionContract proto)))
(.def (CrewAIScenario @ (.get CrewAICompositionContract proto)))
(.def (ToolCallingScenario @ (.get ToolCallingCompositionContract proto)))
#+end_src

Domain Profiles Contracts and dynamic rule sets are owner definitions. They
must preserve the generic Profiles collection Contract and base obligations.
LangGraph requires its seven graph contributions and bounded state-graph rules;
CrewAI its fourteen crew/task/flow contributions and review/checkpoint rules;
Tool Calling its eleven request/validation/permission/receipt contributions.
The stage defaults below are provided by their dynamically resolved Profile
Contracts, not fixed fields of CompositionContract. All name and rule policies
remain Scenario/domain choices. Family association must bind Project to the
matching root domain Contract, not another Contract selected by a user field.

Users may author their own Profiles, inherit maintained Profile/Scenario values,
or initialize new values under upstream domain Contracts. Those intentions may
be combined. The following domain examples compare two parent-normalization
branches, not an exhaustive list of user intentions or mandatory steps. Direct
Contract parent recognition is proposed; the native expansion still extracts
its shared proto. Existing Scenario parents remain the actual parent object.

** Configuration construction is not Session execution

Native .def derives an object from a maintained Scenario. Responsibility-driven
nested construction remains a proposed owned adapter and is not current native
.def behavior. Contract admission then checks the actual effective object and
its evidence. Selected Profile composition and plan/root projection are inert.
Only an explicitly created fresh Session performs its owned lifecycle and
runtime handoff. These phases are not a second public composition hierarchy:
object creation is not validation, and neither validation nor plan projection
starts an executing Session. Existing Case/Session implementations are retained.

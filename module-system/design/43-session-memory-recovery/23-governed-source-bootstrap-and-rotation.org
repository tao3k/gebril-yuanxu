Controller creation is privileged application DI with an explicit configured

Trusted controller setup remains a premise; bootstrap binding and subsequent
source replacement underneath it are checked operations.

* Proposal, authorization and publication

=source-control.ss= issues exact POO proposals with target source, Governance,
operation and payload. Private state captures controller, expected configuration
generation and target source revision. Generation zero denotes bootstrap;
later generations denote replacement. Copying a proposal/control or adding
claimed authorized fields does not change issuance.

Authorization uses the existing Core verification issuer. Its snapshot binds
the exact proposal through a frozen sequence, operation, expected generation,
target revision, Governance identity/revision/owner/threats and canonical
domain payload. Governance assesses the actual proposal: unresolved high /
critical exposed threats block signing. Changed target revision invalidates
an outstanding proposal.

The named Assurance source-control adapter requires current evidence at its
verification Host, a current issued grant at its effect Host, and an explicit
source-policy decision approving the target/action. Evidence/grant alone
cannot approve arbitrary targets. Host validity is rechecked after the policy
callback; callback-triggered revocation cannot mint approval. No service
effect or delivery callback runs.

Commit rechecks current proposal/generation, real Core receipt and expiry,
current approval and target/Governance snapshot. Domain callbacks run outside
the controller mutex. Expected generation and receipt are checked again in
the CAS publication critical section; receipt revocation shares that lock.
Success advances the integer generation and returns an exact issued binding.
Competing stale-generation proposals cannot both publish. Missing, copied,
expired, revoked and cross-proposal/controller receipts change no binding.

The configured clock must be a pure trusted observation. Local CAS and receipt
revocation are atomic; independent Host policy/grant observations are not a
distributed transaction. Cross-authority concurrent policy updates require
their Host's own ordering semantics. No arbitrary remote linearizability is
established by this local protocol.

* Source rotation and obligations

Parent and named Assurance admission constructors require =authorization:=
alongside source and Governance DI. The binding must be exact/current and
agree with both referents. Missing/copied/fabricated bindings cannot create
an admitted consumer Profile. Normal POO extension retaining the adapter
still works; private adapter pins include the binding, not displayed fields.

Replacement retires the old binding generation. Old Profiles cannot review
or admit even if their old registry/content remains current. Obligations
reopen and ASCENT candidates withdraw. The new binding requires a new
Profile/review; old reviews cannot be used by the new adapter. A -> B -> A
returns to source identity, not the old configuration subject. Old A Profiles
and unexpired authorizations remain invalid. The Case keeps its bootstrap
receipt unexpired to isolate ABA refusal from accidental expiry.

Revoking a pending receipt prevents commit; it is not implicit rollback of
historically committed configuration. Changing accepted configuration requires
another governed proposal. Live consumption retains its own current source,
review and permission requirements. Rotation does not delete historical ORG
evidence, counterexamples or independent Project knowledge. Source approval
is neither effect authority nor protected disclosure permission.
